## 1. 头像更新成功但图片不变

**计划声称**：浏览器缓存 + `AccountSettings` 未清缓存 + `LeftAvatar`/`UserMenuHeader` 读不同字段。修复：给 `getAvatarUrl` 加 `bustCache` 参数。

**实际代码**：
- `AvatarUtils.getAvatarUrl` 采用 **mxc→http 的 memoization 缓存**，并独立提供了 `bustCache(url)` 与 `clearCache()`，但**并未按方案给 `getAvatarUrl` 加 `bustCache` 参数**。
- `AccountSettings.handleCrop`（已落地）调用 `userStore.updateAvatar(mxcUrl)` + `AvatarUtils.clearCache()`。
- `userStore.updateAvatar`（`src/stores/domains/user/user.ts:114`）**只更新了 `matrixProfile.avatarUrl`，没有同步 `userInfo.avatar`**。
- `LeftAvatar.vue:11` 读的是 **`userStore.userInfo?.avatar`**；`UserMenuHeader.vue:82`、`UserMenuMobile.vue` 读的是 `currentUserAvatarUrl`（= `matrixProfile.avatarUrl`）。
- 对比 `InfoEdit.vue:211-215`（左侧头像编辑的另一条路径）是**两个字段都更新**的。

**真正根因**：设置页改头像走的是 `updateAvatar` 路径，它只写 `matrixProfile.avatarUrl`，而主界面 `LeftAvatar` 读的是 `userInfo.avatar` → 该字段保持旧值 → 头像不变。计划正确识别了"两个入口读不同字段"，但修复只调了 `updateAvatar`，漏在 `updateAvatar` 内部没同步 `userInfo.avatar`。

**本次修复**：在 `userStore.updateAvatar` 中同步写 `userInfo.value.avatar = avatarUrl`，与 `InfoEdit` 路径一致。新头像 mxc 改变 → `AvatarUtils` memo 键变化（`clearCache()` 也已调用）→ 浏览器拿到新 URL，`LeftAvatar` 立即刷新。

## 2. 消息列表多个 test1 重复

**计划声称**：同一用户多个 DM 房间，去重在 `detailId` 为空时失效。修复：显示层 `useSessionListState` 增强去重 + 服务层 `getSessionList` 防御性去重。

**实际代码**：
- 显示层 `useSessionListState.ts:87` 的去重已落地：`dmSeen` 按 `toLocalpart(item.detailId || item.account || '')` 过滤——逻辑正确。
- 服务层 `getSessionList`（已落地）去重键：`counterpartId = session.detailId || session.roomId`。
- **但 `buildSessionFromRoom`（`MatrixSessionService.ts:212`）的 `detailId` 仅来自 `dmRoomInfo`（`m.direct` 映射的 `invitees/inviter`）**。若房间未注册进 `m.direct`（历史/重复创建的 DM 房间极常见），`detailId = null` → 去重键退回 `roomId`（唯一）→ **无法合并**。

**真正根因**：去重逻辑本身没问题，问题在于**去重键 `detailId` 经常为空**。两个同名 "test1" 的 DM 房间若都没进 `m.direct`，`detailId` 都是 null，按 `roomId` 去重就各自保留 → 列表出现重复。计划只"加了去重壳"，没解决"键从哪来"。

**本次修复**：`buildSessionFromRoom` 在 `dmRoomInfo` 缺失时，从 `room.getJoinedMembers()` 解析"除自己外的另一名成员"作为 `detailId`。这样双人房一定有 counterpart，`detailId` 被填充，显示层与服务层去重同时生效，重复 test1 被合并。

## 3. 好友"进入聊天 / 加密聊天"不跳转

**计划声称**：`focusSessionRoom()` 先跳 `/message`（无 roomId），watcher 检测到已匹配就跳过第二次跳转。修复：让 `focusSessionRoom` 直接 `push('/message/:roomId')`。

**实际代码**：
- 路由 `desktop.ts:37` 为 `{ path: '/message/:roomId?', name: 'message' }`——**支持 roomId 参数**，所以 `router.push({ name:'message', params:{ roomId } })` 能正确落地。计划的导航修复**已正确落地**。
- "进入聊天"按钮（`SingleDetails.handleSendMessage`）→ `useDetailsActions.handleSendMessage` → `useEnterChat().enterChat(uid,'friend')` → `openMsgSession(uid, SINGLE)`。即它**确实经过 `openMsgSession`**，计划的修复命中了它。
- "加密聊天"按钮 → `SingleDetails.handleEncryptedChat` → `contactStore.startDirectRoom` → `openMsgSessionByRoomId`。

**真正根因（已确认）**：导航代码（`focusSessionRoom` 直接 `push('/message/:roomId')`）已正确，卡点在 **`openMsgSession` 的第一步**：
`const res = await matrixSessionService.getSessionDetailWithFriends({ id: uid, roomType: type })`
`getSessionDetailWithFriends` → `getDirectSessionDetail(uid)` 的逻辑是：先 `getDmForUser(uid, false)`（manager 未就绪时静默返 `null`），再 `createDm(uid)`。而 `createDm` 内部 `requireManager()` 在 `dmManager` 为 `null` 时**抛错**，该异常被 `getSessionDetailWithFriends` 的 try/catch 捕获并 `return null` → `openMsgSession` 弹出 `获取会话详情失败` 的 toast 后直接 `return`，**根本不走到 `focusSessionRoom`** → 表现为"点按钮没反应/不跳转"。
关键诱因：`dmManager`（`client.getDirectMessageManager()`）是 Matrix SDK 扩展，初始化有先后依赖；好友详情点按钮时它常常尚未就绪，或该好友的 `m.direct` 映射未写入（历史/重复 DM 房间常见），于是 `getDmForUser` 返 `null` 并触发 `createDm` 失败。

**本次修复（Issue 3 根因修复）**：
在 `MatrixSessionService.getDirectSessionDetail` 中改为「本地优先 + manager 兜底」：
1. **第一步**：调用新增的 `findLocalDirectRoom(userId)`，直接扫描 `client.getRooms()` 中"成员数 === 2 且另一成员就是目标用户、且非空间房间"的已同步房间。只要有本地 1:1 房间，立即 `buildSessionFromRoom` 返回并跳转——**完全不依赖 `DirectMessageManager` 与 `m.direct` 映射**。
2. **第二步**：本地找不到才走原有 `getDmForUser`/`createDm` 流程（需 manager 就绪）。
3. **第三步（兜底）**：若 `createDm` 因 manager 未就绪抛错，再次 `findLocalDirectRoom` 兜底一次，仍找不到才 `return null` 并报错。

这样「进入聊天」「加密聊天」在**最常见的"已存在会话"场景**下，即使 DM 管理器未加载也能正确跳转。`handleSendMessage`→`enterChat`→`openMsgSession(uid)` 与 `handleEncryptedChat`→`startDirectRoom`→`openMsgSessionByRoomId(roomId)` 两条路径均已打通（后者本就绕过 `getSessionDetailWithFriends`）。

新增回归测试 `MatrixSessionService.test.ts`：「manager 无映射且 `createDm` 抛错时，仍从本地 1:1 房间解析出会话、不调用 `createDm`」——验证本地优先逻辑。

## 5. 设备列表出现大量设备（"我只在此设备登录过"）

**计划声称**：服务端返回全量历史设备，无过滤。修复：排序 + 突出当前设备 + "清除所有旧设备"按钮。

**实际代码**：
- `SessionSettings.vue` 已正确实现：分离"当前设备 / 其他设备"，`otherDevices` 按 `lastSeenTs` 降序排序，并提供"登出所有其他设备"。计划的显示优化**已落地**。
- `getDevices()` 来自 `useAccount`，最终调 Matrix `getDevices`——**返回的是该用户账号下的全部历史设备**。

**真正根因**：设备数量多**不是 UI bug**，而是 Matrix 的语义：每次登录/每次客户端初始化都会在服务器端注册一个 `deviceId`。结合本仓库历史已知问题"MatrixClient 重复初始化"（`MatrixClient重复初始化收敛-2026-08-09.md`），开发/调试过程中客户端被反复初始化会**累积大量 deviceId**，于是"只登过一次却看到几十个设备"。UI 已如实展示服务端数据。

**本次处理**：显示为正确行为，无需改 UI。治本方向：
1. 收敛 `MatrixClient` 重复初始化（已有专项），从源头减少 deviceId 产生；
2. 用户可在"设置→会话/设备"中一键"登出所有其他设备"清理历史遗留。
> 如需体验优化，可在 `otherDevices` 中折叠"超过 N 天未活跃"的设备，但非问题根因。

## 8. 设置子页面（更多-设置）全部空白

**计划声称**：`SettingsContent` 在 `computed` 内调 `defineAsyncComponent`（Vue 3 反模式），每次切换都建新实例 → 渲染空白。修复：模块作用域一次性创建。

**实际代码**：
- `SettingsContent.vue` 的修复**已正确落地**：`tabComponents` 在模块作用域由 `Object.fromEntries(...defineAsyncComponent...)` 创建，`<component :is="tabComponents[activeTab]" :key="activeTab">`。
- `vue-tsc --noEmit` 全量通过（EXIT 0）——**排除编译错误导致整页崩溃**。
- `AppearanceSettings.vue` 等 tab 组件**有真实内容**，非空桩。

**真正根因（第二层坑）**：反模式修好了，但 `defineAsyncComponent` **没有 `errorComponent`/`onError`**。当某个 tab 组件在**运行时**动态导入失败（例如依赖了被重构删除的模块、或导入链上有运行时异常），异步组件会**静默停留在错误态、渲染为空**，且因为 `tabComponents` 是模块级单例，首次失败后后续切换也持续空白 → 表现为"每个子页面都空白"。计划只修了"反模式"这一层，没修"运行时错误被吞掉"这一层。

**本次修复**：为所有 tab 异步组件加 `errorComponent`（红色明确报错，显示是哪个 tab 失败）+ `onError`（仅重试一次，避免死循环与瞬时时序误判）。这样若仍有 tab 空白，**会直接显示失败原因而非空白**，便于 10 秒定位是哪一个组件的问题。

**第二轮加固（用户实拍"外观设置"tab 空白、嵌入式面板无返回按钮）**：
1. `defineAsyncComponent` 的 `errorComponent` 仅捕获 **loader 失败**（动态导入 reject）。当某个 tab 加载成功后，在 `setup` 或 render 阶段抛错时（比如某个引用了未初始化 store/找不到 i18n key），`errorComponent` 不会被触发，整面板依旧空白。补一个 `onErrorCaptured` 钩子在 SettingsContent 这一层兜底渲染时异常，并把 `renderError` 状态绑到模板。
2. 非 standalone（嵌入式路由模式）原本只有一个圆 X 关闭按钮，仅 standalone 模式可见。嵌入式面板在 header 右侧新增 "返回" 按钮（ghost 风格，icon `mdi:arrow-left` + label "返回"），点击同样 emit `close`，由 SettingsPage 的 `handleClose` 用 `router.back()` / 回退到 `/message` 处理。
3. 新增 `src/views/settingsWindow/__tests__/SettingsContent.test.ts` 4 个用例：非 standalone 渲染返回按钮、standalone 渲染关闭按钮、render-time 异常触发红色兜底、切 tab 时清掉错误态。
