# P3（A8）isMobile 分支下沉立项方案

- 文档日期：2026-11-16
- 范围：`meta/ratchet-baseline.json` 中 `is_mobile_branch` 计数器当前值 `5` 的全部调用点
- 状态：**已实施完成**（B1–B4 全部落地，ratchet `is_mobile_branch` 5 → 3）
- 关联文档：`docs/UI优化方案-v2.4.md` §19.13（13 处收敛结论）、§19.27（10 → 5 批次）、§19.40（本项实施记录）

---

## 1. 结论摘要

1. 5 处调用中，**2 处是平台判定器/加载器本体**（`usePlatform.ts` 的 `useIsMobile` 与 `mobileOnlyAsyncComponent`），它们是本条 ratchet 的「抽象层边界」，不存在可迁移的移动端替身；机械清零只能靠改写谓词名，属于规避指标，本方案不做。
2. 真正可下沉的是 **3 处**：`PathUtil` 存储布局、`main.ts` 启动分支、`useWsEventHandler` 会话/来电分支。原设想「先建 5 个移动端替身」复核后修正为 **3 个移动端替身 + 1 个运行时组合根**。
3. 推荐方案为**运行期注册表（Registry）**，而不是构建期 `alias` 拆分：前者保留 `?platform=mobile` / `localStorage` 运行时覆盖契约（这正是 §19.13 判定「无法机械清零」的阻塞点），并且与仓库已有的 `registerPrivacyPreferenceHooks` / `registerCapabilityStoreResolver` 注入模式一致。
4. ratchet 目标：`is_mobile_branch` **5 → 3**（剩余为 `usePlatform.ts` 两处边界 + `main.ts` 一处组合根分派）。全程单调下降，不出现「先升后降」。
5. 新增 3 个移动端实现文件、1 个契约文件、3 个注册表模块、3 个桌面默认实现文件；新增/迁移单测 7 个文件。桌面行为零变更，移动端行为按等价迁移验收。

### 2.3 影响面

- `PathUtil`：`resolveStorageLayout()` 被 `getDownloadBaseDir`、`getDownloadBaseDirPath`、`getCacheBaseDir`、`getCacheBaseDirName`、`getScopedBaseDirCandidates` 5 个导出消费；`src/utils/__tests__/PathUtil.test.ts` 中约 7 条用例通过 `vi.mock('@/utils/PlatformConstants')` 切换 `true/false` 断言 AppData 分支。
- `main.ts`：`isMobilePlatform` 仅用于 eruda 与 `setup()`；`main.ts` 无单测，启动行为无既有自动化覆盖。
- `useWsEventHandler`：`App.vue:265` 实例化并 `registerHandlers()`；已有 `src/composables/app/__tests__/useWsEventHandler.manager.test.ts`，但未覆盖 `TOKEN_EXPIRED` / 旧来电两条分支。
- `usePlatform`：`useIsMobile()` 20 个文件 20 处调用；`mobileOnlyAsyncComponent()` 仅 3 个移动端预览走位。

### 2.4 为什么不能用构建期 alias 一刀切

仓库现有 `@/router/routes/desktop`、`@/services/matrix/admin/bridge` 两条 alias 只在 `!isPC` 时重写。若把 `PathUtil` / `useWsEventHandler` 也改为 alias 拆分：

- 构建期拆分后，`src/platform/**` 内不再有 `isMobile()`，ratchet 可降到 2；
- 但桌面浏览器 dev / E2E 的 `?platform=mobile` 运行时覆盖将失效，`PathUtil` 注释中「运行时平台覆盖仍需生效，故每次调用重新求值」的契约被破坏；
- 该契约是 §19.13 判定「不可机械清零」的直接原因，本次立项应解决它而不是绕过它。

## 3. 目标与非目标

### 目标

1. `is_mobile_branch` 单调下降至 `3`，并同步收紧 `meta/ratchet-baseline.json`。
2. 三处平台差异行为（存储布局、启动收尾、会话/来电策略）从共享代码移到 `src/mobile/platform/**`，共享侧只依赖接口。
3. 保留运行时平台覆盖（`?platform=mobile` / `localStorage`）语义，桌面与移动行为等价迁移。
4. 新增导出全部带 JSDoc，`check:doc-coverage` 不退化。

### 非目标

1. 不清零 `usePlatform.ts` 的两处定义（抽象层边界，见 §7.2）。
2. 不改 20 处 `useIsMobile()` 业务消费点、不改 3 处 `mobileOnlyAsyncComponent()` 消费点。
3. 不触碰 `isIOS()`、`hasTauriRuntime()` 等其他平台分支。
4. 不调整任何 UI 表现、路由结构、Matrix 服务层（遵守 R1，无平行实现）。
5. 不引入 admin / AI 相关引用（遵守 R2，移动端零残留）。

## 4. 方案选型

| 方案 | 做法 | ratchet | 运行时覆盖 | 主要问题 |
| :-- | :-- | :-- | :-- | :-- |
| A 构建期 alias 拆分 | 每处新增桌面/移动同名模块，`!isPC` 时 alias 到 `src/mobile/**` | 5 → 2 | **丢失** | 破坏 `?platform=mobile` 契约；与 §19.13 结论冲突 |
| **B 运行期注册表（推荐）** | 共享侧读注册表，`main.ts` 用现有 `isMobile()` 快照注册移动实现 | **5 → 3** | **保留** | 桌面产物会包含移动实现（体积小，见 §8） |
| C 机械清零 | 把 `isMobile()` 改名为 `getPlatformType() === 'mobile'` 等 | 5 → 0 | 保留 | 纯指标规避，无架构收益，本方案拒绝 |

方案 B 的核心：`main.ts` 中那 1 次 `isMobile()` 不再承担业务分支，而是**组合根（composition root）的平台快照**，与 `initializePlatform()` 同层；业务模块不再直接询问平台。

## 5. 详细设计（方案 B）

### 5.1 新增契约

`src/platform/contracts.ts`（纯类型，无平台判断）：

- `StorageLayout`：`downloadBaseDir`、`resolveDownloadBaseDirPath`、`cacheBaseDir`、`cacheBaseDirName`、`scopedBaseDirs`（从 `PathUtil` 原样上移）。
- `PlatformBoot`：`afterPlatformInitialize(): void`。
- `SessionEventStrategy`：
  - `handleLegacyVideoCall(payload, callHandler): void`；
  - `handleRemoteLoginExpired(context): Promise<void>`，`context` 含 `remoteIp`、`logout()`、`onLoggedOut()`。

### 5.2 新增注册表（实为三个独立模块）

原设计为单一 `src/platform/runtime.ts`，实施时因循环导入（`PathUtil` → `runtime` → 移动 `platformBoot` → `TauriInvokeHandler` → `PathUtil`）拆为三个互不依赖的注册表模块：

| 模块 | 注册器 | 读取器 | 默认值 |
| :--- | :--- | :--- | :--- |
| `src/platform/storageLayout.ts` | `registerStorageLayout(mobile: boolean)` | `getStorageLayout()` | 桌面实现（首次 `get` 时惰性创建） |
| `src/platform/platformBoot.ts` | `registerPlatformBoot(mobile: boolean)` | `getPlatformBoot()` | `desktopPlatformBoot` |
| `src/platform/sessionEventStrategy.ts` | `registerSessionEventStrategy(mobile: boolean)` | `getSessionEventStrategy()` | `desktopSessionEventStrategy` |

- 默认值全部为桌面实现（`src/platform/desktop/**`），因此 `PathUtil` 单测、浏览器环境、未注册路径行为不变。
- 注册器接收 `mobile: boolean`（而非 `isMobile()` 结果在模块内求值），重复调用幂等。
- 存储布局改为惰性工厂（`createDesktopStorageLayout()` / `createMobileStorageLayout()`）：避免模块加载期读取 `BaseDirectory` 导致部分对 `@tauri-apps/plugin-fs` 做局部 mock 的测试收集失败。
- 三个注册表**均不调用** `isMobile()`，平台判定只发生在 `main.ts` 组合根。

### 5.3 逐处下沉

#### 5.3.1 `PathUtil` 存储布局（`is_mobile_branch` 5 → 4）

- 共享侧：`resolveStorageLayout()` 改为 `getStorageLayout()`，删除本地 `if (isMobile())`；`PathUtil` 其余逻辑与导出签名不变。
- 桌面实现：`src/platform/desktop/storageLayout.ts`（Resource / AppCache / 三候选，原样迁移）。
- 移动实现：`src/mobile/platform/storageLayout.ts`（AppData 单候选）。
- 测试迁移：`PathUtil.test.ts` 删除 `PlatformConstants` mock，改为 `registerStorageLayout(false/true)` 驱动；`TempFileManager.test.ts` 同步去掉 `isMobileMock`。移动布局断言迁到 `src/platform/__tests__/runtime.test.ts`（桌面 AppCache/Resource/3 候选、移动 AppData/1 候选、切回桌面 3 条）。

#### 5.3.2 启动分支（`is_mobile_branch` 4 → 3）

- 共享侧：`main.ts` 删除 eruda 片段与 `setup()` `DOMContentLoaded` 分支，改为 `registerStorageLayout/registerPlatformBoot/registerSessionEventStrategy(isMobilePlatform)` 后调用 `getPlatformBoot().afterPlatformInitialize()`；`set_complete` 的 `invokeSilently` 迁入移动实现。
- 桌面实现：`src/platform/desktop/platformBoot.ts` 空实现。
- 移动实现：`src/mobile/platform/platformBoot.ts`：dev 下动态 `import('eruda')`；`readyState === 'loading'` 时监听 `DOMContentLoaded`，否则立即执行 `set_complete`。

#### 5.3.3 会话/来电策略（`is_mobile_branch` 3 → 3，仅迁移已有调用）

- 共享侧：`useWsEventHandler` 删除 `isMobilePlatform` 快照；`VideoCallRequest` 回调改调 `getSessionEventStrategy().handleLegacyVideoCall(...)`；`TOKEN_EXPIRED` 改调 `handleRemoteLoginExpired(...)`，原桌面/移动两段逻辑原样迁移。
- 桌面实现：`src/platform/desktop/sessionEventStrategy.ts`（调用 `callHandler.handleVideoCall`；主窗口聚焦 + `sendWindowPayload` 登录窗 + logout）。

## 7. 验收判据

### 7.1 行为等价

1. 桌面：`getDownloadBaseDir()/getCacheBaseDir()/scopedBaseDirs` 与迁移前一致（单测断言 `Resource` / `AppCache` / 3 候选）。
2. 移动：三处实现均返回 AppData 单候选；启动时仍调用 `set_complete(frontend)`；dev 下 eruda 仍初始化。
3. `?platform=mobile` 与 `localStorage` 覆盖仍生效：三个 `register*` 由 `isMobile()` 快照驱动，覆盖发生在注册前。
4. 旧 WS 来电：移动端不进入 legacy 链路；`TOKEN_EXPIRED` 两端提示、登出、跳转与迁移前一致。

### 7.2 不可下沉边界（明确记录）

- `usePlatform.ts:64` / `:72`：平台判定与异步组件选择器本体。清零需把 20 个业务消费点改为双端组件实现，属于 R2「移动端独立实现」范畴的独立工作，不在 P3 内。
- 因此 ratchet 终值为 **3**，而不是 0。

## 9. 回滚策略

- 按批次回滚：B1–B3 各自独立提交，回滚任一提交即回到上一 ratchet 值。
- 注册表默认值为桌面实现，B1 回滚不会影响桌面行为；`PathUtil.test.ts` 的裁剪与 B1 同提交，回滚一并恢复。
- 若 B3 出现 WS 事件回归，可仅回滚 B3（`useWsEventHandler` 恢复快照），保留 B1/B2。
- 基线收紧（B4）单独提交，回滚不影响代码。

## 11. 决策结论（已确认）

1. 采用**运行期注册表**作为本项统一机制（而非 alias 拆分）；实施时进一步拆为三个独立注册表模块以规避循环导入，语义不变。
2. ratchet 终值 **3**，`usePlatform.ts` 两处记录为不可下沉边界。
3. 接受桌面产物静态包含移动实现；移动实现中的 vant / router / eruda 全部使用动态 import，桌面侧不产生额外运行时代价。
