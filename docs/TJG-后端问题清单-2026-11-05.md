## BE-1 废弃的 `offset` 分页返回 `M_BAD_JSON`（✅ 已修复）

- **现象**：`GET /_matrix/vendor/v1/friends?offset=10` → `400 {"errcode":"M_BAD_JSON","error":"Legacy offset pagination is no longer supported; use from cursor"}`
- **问题**：`M_BAD_JSON` 的规范语义是「请求体不是合法 JSON」。这里既没有请求体、也不是 JSON 语法问题，而是**参数语义已废弃**。客户端按 errcode 分支（如 Tjg 的 `VALIDATION_ERRCODES`）会把文案选成「请求格式错误」，用户无法获知真实原因。
- **位置**：`synapse-web/src/routes/friend_room.rs:265-270`
  ```rust
  if params.offset.unwrap_or(0) > 0 && cursor.is_none() {
      return Err(ApiError::bad_request("Legacy offset pagination is no longer supported; use from cursor"));
  }
  if params.from.is_some() && cursor.is_none() && legacy_offset.is_none() {
      return Err(ApiError::bad_request("Invalid friend list pagination cursor"));
  }
  ```
- **建议**：两处都改用 `ApiError::invalid_param(...)` → `M_INVALID_PARAM`（同文件 `resolve_friend_list_limit` 已用这个码，属同接口内不一致）。
- **影响面**：所有还在传 `offset` 的旧客户端（含本仓 `SynapseFriendExtensionService` 的历史版本）。

## BE-2 401 使用非规范 errcode `M_UNAUTHORIZED`（✅ 已修复）

- **现象**：`POST /_matrix/client/v3/upload/token`（无 Authorization）→ `401 {"errcode":"M_UNAUTHORIZED","error":"Missing or invalid authorization header"}`
- **问题**：Matrix 规范里 401 只有 `M_UNKNOWN_TOKEN`（令牌无效/过期）与 `M_MISSING_TOKEN`（未提供）。`M_UNAUTHORIZED` 是自造码：
  - matrix-js-sdk / 第三方客户端只识别规范码，会把「需要重新登录」当成一般错误；
  - Tjg 的 `src/common/errors.ts`、`src/locales/errors/*.ts` 原本都没有该码（本次已在前端补兼容）。
- **位置**：`synapse-common/src/error.rs:283-288`（`ApiError::unauthorized`）、`:30-40`（`MatrixErrorCode::Unauthorized`）、`synapse-web/src/utils/auth.rs:30-43`（`bearer_token`）
- **建议**：按缺失/无效区分返回 `M_MISSING_TOKEN` / `M_UNKNOWN_TOKEN`；若要保留自造码做灰度，至少在响应里**同时**给出规范码（如 `errcode` 用规范码、另加 `hula_errcode` 字段）。

## BE-3 幂等键头不被识别（✅ 已修复，2026-11-05 16:00 复测通过）

- **现象**：同一 `Idempotency-Key: k-abc` 连发两次 → 两次都 200 且返回同一 `request_id:"82"`；同一 `X-Request-Id` 亦同。
- **问题**：`resolve_request_id()` 只读 `x-request-id`，把它当作**业务 request_id** 回传给客户端。前端按通用实践发的是 `Idempotency-Key`，该头被完全忽略。
  - 当前「没有重复创建」不是幂等键生效，而是 `send_friend_request` 的 pending 唯一性兜底（服务层对同一 (sender, receiver) 复用既有记录）。一旦业务改成「允许重复请求」、或换到没有唯一约束的端点（如建群/发消息扩展），重发就会产生重复副作用。
- **位置**：`synapse-web/src/utils/auth.rs:10-17`；消费点 `friend_room.rs:392-397`
- **建议**：
  ```rust
  pub(crate) fn resolve_idempotency_key(headers: &HeaderMap) -> Option<String> {
      for name in ["idempotency-key", "x-request-id"] {
          if let Some(v) = headers.get(name).and_then(|v| v.to_str().ok()).map(str::trim).filter(|v| !v.is_empty()) {
              return Some(v.to_string());
          }
      }
      None
  }
  ```
  并让写操作以 `(user_id, key)` 做去重表（短 TTL），与「请求追踪 ID」解耦。

## BE-4 CORS 预检不放行 `idempotency-key`（✅ 已修复）

- **现象**：`OPTIONS /_matrix/vendor/v1/friends/request`，请求头 `Access-Control-Request-Headers: authorization,content-type,idempotency-key` → 响应
  `access-control-allow-headers: authorization, content-type`（`idempotency-key` 被过滤掉）。
- **问题**：浏览器会按 allow-headers 的白名单剥离未声明头 ⇒ Web 端（非 Tauri）即便后端支持幂等键也收不到。
- **位置**：`synapse-web/src/middleware/cors.rs:216-228`（`allowed_header_set`）
- **建议**：`allowed_header_set` 增加 `"idempotency-key"`，并同步非预检分支的 `Access-Control-Allow-Headers` 常量（`:276-280`）。

## BE-5 `upload/token` 契约与客户端模型错位（✅ 已修复）

- **现象**（带鉴权实测）：
  ```json
  {"content_type":"image/png","filename":"a.png","max_file_size":52428800,
   "storage_type":"matrix","upload_token":"upload_@probe…",
   "upload_url":"/_matrix/media/v3/upload"}
  ```
- **问题**：
  1. 没有 `download_url`，也没有任何「上传后可访问地址」的推导约定；
  2. `upload_url` 是 **POST** 端点（`POST /_matrix/media/v3/upload` 成功返回 `{content_uri: mxc://…}`），而该端点的命名（`upload_token`/`upload_url`）在业界惯例里表示「预签名 PUT 凭证」，客户端很容易按 PUT 使用；
  3. 请求体里客户端传的 `scene` 被静默丢弃（`CreateUploadTokenBody` 无该字段且未 `deny_unknown_fields`）——参数被吞掉却不报错。
- **位置**：`synapse-web/src/routes/media/upload.rs:383-415`
- **建议**：二选一
  - **收敛**：把该端点标注为 deprecated，客户端直接走媒体上传；或
  - **补全**：响应增加 `upload_method: "POST"` 与 `download_url_prefix`（`/_matrix/client/v1/media/download/{server}/{mediaId}`），并对未知字段加 `deny_unknown_fields` 让脏参数显式失败。

## BE-6 `upload_token` 是死字段（✅ 已修复）

- **现象**：`upload_token` 在 `create_upload_token` 里拼出来后，全仓**没有任何代码校验它**（`grep upload_token` 仅 3 处：定义、赋值、路由）。
- **问题**：给客户端一个看似可用的凭证，实际谁都不要它；排查时极易误判「上传鉴权失败是 token 问题」。
- **建议**：删除该字段，或实现它（作为 `POST /media/v3/upload` 的一次性票据）。

## BE-7 `M_UNKNOWN` 同码多义（✅ 已登记 + 守卫，协议层无法消除）

- **现象**（源码）：`M_UNKNOWN` 同时用于 `400`（格式合法但语义无效）、`409`（状态冲突）、`500`（内部错误）、`501`（未实现）、`503`（服务不可用）。
- **问题**：客户端无法用 errcode 区分「我参数不对」与「服务端炸了」，只能靠 HTTP 状态码；而部分网关会把 5xx 改写成固定页，信息进一步丢失。
- **位置**：`synapse-common/src/error.rs`（`conflict` / `not_implemented` / `service_unavailable` / `internal_*` 等构造器，注释里已自认「Matrix 无对应码」）
- **建议**：这类分歧不可避免（规范确实没给码），但应**显式登记**到 `docs/synapse-rust/ROUTE_CONTRACT.md` 的错误矩阵，并给客户端一份 `(http, errcode) → 语义` 的机器可读表，避免各端各猜。

## BE-8 `Expose-Headers` 名称与实际响应头不一致（✅ 已修复 + 守卫）

- **现象**：429/限流响应实际写 `x-ratelimit-retry-after-ms`，而预检的 `access-control-expose-headers` 声明的是 `X-Ratelimit-Retry-After`。
- **问题**：浏览器端 `headers.get('x-ratelimit-retry-after-ms')` 返回 null（未被 expose），只能退回 body 的 `retry_after_ms`。
- **位置**：`synapse-web/src/middleware/cors.rs:249-254` vs `synapse-common/src/error.rs:1076-1081`
- **建议**：两处对齐（推荐统一暴露 `X-RateLimit-Retry-After-Ms`）。

## BE-9 `410 Gone` 的响应体形状特殊（⚠️ 实测形状正常）

- **现象**（源码）：`IntoResponse` 对 `ApiErrorKind::Gone` 特判——先把 `message` 当 JSON 解析，解析成功就直接返回该 JSON（丢掉 `errcode`/`error` 外壳）；解析失败才回落标准体。实测当前唯一调用点传纯文本，返回仍是标准体，故暂未暴露。
- **问题**：同一错误的响应体形状取决于 `message` 的**内容格式**，客户端无法稳定解析。
- **位置**：`synapse-common/src/error.rs:1021-1033`
- **建议**：删除特判，统一走标准 `{errcode, error}`；确需返回结构化载荷时，用 `details` 子字段承载。

## BE-10 `/friends/dm/{uid}` 缺 `exists`，`room_id` 为 `null`（✅ 已修复）

- **现象**：`GET /_matrix/vendor/v1/friends/dm/{uid}`（无既有会话）→ `{"room_id":null,"user_id":"@…:matrix.test"}`
- **问题**：字段名暗示「房间 ID 必为字符串」，实际是 nullable；且没有 `exists` 布尔（客户端需自行派生）。前端类型曾声明 `room_id: string` + `exists: boolean`，属于契约漂移。
- **位置**：`synapse-web/src/routes/friend_room.rs:748-760`
- **建议**：响应补 `"exists": room_id.is_some()`（一行），并在 `docs/sdk/friends.md` 标注 `room_id` 可为 null。前端已改为派生，属于双保险。

## BE-12 事件 `content` 被纳入 btree INCLUDE 列，内容超 ~2.7KB 的事件无法写入（✅ 已修复 2026-11-06 14:51，commit `c8180e544`）

**这是本轮最严重的后端缺陷：它不是「测不到」，而是「测到就必挂」。**

### 现象（两条互相独立的触发路径，同一根因）

| 操作 | 结果 |
|---|---|
| 账号已有 33 个好友，接受第 34 个好友请求 | `500 {"errcode":"M_UNKNOWN","error":"An internal error occurred"}` |
| 向房间发送 2600 / 3000 / 5000 字节**不可压缩**文本消息 | 同上 500 |
| 发送 1000 / 2000 字节不可压缩文本 | 200 |

### 服务端日志（决定性证据）

```
ERROR ... accept_friend_request{user_id="@pgmain…", requester_id="@pgf…"}:
  synapse_common::error: synapse-common/src/error.rs:574:
  internal error context=Failed to create event with graph metadata
  error=error returned from database: index row size 2728 exceeds btree version 4
        maximum 2704 for index "idx_events_sync_covering"
```

### 根因

```sql
CREATE INDEX idx_events_sync_covering ON public.events
  USING btree (room_id, stream_ordering DESC)
  INCLUDE (event_id, sender, event_type, content, origin_server_ts);
```

`content` 被放进了 **INCLUDE 列**（即索引里存了整份 content）。Postgres btree v4 的**单个索引元组上限 2704 字节**（压缩后），一旦 `pg_column_size(content)` 超出，INSERT 直接报 `index row size … exceeds`，事务失败。

实测数据（`m.friends.list` 是用户好友列表的**整份快照**事件，每加一个好友 content +264 字节）：

| 好友数 | `length(content::text)` | `pg_column_size(content)` | 结果 |
|---|---|---|---|
| 33 | 8730 | **2510** | ✅ 写入成功（贴着 2704 的红线） |
| 34 | ≈8994 | ≈2670+ | ❌ `index row size 2728 exceeds … 2704` |

> 逻辑字符数（8730）远大于上限却仍然成功 —— 因为 `content` 是重复度很高的 JSON，**pglz 压缩后**才 2510 字节。
> 判定阈值是**压缩后**大小，这也解释了为什么「写很长的重复字符消息」能过，而「短的随机文本」会挂。

### 影响面（按已确认 / 待确认分开）

**已实测确认**：

1. **好友数 ≥ 34 后无法再加好友**（accept 接口 500），且前端只会弹「未知错误」；
2. **消息正文约 2.5–2.6KB 是不可逾越的上限**（不可压缩内容），且返回的是 `500 M_UNKNOWN` 而不是 `413 M_TOO_LARGE`；
3. 「好友数 > 50 的真实翻页」因此**在本后端上无法构造**（33 个好友就到顶了）—— 这不是测试数据不足，而是后端写不进去。

**高度可疑（同一根因推断，未实测）**：

4. **E2EE 长消息几乎必挂**：`m.room.encrypted` 的 `ciphertext` 是 base64（近不可压缩），约 1.9KB 明文即可越过 2704B 索引元组上限；
5. 长 `m.room.name` / `m.room.topic` / 大 `m.room.power_levels` / 大 `m.room.member`（含头像 URL+displayname 批量）等状态事件；
6. 任何服务端写入的「快照型」状态事件（同 `m.friends.list` 模式的其它 custom event）。

### 复现（可重复，无需前端）

```bash
# 路径 A：好友数量
#   循环 N 次：peer 发请求 → 主号 accept，第 34 次必 500
# 路径 B：消息体积
curl -X PUT "$BASE/_matrix/client/v3/rooms/$RID/send/m.room.message/$TS" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "$(python3 -c 'import json,random,string;print(json.dumps({"msgtype":"m.text","body":"".join(random.choices(string.ascii_letters+string.digits,k=2600))}))')"
# 期望 200，实际 500 M_UNKNOWN
```

### 修复建议（按优先级）

1. **把 `content` 从 INCLUDE 列里去掉**（最小改动、直接解阻断）：`(room_id, stream_ordering DESC)` 普通索引，同步查询回表取 content。`event_id/sender/event_type/origin_server_ts` 都是短列，留在 INCLUDE 无害。
2. 若确实需要「索引内取 content」做 covering scan，改用 `INCLUDE (content_hash)` + 回表，或对 content 单独建 GIN/表达式索引。
3. **错误语义**：插入路径捕获该 sqlx 错误并映射为 `413 M_TOO_LARGE`（与 BE-7「M_UNKNOWN 同码多义」同族，否则客户端无法区分「内容太长」和「服务端故障」，只能提示未知错误）。
4. **好友列表不应以「整份快照」写事件**：`m.friends.list` 每变一次就把全量好友写一条事件，既放大存储，也把事件体量绑到好友数上。建议改为「游标 + 增量」或只在 state 里存 `friends_version`。

### 前端侧的对应现象（已确认）

- 好友 accept 失败在 UI 上只表现为通用错误提示（`M_UNKNOWN` → `error.matrix.unknown`），无「已达上限」类文案；
- 消息发送失败同样落到通用错误，用户重试也无意义。
  ⇒ 在后端修复前，前端无法通过文案弥补，因为**根因是写入失败**，不是限流或校验。
