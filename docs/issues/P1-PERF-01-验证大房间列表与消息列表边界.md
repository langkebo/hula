# [P1][性能] 验证大房间列表与消息列表边界

## 背景

`hula` 作为即时通讯工具，在处理 5000+ 成员的大房间或 10000+ 条历史消息时，列表渲染压力巨大。Matrix 协议的增量更新可能导致频繁的重绘。需要明确当前渲染引擎在极端场景下的崩溃点或性能瓶颈。

## 现状

- 当前行为：使用虚拟滚动，但在快速滚动时可能出现空白或帧率（FPS）骤降。
- 已知风险：大房间进人或批量同步消息时，UI 可能出现数秒的冻结。
- 影响范围：核心聊天视图。

## 目标

- 目标 1：模拟 1k、5k、10k 消息量级的渲染表现。
- 目标 2：量化大房间快速滚动时的平均 FPS。
- 目标 3：定位列表 Item 渲染中的重计算逻辑（如头像、状态图标、富文本预览）。

## 范围

### 包含

- 房间列表（Room List）更新性能。
- 消息时间线（Timeline）虚拟滚动性能。
- 侧边栏成员列表渲染。

### 不包含

- 网络请求层面的优化。
- E2E 加密解密的性能（已有专项）。

## 交付物

- 文档：极端场景性能压力测试报告（存入 `docs/performance/`）。
- 附件：DevTools Performance 录屏与 longtask 记录。
- 代码：针对瓶颈点的 Demo 级修复方案（如缓存组件）。

## 执行步骤

1. 使用脚本生成包含 5000 条消息的本地 Matrix 模拟数据。
2. 启动 Chrome Performance 面板，开启 CPU 4x 减速。
3. 执行快速滚动操作，记录 FPS。
4. 使用 `WebVitalsObserver.ts` 捕获长任务。

## 验收标准

- [ ] 输出清晰的性能边界报告（例如：超过 2000 条消息时 FPS 降至 30 以下）。
- [ ] 识别出列表 Item 中最耗时的子组件或方法。
- [ ] 验证虚拟滚动窗口大小（Buffer Size）是否最优。

## 风险与依赖

- 风险：模拟数据可能与真实 Matrix 同步数据格式有差异。
- 依赖：`P0-PERF-01` 建立首轮性能基线。

## 灰度与回滚

- 灰度方式：先在实验室环境（Lab）验证压力模型。
- 回滚方式：不适用（属于调研性任务）。
