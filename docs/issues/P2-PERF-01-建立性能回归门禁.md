# [P2][性能] 建立性能回归门禁

## 背景

在完成首轮性能基线（`P0-PERF-01`）后，需要将这些静态的基线数据转化为动态的监控规则。通过在 CI/CD 流程中引入性能门禁，可以及时发现代码变更导致的性能退化（Regression），防止性能随迭代缓慢恶化。

## 现状

- 当前行为：无自动化性能回归检测。
- 已知风险：新功能的合入可能在不经意间增加主线程阻塞或降低帧率，直到用户反馈才被发现。
- 影响范围：CI 流水线、代码质量把控。

## 目标

- 目标 1：定义核心指标（FCP, LCP, INP, TBT）的报警与阻塞阈值。
- 目标 2：集成 Lighthouse CI 或自定义性能测试脚本至 CI 流水线。
- 目标 3：实现性能变动在 PR 评论中的自动反馈。

## 范围

### 包含

- Web 端的 Lighthouse CI 配置。
- 关键交互（如进入房间）的自动化脚本性能采样。
- 门禁触发规则（如 LCP 退化超过 20% 自动阻塞 PR）。

### 不包含

- 生产环境的实时性能监控（APM）。
- 移动端原生容器的自动化性能压测。

## 交付物

- 代码：`.lighthouserc.js` 配置文件。
- 代码：CI 流水线中的性能检测 Job 定义。
- 文档：性能门禁操作与阈值说明（存入 `performance-baseline.md`）。

## 执行步骤

1. 基于 `P0-PERF-01` 的数据设定首批阈值（建议在基线基础上留 10% 冗余）。
2. 在 GitHub Actions / GitLab CI 中添加运行性能测试的步骤。
3. 配置性能测试报告的存储与展示。
4. 运行 5-10 次 CI 验证门禁的稳定性，减少误报。

## 验收标准

- [ ] CI 流水线能成功运行性能测试并输出报告。
- [ ] 当人为引入长耗时逻辑时，CI 能够正确触发失败报警。
- [ ] 性能门禁结果能自动同步至代码评审（PR）界面。

## 风险与依赖

- 风险：CI 环境的硬件性能波动可能导致测试结果不稳定（Flaky）。
- 依赖：`P0-PERF-01` 建立首轮性能基线。

## 灰度与回滚

- 灰度方式：先设置为“仅报警不阻塞”，观察一周后再开启强阻塞模式。
- 回滚方式：在 CI 配置中关闭性能检测 Job。
