# [P1][安全] 扩展日志脱敏规则

## 背景

当前的 `Logger` 实现虽然有基本的过滤，但在调试模式下，敏感数据（如 `refresh_token`、OIDC 状态、二维码原始内容、恢复密钥等）仍有进入本地文件或控制台的风险，不符合生产安全合规要求。

## 现状

- 当前行为：部分网络请求体和状态对象被全量打印。
- 已知风险：本地日志文件被窃取后，攻击者可直接获取登录凭证。
- 影响范围：全端日志输出。

## 目标

- 目标 1：扩展日志脱敏白名单/黑名单模式。
- 目标 2：确保涉及 Token 和密钥的字段自动替换为 `[REDACTED]`。
- 目标 3：建立日志脱敏的单元测试，防止新字段漏脱敏。

## 范围

### 包含

- `matrix-js-sdk` 内部日志拦截。
- Rust 侧插件日志脱敏。
- 前端全局 `error` 捕获中的上下文脱敏。

### 不包含

- 用户已手动截图分享的日志内容。

## 交付物

- 代码：增强型 `LogRedactor` 模块。
- 代码：日志脱敏单元测试集。
- 文档：日志合规性说明（存入 `security-baseline.md`）。

## 执行步骤

1. 梳理当前所有包含敏感信息的 JSON 字段名。
2. 实现一个递归脱敏函数，支持深度嵌套对象。
3. 将该函数挂载至 `Logger` 的输出流。
4. 抽样检查 `AppData` 目录下的日志文件内容。

## 验收标准

- [ ] 抽样 50 条包含 Auth 逻辑的日志，确认无明文 Token。
- [ ] 单元测试覆盖率 100%（针对已知敏感字段名）。
- [ ] 开启调试模式时，控制台不输出敏感原始数据。

## 风险与依赖

- 风险：过度脱敏可能导致排查问题时信息不足。
- 依赖：`P0-SEC-03` 明确 token 存储加密方案。

## 灰度与回滚

- 灰度方式：先在内测版本（Beta）开启严格脱敏。
- 回滚方式：降级日志级别或回滚脱敏库版本。
