# [P2][安全] 建立 capability / CSP ADR 流程

## 背景

Tauri 的 `capability` 配置和 Web 端的 `CSP` 是 `hula` 安全防御的核心。这些配置的任何调整都涉及巨大的安全风险，因此不能仅作为普通代码变更处理，必须通过“架构决策记录（ADR）”流程进行审慎评估和持久化归档。

## 现状

- 当前行为：安全配置调整随 PR 直接合入，缺乏深度背景记录。
- 已知风险：数月后可能没人记得为什么当初放开了某个敏感权限（如 `fs:allow-app-config`）。
- 影响范围：长期安全治理。

## 目标

- 目标 1：规范化安全配置的变更流程。
- 目标 2：确保每次权限放开都有对应的业务场景、风险评估和替代方案说明。
- 目标 3：建立可追溯的安全决策库。

## 范围

### 包含

- `src-tauri/capabilities/` 下配置的变更。
- `tauri.conf.json` 中 `csp` 字段的变更。
- 关键安全逻辑（如加密存储实现）的变更。

### 不包含

- 普通业务逻辑的变更。

## 交付物

- 文档：安全决策记录流程说明。
- 模板：针对安全变更定制的 `ADR-template.md`。
- 示例：一份真实的“放开 HTTP Scope”安全决策记录。

## 执行步骤

1. 确立“安全变更 = 必须有 ADR”的团队共识。
2. 在 `docs/adr/` 下创建安全专项目录。
3. 将该要求写入 `security-baseline.md`。

## 验收标准

- [ ] 所有涉及 `capability` 放开的提交都关联了 ADR 编号。
- [ ] ADR 文档清晰记录了“如果不放开此权限，业务将如何受限”。
- [ ] 每年进行一次 ADR 回头看，清理不再需要的权限。

## 风险与依赖

- 风险：决策流程过长可能影响紧急业务的上线进度。
- 依赖：`P0-SEC-01`, `P0-SEC-02`。

## 灰度与回滚

- 灰度方式：不适用。
- 回滚方式：撤销不符合流程的安全配置变更。
