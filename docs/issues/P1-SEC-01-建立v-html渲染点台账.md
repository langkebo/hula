# [P1][安全] 建立 v-html 渲染点台账

## 背景

`hula` 作为一个聊天应用，需要渲染大量来自不可信来源（Matrix 协议）的富文本。虽然项目中使用了 `DOMPurify`，但渲染点（`v-html`）分布零散，缺乏统一的清洗策略审计和输入来源追溯，存在 XSS 风险。

## 现状

- 当前行为：散落在各组件中的 `v-html` 渲染。
- 已知风险：若某个渲染点遗漏了清洗，攻击者可通过恶意消息执行 JS。
- 影响范围：所有涉及富文本展示的组件。

## 目标

- 目标 1：全局普查所有 `v-html` 使用点。
- 目标 2：为每个点建立“数据来源 -> 清洗方式 -> 风险等级”的台账。
- 目标 3：将零散的清洗逻辑收拢至全局指令或统一组件。

## 范围

### 包含

- 消息时间线组件。
- 机器人（Bot）回复渲染。
- 用户个人签名与房间描述。
- 搜索结果高亮显示。

### 不包含

- 非 HTML 渲染（如纯文本渲染）。

## 交付物

- 文档：`hula_v-html_audit_list.csv` 或 Markdown 表格。
- 代码：统一的 `v-safe-html` 指令实现。
- 代码：CI 静态扫描规则（禁止直接使用 `v-html`，需审批豁免）。

## 执行步骤

1. 全局搜索 `v-html` 关键词。
2. 逐一检查 `ThreadView.vue`、`SpotlightDialog.vue` 等核心组件。
3. 确认是否所有输入都经过了 `sanitize` 处理。
4. 记录是否有直接从服务端（未经 SDK 清理）获取并渲染的原始 HTML。

## 验收标准

- [ ] 完成全量台账，无遗漏点。
- [ ] 核心组件全部切换至统一的安全渲染方式。
- [ ] 新增 `v-html` 必须通过 Security Review。

## 风险与依赖

- 风险：清洗过严可能导致部分复杂的 Markdown 样式失效。
- 依赖：`P0-SEC-01` 补齐生产 CSP 基线。

## 灰度与回滚

- 灰度方式：先在 Dev 环境启用严格清洗模式。
- 回滚方式：恢复 `v-html` 原始用法，调低清洗强度。
