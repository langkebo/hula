## 三、严重问题（P0，需立即修复）

### S-1 本地任意文件读取 + 任意目标地址上传（SSRF / 数据外泄）

- **位置**：[upload_command.rs](file:///Users/ljf/Desktop/hu_ts/Tjg/src-tauri/src/command/upload_command.rs#L18-L38)、`upload_put`（同文件 #L176 起）
- **问题描述**：`upload_file_put` 接收前端传入的 `path` 与 `url`。`resolve_upload_path` 在 `path` 为绝对路径时**直接返回**（#L36-38），未做任何目录白名单校验；同文件里已有 `path_is_within`（#L119-127）用 `canonicalize` 做越界防护，但**只在拖拽复制命令中使用**，`upload_file_put` 未调用。随后 `upload_put` 把该文件完整流式 POST/PUT 到调用方任意指定的 `url`，且 `headers` 也由调用方完全控制。
- **影响范围**：任何能触达该 IPC 的前端代码（含被 XSS 注入的渲染内容、被污染的 markdown、第三方 widget）都可读取 `~/.ssh/id_rsa`、钥匙串导出文件、`$APPDATA` 下的会话/密钥库，并外发到攻击者服务器。等同于"本地文件读取 + 出网"。
- **优化建议**：
  1. `upload_file_put` 复用 `path_is_within`，把可读根限制在 `$APPDATA/userData/**` 与 `$APPCACHE/**`；
  2. `url` 做协议与主机白名单（仅允许当前 homeserver 域，或仅允许 `matrix:` 媒体上传端点），拒绝内网/回环/元数据地址（169.254.169.254、127.0.0.0/8、10/8、172.16/12、192.168/16）；
  3. `headers` 黑白名单，禁止 `Host`、`Cookie`、`Authorization` 之外的自定义透传；
  4. 更好的做法：改为"传 mxc 目标/房间 ID，由 Rust 侧自行拼接 URL"。

### S-2 系统唤醒监听器无法注销，导致重连风暴

- **位置**：[matrixClientPlatform.ts](file:///Users/ljf/Desktop/hu_ts/Tjg/src/services/matrix/matrixClientPlatform.ts#L22)、[MatrixClientLifecycle.ts](file:///Users/ljf/Desktop/hu_ts/Tjg/src/services/matrix/MatrixClientLifecycle.ts#L160-L171)
- **问题描述**：`setupSystemResumeListener(onResume: () => void): void` 只注册不返回清理句柄；`MatrixClientLifecycle` 的注释已明确记录"`setupSystemResumeListener` 返回 void（不提供取消订阅 API）"，但仍在每次启动流程中调用。登出后重新登录、断线重连、多客户端实例切换都会叠加一层监听器。
- **影响范围**：运行时间越长，系统唤醒一次会触发 N 次 `forceReconnect()`；叠加的 `forceReconnect` 本身又没有退避（见 H-8），会瞬间打出多条并发登录/同步请求，触发服务端限流，并造成 UI 状态抖动。
- **优化建议**：改为返回 `() => void`（或 `Promise<UnlistenFn>`），`MatrixClientLifecycle` 持有并在 `stop()` / 实例切换时调用；同时加一次性幂等保护（重复 setup 先 teardown）。

### S-3 界面设计系统守护口径分裂（硬编码颜色约束存在大块盲区）

- **位置**：[check-ratchet.mjs](file:///Users/ljf/Desktop/hu_ts/Tjg/scripts/check-ratchet.mjs#L169)（唯一全仓守卫）、[no-hardcoded-colors.test.ts](file:///Users/ljf/Desktop/hu_ts/Tjg/tests/lint/no-hardcoded-colors.test.ts)、`src/components/workbench/__tests__/hardcoded-color-lint.test.ts`（审计后被删除）；旁证：[simple.scss](file:///Users/ljf/Desktop/hu_ts/Tjg/src/styles/scss/theme/simple.scss)、[code-block.scss](file:///Users/ljf/Desktop/hu_ts/Tjg/src/styles/scss/chatBot/code-block.scss)
- **问题描述**：仓库同时存在三套硬编码色守卫，彼此口径不一致，且没有一套做到"全仓 + 全格式 + 全写法"：
  1. `check-ratchet.mjs` 的 `hardcoded_color`：唯一遍历整个 `src` 的守卫，但未配置 `extensions`，退化为 `SOURCE_EXTENSIONS`（`.ts/.mts/.cts/.tsx/.vue`），**`.scss` / `.css` 从未被扫描**；正则 `#3|#6|#8 hex + rgba?(` 漏掉 4 位 hex 与 `hsl()`；基线为 0，但只统计总量，无法定位具体新增文件。
  2. `tests/lint/no-hardcoded-colors.test.ts`：只覆盖 `src/mobile`、`src/components` 的 `.vue` 与 `src/styles/scss` 的 `.scss`，正则仅 3/6 位 hex，`rgba()` / `hsl()` / `src/views` / `src/layout` / `src/styles/css` 全部不在范围内。
  3. `src/components/workbench/__tests__/hardcoded-color-lint.test.ts`：固定遍历手写的 `keyFiles` 数组（10 个文件），正则仅 `#[0-9a-fA-F]{6}`。

  三者叠加后的实际盲区：`src/styles/scss` 中的 `rgba(...)`（`simple.scss` 11 处、`code-block.scss` 13 处）无人拦截；全仓 `hsl()` 与 4 位 hex 无人拦截；`src/views`、`src/layout`、`src/styles/css` 的 `.vue`/`.css` 仅被 ratchet 的窄正则覆盖。
- **影响范围**：违反项目硬约束"禁止硬编码颜色，只用 `--tjg-*`"，暗色主题与后续换肤会出现局部不跟随；三套门禁并存还会给出"已通过"的错误安全感。
- **优化建议**：收敛为单一权威守卫——把 `check-ratchet.mjs` 的 `hardcoded_color` 扩展为覆盖 `.ts/.tsx/.vue/.scss/.css`、正则补齐 4/8 位 hex 与 `rgb()/hsl()`、按路径排除 token 源（`design-tokens.css`）与渐变资源（`login-bg.scss`），存量债务进 ratchet 基线逐步收紧；同时删除与之口径冲突的弱测试，避免"改一处漏一处"。
- **修复状态（2026-10-31）**：已按上述建议落地。`hardcoded_color` 扩展至 `.ts/.tsx/.vue/.scss/.css`，正则含 3/4/6/8 位 hex 与 `rgb()/rgba()/hsl()/hsla()`，基线登记为 24（`simple.scss` 11 + `code-block.scss` 13），写入 `color: #fff` 的新文件实测被拦下；弱测试 `hardcoded-color-lint.test.ts` 已删除，`no-hardcoded-colors.test.ts` 作为更严格的子集守卫保留。
