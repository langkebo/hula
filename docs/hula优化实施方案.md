## 1. 文档目标

本文档基于 `https://github.com/element-hq/element-web` 的源码组织方式、架构分层、性能治理和功能落地经验，结合 `hula` 当前的真实技术栈与既有审计结论，给出一份可分阶段执行、可量化验收、可灰度发布、可快速回滚的优化实施方案。

本文档不重复否定 `hula` 已完成的工作，而是在以下事实上继续推进：

- `hula` 已经使用 `Vue 3 + TypeScript + Vite + Pinia + Tauri 2.x`
- 项目已有较高测试覆盖、基础性能监控、较完整文档和多条 CI 工作流
- 现阶段的主要问题不是“从零建设”，而是“体系分散、标准不统一、部分能力只做到可用未做到生产级”
- `element-web` 的最佳实践可以借鉴，但必须根据 `hula` 的 `Vue/Tauri/多端` 背景做适配

## 2. 基线摘要

### 2.1 当前项目状态

结合现有文档和代码审计，`hula` 具备以下基础：

- 前端框架：`Vue 3.5.x` + Composition API
- 状态管理：`Pinia` + `pinia-plugin-persistedstate`
- UI 技术栈：桌面端 `Naive UI`，移动端 `Vant`
- 构建体系：`Vite 7`，桌面容器为 `Tauri 2.x`
- 测试体系：`Vitest` + `Playwright` + Storybook 基础能力
- Matrix 能力：消息、房间、媒体、加密、Sliding Sync、VoIP、管理端接口等均已接入
- 文档资产：已有架构、性能、安全、测试、优化路线等多份文档

### 2.2 已知优势

- 代码质量整体较好，已有大规模测试资产
- Matrix 服务层拆分较完整，域边界已优于很多同类项目
- 已接入 `WebVitalsObserver`、`PerformanceReporter` 等性能指标采集能力
- 已有多端架构雏形，桌面/移动端共用核心业务层

### 2.3 已知问题

- 前端渲染路径仍有重型模块在首屏或高频交互路径上被过早加载
- 状态管理虽已分域，但仍存在跨域耦合、持久化边界偏宽、异步流程分散的问题
- 组件体系存在“双端双组件库并行”带来的主题、断点、交互一致性成本
- 构建链已是 `Vite`，但缺少更严格的 bundle 预算、依赖预构建策略和产物审计
- 测试覆盖率虽高，但桌面容器级、视觉回归、性能基准、故障注入仍不完整
- 安全能力具备基础设施，但缺少更细颗粒度的策略收口和自动化门禁
- 服务发现当前是 Matrix endpoint discovery，不是完整服务治理体系

## 3. 总体优化目标

### 3.1 业务目标

- 缩短冷启动时间，提升大房间和重交互页面的流畅度
- 提高设置、登录、消息、媒体、VoIP 等关键路径的一致性与恢复能力
- 降低前端和 Tauri 两端的技术债，减少隐式耦合
- 建立覆盖性能、安全、质量、文档的持续治理闭环

### 3.2 技术目标

- 首屏关键 JS gzip 体积降低 25% 以上
- 主线程长任务数量降低 40% 以上
- 关键交互页面 P95 渲染耗时控制在 200ms 以内
- 单元测试覆盖率门禁稳定保持在 85% 以上，核心域目标保持 90%+
- E2E 覆盖登录、消息、上传下载、加密、通知、VoIP 关键闭环
- 安全扫描、依赖审计、bundle 预算、性能基线全部纳入 CI

### 3.3 实施原则

- 先测量，后优化
- 先统一标准，再局部提速
- 先做低风险高收益，再做架构级重构
- 所有变更必须具备灰度策略、回滚方案和验收标准

## 6. 前端渲染性能优化策略

### 6.1 参考 `element-web` 的经验

`element-web` 的成熟经验可以概括为：

- 路由和功能边界明确，避免把所有能力塞进首屏
- 对重型能力进行延迟加载
- 使用缓存、去重和局部刷新降低重复渲染
- 对列表与时间线类场景重点优化滚动和分页
- 将计算密集逻辑从 UI 主线程迁移出去

### 6.2 `hula` 的执行策略

#### 6.2.1 虚拟滚动

目标：

- 房间列表、消息列表、搜索结果、成员列表全面引入统一虚拟滚动策略
- 大房间历史消息在 1 万条量级下保持可交互

措施：

- 统一封装 `VirtualListAdapter`，屏蔽桌面/移动实现差异
- 消息时间线采用“窗口化渲染 + 顶部/底部占位 + anchor 恢复”
- 对图片、代码块、引用消息等高度不稳定节点做延迟测量
- 结合 `IntersectionObserver` 控制图片与附件预加载

验收：

- 5k+ 消息房间，滚动 FPS > 55
- 滚动中内存峰值不再线性增长

#### 6.2.2 懒加载

目标：

- `mermaid`、`three`、`@vue-office/*`、高级媒体预览、AI 插件全部退出首屏主包

措施：

- 路由级动态导入
- 能力级动态导入
- 将加密设置、视频预览、文件预览、管理后台、AI 模块延迟到进入页面时再加载
- 图片/音视频预览组件采用按需注册

验收：

- 主包体积下降 20%-30%
- 非核心功能首次进入可接受的懒加载时间 < 1.5s

#### 6.2.3 代码分割

措施：

- 拆分 `vite.config.base.ts`、`vite.config.desktop.ts`、`vite.config.mobile.ts`
- 手工 chunk 以“平台 / 核心 Matrix / UI 库 / 富媒体 / AI / 管理后台”维度组织
- 降低 `chunkSizeWarningLimit` 到 `500KB`
- 将 Storybook、测试、脚本环境的构建依赖与生产产物隔离

#### 6.2.4 Tree-Shaking

措施：

- 清理空壳 alias 和历史兼容导出
- 限制大模块的 barrel re-export
- 按函数路径引入工具库
- 梳理 `matrix-js-sdk` 的导入边界，避免把非使用能力带入首屏

#### 6.2.5 缓存策略

措施：

- 引入多层缓存：内存 LRU、IndexedDB、磁盘缓存、Tauri 侧文件缓存
- 媒体资源缓存加入 hash / etag / 过期策略
- 列表页、消息页、头像、缩略图采用分层命中策略
- AI/地图/附件类请求加入请求去重与短期缓存

验收：

- 重复打开同一房间时图片和历史请求下降 40%+

#### 6.2.6 WebWorker 使用

适用场景：

- Matrix 事件预处理
- Markdown / Mermaid / 富文本解析
- 图片压缩、语音波形、附件加解密
- 大体量搜索结果聚合

措施：

- 建立统一 `worker task registry`
- 每类 worker 定义输入输出协议和超时机制
- 为 worker 引入取消、优先级和错误回传

#### 6.2.7 SSR/CSR 混合方案

结论：

- 主聊天应用不建议直接引入完整 SSR
- 可对以下场景试点“预渲染 / islands / hybrid CSR”：
  - 官网式静态页
  - 公共邀请页
  - 登录前协议页
  - Storybook/组件文档页

建议：

- 核心业务维持 CSR
- 非核心公开页面采用 SSG/预渲染
- 如果后续 Web 独立部署增强，再评估 Nuxt/Vite SSG 路径

## 7. 状态管理重构计划

### 7.1 选型结论

用户给出的候选包括 `Redux / Zustand / Recoil`，但 `hula` 当前是 `Vue 3` 项目，因此不建议迁移到 React 生态状态库。

最终建议：

- 主状态管理继续使用 `Pinia`
- 异步流程采用“服务层 + composable + store action”三层分离
- 局部临时状态优先使用 composable，而不是滥用全局 store

选型对比：

| 方案 | 是否推荐 | 原因 |
|---|---|---|
| Pinia | 强烈推荐 | Vue 生态最佳实践，现有项目已深度使用 |
| Redux | 不推荐 | 与 Vue 生态不匹配，迁移成本高 |
| Zustand | 不推荐 | React 定位更强，Vue 侧收益低 |
| Recoil | 不推荐 | React 专用，不适用于当前技术栈 |

### 7.2 重构方向

#### 7.2.1 模块拆分

原则：

- 按业务域拆 store，不按页面拆
- 每个 store 只负责“状态 + 纯派生 + 有限 action”
- 网络、副作用、Matrix SDK 调用继续下沉到 service 层

建议的层次：

- `domain store`：业务真状态
- `session store`：登录态、当前房间、当前设备等短周期状态
- `ui store`：抽屉、弹窗、浮层、过滤条件
- `cache store`：可再生缓存，不直接持久化整个对象树

#### 7.2.2 异步流程简化

措施：

- 建立统一 `useAsyncTask` / `useMutationTask` / `useQueryTask` 模式
- store action 只做 orchestration，不直接拼装复杂 HTTP/SDK 调用
- 为消息发送、文件上传、设置保存、加密恢复等流程统一状态机

#### 7.2.3 中间件优化

措施：

- 收口 `persistedstate` 的使用范围，仅持久化真正需要跨重启保留的状态
- 对敏感状态、临时状态、可重建缓存禁止落盘
- 增加 dev-only 调试插件，生产关闭详细快照

#### 7.2.4 DevTools 集成

措施：

- 统一 Pinia devtools 标识命名
- 给关键异步 action 添加 trace id
- 对消息发送、文件上传、会话恢复、同步状态切换建立时间轴事件

验收：

- 能在开发环境追踪任一消息从输入到落库到渲染的完整链路

## 8. 组件库升级与定制方案

### 8.1 总体方向

`hula` 当前桌面端使用 `Naive UI`，移动端使用 `Vant`。短期不建议替换组件库，建议基于 `Element Design Token` 的方法论做统一主题层，而不是强行迁移到 Element Plus。

### 8.2 基于 Design Token 的主题一致性

措施：

- 建立唯一 Token 源：`core / semantic / component / motion / z-index / breakpoint`
- 桌面端与移动端组件库全部通过 token adapter 映射
- 不允许组件内新增未注册色值、圆角、阴影、层级变量

验收：

- 同一语义色在 Naive UI / Vant / 自定义组件中表现一致

### 8.3 按需加载配置

措施：

- 精简自动导入范围
- 针对 Naive UI / Vant 逐步切换到更显式的组件引用边界
- Storybook 和测试环境使用更轻量注册策略

### 8.4 图标字体替换为 SVG

措施：

- 盘点现有 iconfont 使用点
- 新图标统一走 SVG sprite 或 Iconify
- 高频操作图标采用内联 SVG，支持颜色继承和无障碍 title

验收：

- 图标清晰度、主题色适配和可维护性显著提升

### 8.5 可访问性增强

措施：

- 为按钮、输入框、菜单、浮层统一补齐 aria 属性
- 提高键盘导航可达性
- 统一 focus ring 设计
- 为 SVG 图标补 `title` 或 `aria-hidden`
- 色彩对比度达到 WCAG AA

### 8.6 响应式断点统一

措施：

- 建立统一断点系统：`xs / sm / md / lg / xl`
- 禁止业务组件自定义随意断点
- 桌面与移动共用断点语义，不共用具体布局实现

## 9. 构建工具链升级路径

### 9.1 Webpack → Vite

结论：

- `hula` 已经完成 `Vite` 迁移，无需再做 Webpack→Vite
- 当前重点应从“迁移”转为“治理与加固”

### 9.2 Babel → SWC

结论：

- 生产构建主链路已由 `Vite/esbuild` 提供基础转换
- 不建议为了“追热点”进行全量 Babel→SWC 改造
- 建议在以下场景逐步验证 SWC：
  - JSX/TSX 转换
  - Storybook 编译
  - 测试环境提速
  - 脚本工具链

试点路径：

- 第一步：对非核心构建链引入 SWC 对照实验
- 第二步：采集构建时长、 sourcemap 质量、兼容性问题
- 第三步：仅在收益明确时替换

### 9.3 ESM 优先输出

措施：

- 保持前端产物 ESM 优先
- 脚本工具和 Node 侧尽可能统一 ESM
- 清理 CommonJS 兼容负担，仅在必须与旧生态兼容时保留桥接层

### 9.4 sourcemap 生成策略

建议：

- 开发环境：完整 sourcemap
- Staging：外部 sourcemap + Sentry 上传
- Production：隐藏 sourcemap，不随产物公开分发

### 9.5 Bundle 体积监控阈值

建议阈值：

- 首屏主包 gzip < `500KB`
- 单 chunk gzip < `300KB`
- 全量 JS gzip < `3MB`
- 任一新增依赖造成主包增长 > `50KB` 需评审

### 9.6 依赖预构建白名单

措施：

- 对 `matrix-js-sdk`、高频工具库、稳定依赖建立 `optimizeDeps` 白名单
- 对重型但低频依赖避免强制预构建
- 将预构建清单纳入文档和 CI 审查

## 10. 测试体系完善措施

### 10.1 覆盖率目标

虽然现有文档显示整体覆盖率较高，但建议从流程治理角度重新设门禁：

- 全仓最低门禁：`85%`
- 核心域（Matrix、store、hooks、auth、sync、media）：`90%+`
- 安全和恢复逻辑必须具备失败分支测试

## 11. 安全加固清单

### 11.1 CSP 策略细化

措施：

- 收紧 `script-src`、`connect-src`、`img-src`、`media-src`
- 分环境维护 CSP，避免生产保留调试白名单
- 尽量消除 `'unsafe-inline'` 和 `'unsafe-eval'`

### 11.2 SRI 完整性校验

适用场景：

- Web 环境第三方 CDN 资源
- 远程字体、脚本、样式等静态资源

### 11.3 依赖漏洞扫描自动化

措施：

- 将 `pnpm audit`、Dependabot、SCA 工具纳入 CI
- 对高危漏洞设置阻塞策略

### 11.4 XSS 防护

用户要求中提到 React XSS 防护，`hula` 为 Vue 项目，因此执行为 Vue 等价策略：

- 严格限制 `v-html`
- 富文本和 Markdown 渲染统一走 `DOMPurify`
- 链接、图片、附件、嵌入卡片统一走白名单清洗

### 11.5 敏感信息脱敏

措施：

- 日志脱敏：token、手机号、邮箱、设备 ID、恢复密钥
- 错误上报前做字段过滤
- 本地持久化状态避免保存敏感响应体

### 11.6 HTTPS 强制跳转

措施：

- Web 部署环境默认强制 HTTPS
- 仅开发或内网白名单允许 `http://`
- 对 Matrix homeserver 明文连接增加显式告警

### 11.7 OAuth 2.0 PKCE 流程

措施：

- OIDC / SSO 流程默认走 PKCE
- 严格校验 `state`、`nonce`、`redirect_uri`
- 避免把敏感 token 暴露在非受控日志和路由持久层

## 14. 服务发现专项优化方案

### 14.1 现状判断

`hula` 当前 `services/backend` 的服务发现实现主要是：

- Matrix `.well-known` endpoint discovery
- homeserver / identity server 本地持久化
- session 级 endpoint 绑定

它还不是完整的注册中心和服务治理系统。

### 14.2 优化目标

- 保留当前 Matrix endpoint discovery 能力
- 抽象为可扩展 `DiscoveryProvider`
- 为未来多注册中心、多节点、高可用治理预留接口

### 14.3 代码级改造建议

- 新增 `DiscoveryProvider` 接口
- 现有 `.well-known` 逻辑下沉为 `MatrixWellKnownProvider`
- 新增 `EndpointResolver` 负责：
  - 版本号
  - CRC 校验
  - fallback
  - 健康状态
  - 缓存
  - 监控埋点

### 14.4 高可用能力补齐

后续阶段逐步增加：

- Consul / Etcd / Zookeeper 适配器
- RR / Random / LeastConn / ConsistentHash
- 熔断 / 限流 / 重试退避 / 半开探测
- 双写容灾与灰度切换

## 16. 风险与回滚策略

### 16.1 主要风险

- 懒加载边界调整导致首次进入某些页面变慢
- store 重构导致隐式依赖断裂
- 构建配置分层可能引发双端产物差异问题
- 安全策略收紧可能影响调试与历史功能

### 16.2 回滚原则

- 所有架构改动保留兼容层至少一个迭代
- 配置类变更优先走 feature flag
- 构建链路保留旧配置入口
- 新监控默认先以告警模式运行，再转阻塞

## 26. 灰度发布与回滚策略矩阵

### 26.1 总体策略

所有 P0/P1 级优化都应遵循以下原则：

- 默认先以 feature flag 或配置开关方式上线
- 先旁路观测，再小流量灰度，再全量启用
- 任一阶段出现指标恶化，优先通过开关回退，而不是临时热修业务代码

### 26.2 灰度阶段

| 阶段 | 范围 | 目标 | 放量条件 |
|---|---|---|---|
| Stage 0 | 本地 / 测试环境 | 验证功能正确性 | 单测、集成、E2E 通过 |
| Stage 1 | 内部开发环境 | 验证日志、埋点、错误上报完整性 | 无阻塞错误 |
| Stage 2 | 1% 用户或灰度环境 | 观察性能和稳定性 | KPI 无显著恶化 |
| Stage 3 | 10%-30% 用户 | 观察边缘场景与回滚能力 | 错误率与 P95 可控 |
| Stage 4 | 50%-100% 用户 | 全量上线 | 告警稳定、无关键回归 |

### 26.3 任务级灰度建议

| 任务 | 建议开关 | 灰度方式 | 回滚方式 |
|---|---|---|---|
| 首屏懒加载 | `feature.lazyEntryV1` | 按环境先开，再小流量用户开 | 关闭开关，恢复静态导入 |
| persisted state 收口 | `feature.persistScopeV1` | 先内部账号，再灰度用户 | 回切旧 key 读取逻辑 |
| Vite 配置分层 | `build.profile=desktop/mobile` | 先 CI 和预发使用 | 回切旧单配置入口 |
| 虚拟滚动 | `feature.virtualListV1` | 先房间列表，再消息列表 | 切回旧渲染器 |
| Worker 化 | `feature.workerTasksV1` | 按任务类型逐个开启 | 回到主线程实现 |
| Design Token 统一 | `feature.designTokenV1` | 先设置页、再核心页面 | 切回旧变量映射层 |
| Sentry / 埋点 | `feature.observabilityV1` | 先开发/预发，再生产 | 关闭采集或降采样 |
| DiscoveryProvider 抽象 | `feature.discoveryProviderV1` | 先 shadow 模式，再主读切换 | 回退现有 localStorage + `.well-known` 逻辑 |

### 26.4 回滚触发阈值

满足以下任一条件，建议立即暂停放量或执行回滚：

- 首屏 P95 恶化超过 `15%`
- JS 错误率超过基线 `2x`
- 文件上传失败率超过 `5%`
- 登录失败率超过 `1%`
- E2E 关键链路出现阻塞性失败
- 生产出现新的高频安全告警

### 26.5 回滚优先级

1. 关闭 feature flag
2. 回退配置或路由入口
3. 回退到上一个稳定构建产物
4. 必要时执行数据兼容层恢复脚本

### 26.6 回滚演练要求

每个 P0 级任务在发布前必须完成：

- 一次灰度演练
- 一次回滚演练
- 一次监控告警验证
