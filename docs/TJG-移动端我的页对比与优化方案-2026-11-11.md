## 一、结论摘要

1. **初版列出的三个硬缺口（M1 九宫格假入口、M2 设备管理 4 层、M3 无搜索）已在 S1/S2 全部关闭**。当前代码取证：九宫格 5 个入口全部为真实路由；设备管理在首屏 1 跳、设置页 1 跳；设置页有吸顶搜索（29 条索引，含别名与锚点滚动）。
2. **「我的」页信息架构已回到「一屏一事」**：首屏只剩身份卡 + 4 行入口 + 5 宫格，昵称输入框与登出 danger 按钮均移出（分别并入 `EditProfile` 与设置页底部）。
3. **初版的两个卫生问题也已关闭**：`MobileEmojiManager.vue` 已注册 `/mobile/mobileMy/emoticons` 并有一级项与搜索入口；`/mobile/encryption` 已由「高级」组首项接入（2 跳可达），不是孤儿路由。
4. **「我的」页能力补齐已全部收口**：M6 好友请求三项（§14.5–14.7）、M9 存储明细与真清理（§14.8–14.10）、M8 设备改名（§14.11）均于 2026-11-11 完成，`my-hub-live` 6 passed。
5. **第二轮新增的 2 个 P0（均不在「我的」页范围内）均已关闭**：
   - `/mobile/rtcCall` 路由未声明 `props`，调用方只传 `query`，而页面用必填 `props`（`callId`/`isVideo`/`isIncoming`）⇒ 视频通话降级为语音界面、来电显示为去电、`callId` 为 `undefined`；
   - ~~`/mobile/dynamic` 是空间页的复制品（复用 `space.*` 文案与 `useSpaces`），`/mobile/dynamic/:id` 是占位页，且两者**无任何入口**~~ → **已删除**（路由、页面与过期 e2e 一并移除，见 §15.3）。
   详见 §十五。
6. 桌面比移动端多出来的能力，主要是**桌面专属但移动端不该照搬**的（键盘快捷键、窗口阴影、字体族文件、Mjolnir 社区管控），属于「合理不迁移」，需在能力清单中显式声明，避免被误判为缺陷。

## 二、现状取证

### 2.1 两端层级结构

```
桌面（settingsWindow）
  设置窗口(index.vue)
    └─ SettingsSidebar（搜索框 + 5 组 14 个 tab，方向键/Home/End 可达）
         └─ SettingsContent → tab（account / sessions / appearance / … ）
              └─ tab 内部分区（sections/*.vue）
  深度：2 跳（窗口 → tab），tab 内分区同屏可见

移动（views/my）
  「我的」首屏(index.vue)
    ├─ Settings.vue        顶栏 3 按钮：我的消息 / 扫一扫 / 设置（齿轮）
    ├─ PersonalInfo.vue    身份卡：头像 + 昵称 + 状态 + 账号 + 二维码 + 简介（只读）
    ├─ MobileMyEntryList   4 行入口：设备管理 / 通知 / 安全 / 设置
    └─ MobileQuickActions  5 宫格：扫一扫 / 文件 / 相册 / 二维码 / 私密聊天（全部真路由）
  MobileSettings.vue（/mobile/mobileMy/settings）7 组 20 项 + 吸顶搜索
    └─ 22 个二级页（MOBILE_MY_SETTINGS_CHILD_ROUTES）
  深度：设备管理 1 跳（首屏直达），设置页内 2 跳
```

### 2.2 桌面 tab 权威清单（`settingsSchema.ts` `SETTINGS_TABS`）

| 分组 | tab | 约束标记 |
| --- | --- | --- |
| general | account / sessions / appearance / notifications / preferences / keyboard | keyboard `desktopOnly` |
| communication | voiceVideo / friends / burnAfterRead | voiceVideo 需 `voip` 能力；friends 需 `friend-list` 能力 |
| security | securityPrivacy / encryption | — |
| advanced | mjolnir / storage | — |
| other | helpAbout | — |

共 **14 个 tab**；分类靠 `group` + `requiredCapability` 动态过滤（无能力时置灰而非隐藏）。

### 2.3 移动端设置一级项（`MobileSettings.vue`）

account(5：设备/状态/编辑资料/改密/安全) · social(1) · notification(1) · appearance(4：主题/语言/字号/气泡) · privacy(2：偏好/阅后即焚) · help(1) · advanced(6：加密/语音视频/存储/表情包/实验/服务器) = **20 项，7 组**；二级页 **22 条**。

## 三、信息架构差异

| 维度 | 桌面「设置」 | 移动「我的」 | 差异性质 |
| --- | --- | --- | --- |
| 一级容器 | 独立设置窗口，侧栏常驻 | 首屏：身份卡 + 4 行入口 + 5 宫格；设置项已全部下沉到设置页 | ✅ 已分层 |
| 分组方式 | 5 组语义分组 + 组标题 | 7 组；「偏好 / 阅后即焚」仍归 `privacy`，与桌面分组不完全一致 | 🟡 轻微漂移 |
| 定位效率 | 输入框搜索（跨 tab + 分区，含「不支持」标记）+ ↑↓/Home/End 键盘导航 | 吸顶搜索框（29 条索引，含别名与锚点滚动）；无键盘导航（移动端无此场景） | ✅ |
| 深度 | 2 跳；同层分区可见 | 设备管理 1 跳（首屏）/ 2 跳（设置）；其余二级页 2 跳 | ✅ |
| 能力过滤 | `requiredCapability` 驱动，未加载时骨架屏 | 高级组为静态数组（`mobileSettingsConfig.ts`），能力缺失不置灰也不提示 | 🟠 无法随能力收敛 |
| 状态回显 | tab 内 switch 即时生效 + toast | 同（switch 即改即存），仍无「保存中/失败并回滚」提示 | 🟡 反馈弱 |
| 退出登录 | 位于 account 的 `danger_zone` 分区 | 设置页底部 danger 按钮（已移出首屏） | ✅ 危险操作后置 |

**核心判断（复核后）**：初版指出的「个人主页与设置压在一屏」已解决；剩余差异集中在**能力收敛**（静态高级组）与**写入反馈**（开关失败无回滚），属于工程健壮性而非信息架构问题。

### P0（初版判定；M1–M3 均已关闭）

**~~M1 · 九宫格 5 个入口有效命中 0~~ ✅ 已修复（S1）**
证据：`MobileQuickActions.vue` 中 `scan → /mobile/mobileMy/myQRCode`（该路由是「我的二维码」页，`mobile.ts` 的 `mobileMyQRCode`），`wallet`/`favorite`/`file`/`shake` 均无 `route`，点击走 `showToast('开发中')`。
UX 影响：
- 用户点「文件」看到「开发中」，但 `/mobile/mobileMy/files` 页面（214 行、含分类/删除/转发/保存）**早已存在** ⇒ 能力有、入口假，用户会认为产品残缺；
- 「扫一扫」跳成「我的二维码」⇒ 想扫码加好友的人被送到展示自己码的页面，第一步就走错；
- 首屏最高价值的区域（F 型视线落点）浪费在 4 个谎报入口上，直接拉低对整页的信任。
修复成本：极低（接线 + 语义纠正 / 或按清单下线）。

**~~M2 · 「设备管理」沉到第 4 层~~ ✅ 已修复（S1）**
证据：`MobileSettings` 无 devices 项；只有 `SecuritySettings.vue:24` 一处 `router.push(MOBILE_SETTINGS_DEVICES_PATH)`。
UX 影响：丢手机/异地登录时，用户要在「我的 → 设置 → 安全设置 → 设备管理」四步内完成处置；焦虑场景下每多一层都是流失点。桌面是一次点击（`sessions` tab）。

**~~M3 · 设置无搜索~~ ✅ 已修复（S2）**
证据：`MobileSettings.vue` 无任何 `search` 引用；桌面 `SettingsSidebar.vue` 有 `searchQuery` + 路径面包屑 + `available` 标记。
UX 影响：16 个一级项 + 19 个二级页，用户只能靠记忆滚动。典型失败场景：「阅后即焚倒计时」这种低频设置，用户会先怀疑"移动端没有这个功能"，然后再去反馈，而不是继续翻。

### P1（能力存在但够不到 / 关键场景缺失）

**~~M4 · 加密与密钥详情页不可达~~ ✅ 已修复（S2）**
证据：`/mobile/encryption` → `mobileEncryption` → `EncryptionSettings.vue`，但 `grep mobileEncryption` 在 `src/**` 非路由文件中 **0 命中**。
UX 影响：UTD（无法解密）与"验证新设备"是 E2EE 产品最需要自解释的两处，页面写好了却没有任何入口，等于白写；用户只能看到 `SecuritySettings` 里的交叉签名开关，看不到状态诊断。

**~~M5 · 通知缺 DND 时段与通知历史~~ ✅ 已修复（S3 续）**
证据：桌面的 `setting.push.dnd.*`（起止时间）与 `setting.push.history.*`（历史列表 + ack + 已读）在移动端 0 对应键。
UX 影响：
- 没有 DND ⇒ 夜间只能全局关通知，第二天容易漏消息（"全关"是唯一选择，粒度粗糙）；
- 没有通知历史 ⇒ 通知被系统清掉后无法回溯"刚才谁找过我"，结合后端 `/notifications` 已能产出记录（报告 §4.9-A6），移动端反而是唯一看不到的地方。
注意：`ack` 用 `notification_id`（非 `event_id`），且 ack 后列表**不归零**（`read=true`），前端必须按 `read` 过滤，否则未读角标永远清不掉。

**M6 · 好友请求策略缺失（2026-11-11 更正范围）**

> ⚠️ **更正**：初版写的是「谁能加我 / 陌生人私信没有出口」——**不成立**。
> `MobileInvitePermission.vue`（241 行）早在，已覆盖陌生人私聊开关、blocklist/allowlist 名单、新私聊自动加密，
> `invitePolicy.ts` 里还有客户端强制点（`InvitePolicyEnforcer` 监听 `Room.member` 主动 leave 拒邀）。
>
> **真实缺口**：策略对象里 `allowFriendRequests` / `autoAcceptFriends` / `requireFriendRequestMessage`
> 三项**移动端没有任何 UI**（桌面 `FriendsSettings` 有），也就是手机上管得了「谁能私聊我」、管不了「谁能加我好友」。
> `MobileInvitePermission.persist()` 的注释里甚至写着「好友请求三项必须来自服务端最新值」——作者早知道它们存在，只是没做入口。

UX 影响：陌生人可以持续发好友请求，用户只能在「好友」Tab 里一条条忽略，无法事前关闸；也无法要求「加好友必须附言」来挡掉空白请求。

**~~M7 · 外观只有主题/语言/字号~~ ✅ 已修复（S3）**
证据：桌面的 `bubble_style`（圆角/直角）、`blur`、`window_shadow` 未迁移。
UX 影响：气泡样式是移动端最常被吐槽的观感项（微信/iMessage 双基线用户），缺它会让"外观"这一组看起来像只换了深色模式，实际可选空间极小。

**~~M8 · 设备不能重命名~~（2026-11-11 更正：已实现，本条为误判）**

> ⚠️ **更正说明**：初版结论来自 `grep -n "rename\|display_name\|setDeviceName"`——本仓的 bash `grep` 不支持 BRE 的 `\|`，会**静默返回空**，于是把"没搜到"当成了"没有"。
> 用 Grep 复核后：`DeviceManagement.vue` 早已有 `case 'rename'`（打开输入弹窗）、`deviceActions` 里的「重命名设备」项，以及 `mobile_devices.rename_*` 五个文案键，实现完整。
>
> **二次更正（同日，2026-11-11 晚）**：「无自动化覆盖」也**不成立** —— `__tests__/DeviceManagement.test.ts` 已有 17 条用例，其中三条专门覆盖重命名（成功 / 空值拒绝 / 失败提示），还有一条钉着「当前设备不提供任何操作项」。
>
> 所以这一条最终只剩一件真事：**`deviceActions` 对「当前设备」返回空数组**，把「不可删除」误写成了「不可操作」，顺手封掉了改名 ⇒ 单设备用户永远改不了自己这台的名字（桌面端一直可以）。已于 §14.11 修复，并顺带修掉操作面板显示英文标识符的问题。

### 8.3 二级页通用规范

**两个采集口径上的坑（都真实踩过）**

1. **不能只看盒子尺寸**：顶栏 3 个图标是 `32×32` 视觉盒 + `after:-inset-8px`（命中区 48×48）。采集器必须把伪元素负 inset 算进有效热区，否则会误报 3 项。第一版就是这么误报的。
2. **单手可达不能把顶栏按钮算进来**：顶栏天然在屏幕最上方，混进来会让指标永远不达标、也测不出「内容入口是否下沉」。已限定为 `.m-quick-item` + `.van-cell`。

> 另：UnoCSS 的 `min-w-[44px]` 写在 `:class` 数组字符串里没有生成样式（宽度仍是 28），改用内联 `:style` 才生效 —— 以后遇到「类名在、样式没生效」优先怀疑生成器扫描，直接上内联 style 验证。

### 10.3 关于 TTI 一直「采不到」的更正（2026-11-11 晚）

此前报告写的是「TTI 采不到，因为 reload 后会话恢复失败（D12）」。D12 修好后重采仍是 `n/a`，
才查出**采集判据本身是错的**：

- 旧实现：`page.reload()` → 等 `.m-quick-actions` 可见（60s）。
- 事实：reload 的落点是**消息页**（路由不持久化），`.m-quick-actions` 只在「我的」页。
  ⇒ 元素永远不出现，必然等满超时记 `null`。**与会话恢复无关**。

现改为两段分别计时（`e2e/my-hub-metrics.spec.ts`）：

1. `sessionRestoreMs`：reload → `getClient()` 非空（会话恢复完成的判据）；
2. `ttiMs`：reload → 进「我的」页 → 九宫格可见（含上面的恢复 + 一次 SPA 导航）。

三次采样：`ttiMs` 2413 / 2519 / 2942ms，`sessionRestoreMs` 1148 / 1247 / 1631ms。

**结论**：800ms 的目标目前**不现实**（差了约 3 倍），且一半以上耗在会话恢复
（`loginWithToken` + `startClient` + 首轮 sync）——这不是「我的」页的问题，是冷启动路径的问题。
若继续做性能优化，应先把目标拆成「会话恢复 ≤1.5s」与「首屏渲染 ≤800ms」两个可分别优化的指标。

### 14.9 两个口径决定（都会影响数字对不对）

1. **只统计磁盘**：这一页讲的是「本机占用」，worker 的**内存索引不是占用**；况且磁盘统计不依赖 worker 存活，任何时候都能给真数字。（曾短暂用 worker 的 `getSearchIndexStats()` 优先，会让页面显示 0 而磁盘其实有数据。）
2. **不显示「其它」的字节数**：`estimate()` 的 total 减掉 localStorage 剩下的是「IndexedDB + 其它」，无法归因到某一类。给一个算出来的数字等于编数据，宁可不给。

### 14.11 M8 收尾：本机可改名 + 两个顺带修掉的真缺陷

M8 这一条前后更正过两次（见 §五），最后一版只剩一件真事。落地时又撞出两个真缺陷，一共三件事：

**① 本机不可改名（原缺口）**

`deviceActions` 里写的是「当前设备返回空数组」，注释理由是「方案 3.1：当前设备固定顶部，不可删除」。但**不可删除 ≠ 不可操作**，顺手把改名也封了 ⇒ 单设备用户（新账号只有一台）永远改不了自己这台的名字。

桌面端一直允许：`SessionSettings` 第一张卡就是 `showRenameDialog(currentDevice)`。已对齐：本机只给 `rename`，仍不给 `logout`（那是自踢下线）与 `trust`（对自己没意义）。

**② 设备列表的数据源错了（比 ① 更严重，e2e 撞出来的）**

整页只吃 `keys/query`（`useDeviceTrust`）。而 `keys/query` 只返回**上传过 device_keys 的设备** —— 刚登录、crypto 还没初始化的设备（**包括本机**）根本不在里面。实测：页面只剩标题「设备管理 / 管理您的登录设备」，一行设备都没有。

「我这账号有哪些登录会话」的权威端点是 `GET /devices`（含本机、含 `last_seen`、含 `display_name`）。已改为：**行集合取自 `GET /devices`，`keys/query` 只用来补「是否已验证」**，两条数据源并行、任一失败都不影响列表可用。

**③ 操作面板把英文标识符显示给用户**

Vant 4 的 `ActionSheetAction` **只有 `name`**（就是显示文案），没有 `text` 字段。原实现是 `{ name: 'rename', text: t('mobile_devices.rename_device') }` ⇒ 弹层里直接渲染「rename / logout」。修复：`name` 放本地化文案（Vant 拿它显示），动作靠 `key` + `callback` 区分（`@select` 已移除，否则会把文案当标识符回传）。

> 这个 bug 从没被人发现，是因为它只在「点开某台设备的操作面板」时出现，且没有任何 e2e 走到那一步。单测也测不到（断言的是 `name` 的值，而旧实现的 `name` 恰好就是 `'rename'`，看起来「对」）。补了一条单测直接钉「文案必须来自 i18n、不能是英文标识符」。

### 15.2 P0-1：通话页参数断裂（`/mobile/rtcCall`）——已修复

#### 原判断（第一轮）与真实根因

第一轮只看到「路由没有 `props`」。落地修复时逐行核对调用链，实际是四处叠加的断裂，任何一处单独修补都不足以让通话可用：

1. **路由层**：`src/router/routes/mobile.ts` 的 `rtcCall` 只有 `path` / `name` / `component`，没有 `props`；页面 `src/mobile/views/rtcCall/index.vue` 也从不读 `route.query`。两个调用方（`src/mobile/components/RtcCallFloatCell.vue`、`src/mobile/components/chat-room/panel/More.vue`）只把参数放在 query 上，于是 `isVideo` / `isIncoming` 恒为 `false`，来电被渲染成去电、视频被降级成语音。
