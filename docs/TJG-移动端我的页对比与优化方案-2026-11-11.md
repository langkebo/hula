# 移动端「我的」页面 vs 桌面端「设置」页面：差异分析与优化方案

> 日期：2026-11-11 · 范围：`src/mobile/views/my/*`、`src/mobile/components/my/*`、`src/views/settingsWindow/*`、`src/stores/domains/settings/settingsSchema.ts`
> 方法：按源码取证（文件 + 符号），不采信注释与文档描述；同一事实用「路由是否注册」「是否有 push 调用」双向核对。

---

## 一、结论摘要

1. **功能覆盖差距远小于信息架构差距**。移动端已落地 19 个设置子路由（设备、密码、忽略用户、安全密钥、存储、推送、邀请权限、注销、通知、帮助、语音视频、实验、集成、服务器、文件、阅后即焚、偏好、加密、安全与隐私），能力面并不缺；真正的差距在**入口分层与暴露方式**。
2. **三个硬缺口**（用户可感知、非能力缺失）：
   - 九宫格 5 个入口 **有效命中 0 个**：4 个弹「开发中」，1 个（扫一扫）指向「我的二维码」语义错位；
   - 「设备管理」被压到第 4 层（我的 → 设置 → 安全设置 → 设备管理），而它是安全事件的第一处置入口；
   - 设置**无搜索**：16 个一级项 + 19 个二级页，只能靠滚动记忆定位。
3. **两个卫生问题**：`/mobile/encryption` 路由存在但全仓无人 push（事实不可达）；`MobileEmojiManager.vue` 既无路由也无引用（死代码）。
4. 桌面比移动端多出来的能力，主要是**桌面专属但移动端不该照搬**的（键盘快捷键、窗口阴影、字体族文件、Mjolnir 社区管控），属于「合理不迁移」，需在方案里显式声明，避免被误判为缺陷。

## 二、现状取证

### 2.1 两端层级结构

```
桌面（settingsWindow）
  设置窗口(index.vue)
    └─ SettingsSidebar（搜索框 + 5 组 14 个 tab，方向键/Home/End 可达）
         └─ SettingsContent → tab（account / sessions / appearance / … ）
              └─ tab 内部分区（sections/*.vue）
  深度：2 跳（窗口 → tab），tab 内分区同屏可见

移动（views/my）
  「我的」首屏(index.vue)
    ├─ Settings.vue        顶栏 3 按钮：我的消息 / 扫一扫 / 设置（齿轮）
    ├─ PersonalInfo.vue    头像 + 昵称 + 状态 + 账号 + 二维码 + 简介 + 点赞关注
    ├─ MobileQuickActions  5 宫格：扫一扫 / 钱包 / 收藏 / 文件 / 摇一摇
    ├─ 昵称内联编辑        首屏直接暴露输入框 + 保存
    └─ 退出登录            danger 按钮，首屏底部
  MobileSettings.vue（/mobile/mobileMy/settings）7 组 16 项
    └─ 19 个二级页（MOBILE_MY_SETTINGS_CHILD_ROUTES）
  深度：3 跳（我的 → 设置 → 二级页），"设备管理"需 3 跳（经安全设置）
```

### 2.2 桌面 tab 权威清单（`settingsSchema.ts` `SETTINGS_TABS`）

| 分组 | tab | 约束标记 |
| --- | --- | --- |
| general | account / sessions / appearance / notifications / preferences / keyboard | keyboard `desktopOnly` |
| communication | voiceVideo / friends / burnAfterRead | voiceVideo 需 `voip` 能力；friends 需 `friend-list` 能力 |
| security | securityPrivacy / encryption | — |
| advanced | mjolnir / storage | — |
| other | helpAbout | — |

共 **14 个 tab**；分类靠 `group` + `requiredCapability` 动态过滤（无能力时置灰而非隐藏）。

### 2.3 移动端设置一级项（`MobileSettings.vue`）

account(4) · social(1) · notification(1) · appearance(3：主题/语言/字号) · privacy(2：偏好/阅后即焚) · help(1) · advanced(4：语音视频/存储/实验/服务器) = **16 项，7 组**。

## 三、信息架构差异

| 维度 | 桌面「设置」 | 移动「我的」 | 差异性质 |
| --- | --- | --- | --- |
| 一级容器 | 独立设置窗口，侧栏常驻 | 「我的」首屏混合了**个人资料 + 快捷入口 + 设置入口 + 危险操作** | 🔴 职责混杂 |
| 分组方式 | 5 组语义分组 + 组标题 | 7 组，但语义漂移：「偏好 / 阅后即焚」被归到 `privacy`，桌面归 `general/communication` | 🟠 分组不一致 |
| 定位效率 | 输入框搜索（跨 tab + 分区，含「不支持」标记）+ ↑↓/Home/End 键盘导航 | 无搜索、无锚点、无最近访问 | 🔴 长列表裸滚 |
| 深度 | 2 跳；同层分区可见 | 3 跳；「设备管理」4 层 | 🔴 关键项过深 |
| 能力过滤 | `requiredCapability` 驱动，未加载时骨架屏 | 高级组硬编码 4 项（`mobileSettingsConfig.ts` 静态数组），能力缺失也不提示 | 🟠 无法随能力收敛 |
| 状态回显 | tab 内 switch 即时生效 + toast | 同（switch 即改即存），但**无"保存中/失败"回滚提示** | 🟡 反馈弱 |
| 退出登录 | 位于 account 的 `danger_zone` 分区 | 首屏底部独立 danger 按钮 | 🟠 危险操作前置 |

**核心判断**：移动端把「我的 = 个人主页」和「我的 = 设置入口」两件事压在一屏，导致首屏黄金区被低频内容（昵称输入框、无效九宫格）占据，而高频入口（设备、通知、隐私）反而下沉到第 3–4 层。这是"层级扁平化"原则的直接违背。

## 五、缺失与弱化清单（含用户体验影响）

> 影响描述区分「用户能感觉到什么」，不写抽象评价。

### P0（不修则信任受损 / 主路径阻断）

**M1 · 九宫格 5 个入口有效命中 0**
证据：`MobileQuickActions.vue` 中 `scan → /mobile/myQRCode`（该路由是「我的二维码」页，`mobile.ts` 的 `mobileMyQRCode`），`wallet`/`favorite`/`file`/`shake` 均无 `route`，点击走 `showToast('开发中')`。
UX 影响：
- 用户点「文件」看到「开发中」，但 `/mobile/mobileMy/files` 页面（214 行、含分类/删除/转发/保存）**早已存在** ⇒ 能力有、入口假，用户会认为产品残缺；
- 「扫一扫」跳成「我的二维码」⇒ 想扫码加好友的人被送到展示自己码的页面，第一步就走错；
- 首屏最高价值的区域（F 型视线落点）浪费在 4 个谎报入口上，直接拉低对整页的信任。
修复成本：极低（接线 + 语义纠正 / 或按清单下线）。

**M2 · 「设备管理」沉到第 4 层**
证据：`MobileSettings` 无 devices 项；只有 `SecuritySettings.vue:24` 一处 `router.push(MOBILE_SETTINGS_DEVICES_PATH)`。
UX 影响：丢手机/异地登录时，用户要在「我的 → 设置 → 安全设置 → 设备管理」四步内完成处置；焦虑场景下每多一层都是流失点。桌面是一次点击（`sessions` tab）。

**M3 · 设置无搜索**
证据：`MobileSettings.vue` 无任何 `search` 引用；桌面 `SettingsSidebar.vue` 有 `searchQuery` + 路径面包屑 + `available` 标记。
UX 影响：16 个一级项 + 19 个二级页，用户只能靠记忆滚动。典型失败场景：「阅后即焚倒计时」这种低频设置，用户会先怀疑"移动端没有这个功能"，然后再去反馈，而不是继续翻。

### P1（能力存在但够不到 / 关键场景缺失）

**M4 · 加密与密钥详情页不可达**
证据：`/mobile/encryption` → `mobileEncryption` → `EncryptionSettings.vue`，但 `grep mobileEncryption` 在 `src/**` 非路由文件中 **0 命中**。
UX 影响：UTD（无法解密）与"验证新设备"是 E2EE 产品最需要自解释的两处，页面写好了却没有任何入口，等于白写；用户只能看到 `SecuritySettings` 里的交叉签名开关，看不到状态诊断。

**M5 · 通知缺 DND 时段与通知历史**
证据：桌面的 `setting.push.dnd.*`（起止时间）与 `setting.push.history.*`（历史列表 + ack + 已读）在移动端 0 对应键。
UX 影响：
- 没有 DND ⇒ 夜间只能全局关通知，第二天容易漏消息（"全关"是唯一选择，粒度粗糙）；
- 没有通知历史 ⇒ 通知被系统清掉后无法回溯"刚才谁找过我"，结合后端 `/notifications` 已能产出记录（报告 §4.9-A6），移动端反而是唯一看不到的地方。
注意：`ack` 用 `notification_id`（非 `event_id`），且 ack 后列表**不归零**（`read=true`），前端必须按 `read` 过滤，否则未读角标永远清不掉。

**M6 · 好友隐私与请求管理弱化**
证据：`MobileSettings` social 组只有 `friend_groups`；桌面 `friends` tab 含分组 + 待处理 + 隐私策略。
UX 影响：好友请求处理被拆到好友 Tab（尚可），但「谁能加我 / 是否允许陌生人私信」这类**预防性**设置没有出口，用户只能在被打扰后去找客服，而不是事前关闸。

**M7 · 外观只有主题/语言/字号**
证据：桌面的 `bubble_style`（圆角/直角）、`blur`、`window_shadow` 未迁移。
UX 影响：气泡样式是移动端最常被吐槽的观感项（微信/iMessage 双基线用户），缺它会让"外观"这一组看起来像只换了深色模式，实际可选空间极小。

**~~M8 · 设备不能重命名~~（2026-11-11 更正：已实现，本条为误判）**

> ⚠️ **更正说明**：初版结论来自 `grep -n "rename\|display_name\|setDeviceName"`——本仓的 bash `grep` 不支持 BRE 的 `\|`，会**静默返回空**，于是把"没搜到"当成了"没有"。
> 用 Grep 复核后：`DeviceManagement.vue` 早已有 `case 'rename'`（打开输入弹窗）、`deviceActions` 里的「重命名设备」项，以及 `mobile_devices.rename_*` 五个文案键，实现完整。
>
> **真实缺口改为**：该能力**没有任何自动化覆盖**（无单测 / 无 e2e），且 `deviceActions` 对「当前设备」返回空数组 ⇒ 新账号（只有一台设备）根本看不到这个入口，等于**单设备用户不可达**——这个才是需要在文档里记的点。

**M9 · 存储页只读配额**
证据：移动 5 个键（`quota/used/loading/title/usage_section`）vs 桌面 24 个键（上传上限、分片、压缩质量、配额告警阈值）。
UX 影响：用户能知道"用了多少"，但不知道"为什么这么大 / 能不能清"。注：清理缓存在**两端都缺**，应作为新增能力而非"移动端缺失"。

### P2（卫生与一致性）

**M10 · 死代码与孤儿路由**
`MobileEmojiManager.vue`（255 行）无路由无引用；`/mobile/encryption` 有路由无入口。影响：包体白携带、后续改动误以为"已上线"、审计成本上升。

**M11 · 版本号双源且硬编码**
`MobileSettings.vue:185` 写死 `v1.0.0`，而 `HelpFeedback` 用 `mobile_help.latest_version` 动态读。影响：两处显示不一致时，反馈问题时用户报的版本号不可信。

**M12 · 首屏冗余与危险操作前置**
- 首屏裸放「昵称输入框 + 保存」，与 `EditProfile`（含昵称/头像/简介/性别/生日/手机/地区）功能重叠 ⇒ 用户不知道该在哪改，改完两边不同步（`index.vue` 只更新 `userStore`，不走 `EditProfile` 的保存链路）；
- 「退出登录」danger 按钮在首屏底部，单手滚动时误触概率高（桌面放在 `danger_zone` 内，需二次进入）。
- 两处登出入口分别走 `useSessionActions` / `useLoginFlow`，底层同为 `sessionOrchestrator.logoutCurrentSession`，行为一致但路径分叉，属维护债。

## 六、优化目标

### 6.1 量化目标（验收用）

| # | 目标 | 现状基线 | 目标值 |
| --- | --- | --- | --- |
| G1 | 首屏无效入口数（点了没有真实目的地） | 4 / 5（仅 1 个接线且错指向） | 0 |
| G2 | 到「设备管理」的点击数 | 4 | ≤ 2 |
| G3 | 设置可检索覆盖率（19 个二级页 / 16 个一级项） | 0% | 100% |
| G4 | 首屏**输入类控件**数 / **danger 按钮**数 | 2（昵称输入 + 保存）/ 1（退出登录） | 0 / 0（分别迁入 `EditProfile` 与设置页底部） |
| G5 | < 44×44 CSS px 的触控目标数 | 待采集（顶栏按钮已用 `after:-inset-8px` 扩到 48px，合规） | 0 |
| G6 | 设置页首屏可交互（TTI） | 待采集 | ≤ 800ms（P75，中端安卓） |
| G7 | 孤儿路由 / 零引用组件 | 2 | 0 |

### 6.2 定性目标

- **一屏一事**：首屏只承担「我是谁 + 我去哪」，不承担「我改什么」；
- **安全前置**：设备/加密/隐私类在 2 跳内可达；
- **单手可完成**：所有一级入口落在屏幕下 2/3，顶部只保留导航与低频操作；
- **渐进披露**：首屏 6–8 个一级项，其余进「全部设置」；能力缺失时置灰 + 说明，不静默消失。

### 13.3 顺带修掉的真实缺陷（e2e 撞出来的）

**移动端路由里被踢出时跳到了桌面登录页。**

`authGuard` 的 `loginPath` 只看全局 `isMobile`。但平台判定与「用户此刻站在哪套路由里」可能不一致（移动端产物保留桌面窗口路由；浏览器整页重载会丢掉 `?platform=mobile`）。此时用户在 `/mobile/mobileMy/settings` 被判定未登录，会被甩到 `/login` —— 手机上看到 PC 登录页。

修复：`loginPath` 改为 `isMobile || to.path.startsWith('/mobile')`，以「用户所见页面」为准；补单测并做变异自证（改回旧逻辑 ⇒ 新用例 `Expected "/mobile/login" Received "/login"` 变红）。

### 13.4 测试基建（本轮踩到的两件事）

1. **`push` 到同一路由不会重建组件**：设置页搜索词会残留并把列表 `v-show` 隐藏，导致后续断言命中隐藏元素（`unexpected value "hidden"`）。用例改用 `gotoSettings()` helper：进入后先清空搜索。
2. **开发态 `hasAuthenticatedSession()` 会偶发读空**（既有缺陷，非本轮引入），导航被随机甩到登录页。本套用例只验证「入口可达」，故用项目自带标记 `tjg:e2e:platform=mobile` + `tjg:e2e:mock-auth=1` 稳定环境；鉴权由 `authGuard` 单测覆盖。

### 14.3 一条方法论教训（值得写进流程）

**本仓的 bash `grep` 不支持 BRE 转义 `\|`，会静默返回空**，看起来完全像"确实没有匹配"。M8 就是被它误判的：`grep -n "rename\|display_name\|setDeviceName"` 返回空 → 我写成"无 rename"。
后续凡是用 `\|` / `\s` / `\+` 的检索，一律改用 Grep 工具或 `grep -E`；出现"找不到"的结论前必须用另一种方式复核一次。
