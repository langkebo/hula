## 二、结论摘要

| 严重程度 | 数量 | 关键主题 |
|---|---|---|
| 高 | 4 | token 自动续期失效、上传凭证鉴权缺失、上传响应字段全部错配、好友请求字段全部错配 |

三条主链路（**登录续期**、**附件发送**、**好友申请**）在当前代码组合下**存在确定性断裂**，且断裂点都在「字段名/单位/鉴权头」这类联调最典型的位置上。

## 三、问题清单

> 格式：问题描述 → 涉及前后端 → 复现步骤 → 严重程度 → 原因推断 → 验证状态

### H-1 token 自动续期在主登录路径上从未被排期

- **问题描述**：账号密码登录与 SSO 登录读取 `loginResponse.expires_in_ms`，服务端只返回 `expires_in`（秒），取值恒为 `undefined ?? 0 = 0`，`expiresInMs > 0` 判定为假 ⇒ `tokenManager.schedule()` 从未被调用 ⇒ access_token 24h 到期后无自动刷新。而 token 过期后前端仅广播 `TOKEN_EXPIRED` 让用户重登，没有「刷新 + 重试」拦截器。
- **涉及**：
  - 前端 `src/services/matrix/MatrixClientAuth.ts:135`（`login`）、`:293`（`completeSSOLogin`）—— 均用 `expires_in_ms ?? 0`
  - 前端 `src/services/matrix/MatrixClientAuth.ts:189`（`registerGuest`）—— 用 `expires_in * 1000`（正确，形成同仓不一致）
  - 前端 `src/services/matrix/MatrixTokenManager.ts:23-35`（未被调度即失效）
  - 前端 `src/services/matrix/MatrixWsBridge.ts:35-50`（过期只发事件，不刷新）
  - 后端 `POST /_matrix/client/v3/login`、`/refresh`（仅返回 `expires_in`）
  - 页面：`src/views/loginWindow/*`、`src/mobile/login.vue`
- **复现**：
  1. `POST /_matrix/client/v3/register`（或 login）→ 响应体仅含 `expires_in: 86400`，无 `expires_in_ms`
  2. 前端 `login()` 内 `expires_in_ms ?? 0` → 0 → `if (refresh_token && 0 > 0)` 不成立
  3. 把 access_token 有效期调短（或等 24h）→ 任意请求 401 → 只能手动重登
- **严重程度**：**高**
- **原因推断**：早期后端曾返回 `expires_in_ms`（MSC 草案命名），改为规范 `expires_in` 后前端两处漏改；`MatrixTokenManager.refresh()` 里有 `expires_in` 的兜底（`:78-82`），但**调度入口**没有同样兜底，导致兜底成为死代码。
- **验证状态**：**已验证（实测 + 源码）**——实测 register/refresh 响应只含 `expires_in`。

### H-2 上传凭证接口调用未携带鉴权头

- **问题描述**：`UploadService` 直接用裸 `HttpClient` 打 `/_matrix/client/v3/upload/token` / `/upload/provider`，`HttpClient` 不注入任何 header，后端 `AuthenticatedUser` 提取器要求 Bearer ⇒ 恒 401。返回 `null` 后，图片/文件策略抛 `AppException('获取上传链接失败，上传服务不可用')`，**聊天附件发送全链路失败**。
- **涉及**：
  - 前端 `src/services/performance/UploadService.ts:47`、`:69`（无 `Authorization`）
  - 前端 `src/composables/common/useUpload.ts:185-198`（null 直接抛错）、`:260-264`（提示 `credential_failed` 并 return）
  - 前端 `src/strategy/strategies/{image,file,voice}.ts` 的 `uploadFile`
  - 后端 `synapse-web/src/routes/media/upload.rs:393`（`auth_user: AuthenticatedUser`）
  - 页面：聊天输入框发图/发文件/发语音（`src/composables/chat/useMsgInputSend.ts`）、AI 参考图上传
- **复现**：
  1. `curl -X POST :8008/_matrix/client/v3/upload/token`（无 Authorization）→ **401** `{"errcode":"M_UNAUTHORIZED"}`
  2. 前端调用同一 URL，同样 401 → `getOssToken` catch → `null`
  3. `getUploadCredential` 返回 null → `getUploadAndDownloadUrl` 返回 null → 策略抛「上传服务不可用」
- **严重程度**：**高**
- **原因推断**：`UploadService` 属于早期「REST 直连」遗留，未随 `SynapseExtensionHttpBase`（有 `ensureInitialized()` 取 token）改造；`HttpClient` 定位是「无鉴权裸通道」，此处被误用于需要鉴权的端点。
- **验证状态**：**已验证（实测 401 + 源码）**；前端 UI 表现（弹「上传失败」）为**推断**（dev server 未起）。

### H-3 上传凭证响应字段与前端契约完全不匹配

- **问题描述**：后端返回 snake_case 且语义不同：`{upload_token, storage_type, upload_url, filename, content_type, max_file_size}`；前端声明 camelCase 且要求 `uploadUrl` + `downloadUrl` 双必填。即使 H-2 修好鉴权，`credential.uploadUrl` 仍为 `undefined`，依旧抛「上传服务不可用」。另外后端**没有 `downloadUrl`**（上传后需自行拼 `/_matrix/media/v3/download/...`），前端无此逻辑。
- **涉及**：前端 `src/services/performance/UploadService.ts:8-17`；后端 `media/upload.rs:403-414`；消费方 `useUpload.ts:194-196`
- **复现**：带鉴权 `POST /_matrix/client/v3/upload/token` → 实测响应见下
  ```json
  {"content_type":"image/png","filename":"a.png","max_file_size":52428800,
   "storage_type":"matrix","upload_token":"upload_@probe…",
   "upload_url":"/_matrix/media/v3/upload"}
  ```
- **严重程度**：**高**
- **原因推断**：后端把该端点实现成「Matrix 原生上传的元信息」，前端仍按「OSS 预签名凭证」（MinIO/阿里云时代）建模，两侧语义已分叉但无契约测试约束。前端传入的 `scene` 字段被后端静默丢弃（`CreateUploadTokenBody` 无该字段且未 `deny_unknown_fields`）。
- **验证状态**：**已验证（实测）**——字段映射流水线判定：`uploadUrl` = NAME_STYLE(MEDIUM)、`downloadUrl` = MISSING(HIGH)、6 个可选 OSS 字段 = MISSING(MEDIUM)。

### H-4 好友请求列表字段与前端模型不一致，回退路径产出全 `undefined`

- **问题描述**：后端请求条目是 `{user_id, message, timestamp, status}`；前端 `normalizeSynapseFriendRequest` 按 `requester` / `recipient` / `created_ts` 取值 ⇒ `FriendRequest.user_id` 恒 `undefined`、`timestamp` 恒 `undefined`。REST 轮询随后用 `user_id` 做「新增请求」差集，`Set` 里只有 `undefined` ⇒ 新请求检测与红点全错。
- **涉及**：
  - 前端 `src/services/matrix/friends/friendUtils.ts:56-69`（取 `requester`/`recipient`/`created_ts`）
  - 前端 `src/services/matrix/friends/MatrixFriendSync.ts:357-373`（轮询差集用 `user_id`）
  - 前端 `src/services/matrix/friends/MatrixFriendService.ts:141-182`
  - 后端 `synapse-services/src/friend_room_service/mod.rs:527-558`
  - 后端路由 `synapse-web/src/routes/friend_room.rs:451-467`
  - 页面：`src/components/friend/FriendRequestCard.vue`、`src/views/homeWindow/FriendsList.vue`、`src/mobile/views/friends/*`
- **复现**：实测 `GET /_matrix/vendor/v1/friends/requests/outgoing`
  ```json
  {"requests":[{"message":"hi","status":"pending","timestamp":1793832482378,
                "user_id":"@probe21793832481:matrix.test"}]}
  ```
  无 `requester` / `recipient` / `created_ts` / `request_id`。
- **严重程度**：**高**（数据结构级错误；触发条件为「FriendManager 不可用 / 返回空 / 抛错」时的 REST 回退路径，属常见降级场景）
- **原因推断**：前端模型按「请求实体」建模（含双方 + 创建时间），后端按「对端视角的摘要」建模（只给对端 `user_id`）。`friendUtils.test.ts` 的夹具用的是前端自己的形状（自洽桩），所以单测全绿。
- **验证状态**：**已验证（实测 + 源码）**；界面表现（申请卡片空白/时间为 Invalid Date）为**推断**。

### M-1 好友列表无分页，超过 50 条静默截断

- **问题描述**：后端 `GET /friends` 默认 `limit=50`（`1..=200`），并以 `total` / `next_batch` / `next_offset` 回传游标；前端调用不带任何 query、也不读 `total`/`next_batch` ⇒ 好友 >50 时只显示前 50，无「加载更多」，用户无感知。
- **涉及**：前端 `src/services/matrix/extensions/SynapseFriendExtensionService.ts:96-143`；后端 `friend_room.rs:254-303`、`:235-252`
- **复现**：实测 `GET /_matrix/vendor/v1/friends` → `{"friends":[],"limit":50,"total":0,"next_batch":null,"offset":0,…}`；把 `limit=500` → 400 `M_INVALID_PARAM`（后端校验正确，前端只是从不传）
- **严重程度**：**中**
- **原因推断**：分页能力由后端 BE-10 引入，前端未跟进；`offset` 兼容入口已废弃，接入需改用 `from` 游标。
- **验证状态**：**已验证（实测 + 源码）**

### M-2 扩展端点请求无超时、无取消、无重试

- **问题描述**：`SynapseExtensionHttpBase.request()` 直接 `runtimeFetch(url, options)`，未创建 `AbortController`、未设 `timeoutMs`；对比 `HttpClient` 有 30s 超时。好友列表等接口若后端慢查询/挂住，Promise 永不 settle，UI 停留在 loading，且无法取消。
- **涉及**：前端 `src/services/matrix/extensions/SynapseExtensionHttpBase.ts:76-135`、`:165-186`（HEAD 探测同样无超时）；受益方为全部 `/_matrix/vendor/v1/friends|invites|voice|rooms/*` 调用
- **复现**（推断）：把后端某 handler 延迟 60s，进入通讯录 → 骨架屏不消失；退出页面请求仍在飞
- **严重程度**：**中**
- **原因推断**：该基类由 1069 行「杂物抽屉」拆分而来，只做了 token 去重（AR-07b），未补传输层治理。
- **验证状态**：**已验证（源码）**

### M-3 失败被吞成「空数据」，故障与「真的没有」不可区分

- **问题描述**：以下方法在 catch 里返回空/false，而非抛错或返回可区分状态：`getFriends→[]`、`searchFriends→[]`、`getPendingRequests→{[],[]}`、`checkFriendship→false`、`getDmRoom→{room_id:'',exists:false}`。后果：后端 500/网络断开时，用户看到「没有好友」「不是好友」「搜索无结果」，无法触发重试或提示。
- **涉及**：前端 `SynapseFriendExtensionService.ts:129-142 / 214-229 / 264-267 / 378-381`、`SynapseDmExtensionService.ts:53-56`；页面同上（通讯录、加好友、会话详情）
- **复现**（推断）：停掉后端 → 刷新通讯录 → 显示为空列表且无错误提示；日志里只有 `logger.error`
- **严重程度**：**中**
- **原因推断**：早期为实现「端点不可用时降级为空」的兼容策略（`isFriendEndpointAvailable`），把**能力缺失**与**调用失败**混为一类处理。
- **验证状态**：**已验证（源码）**

### M-4 `request_id` 后端为字符串，前端声明为数字

- **问题描述**：`send_friend_request` 返回 `request_id` 是 `resolve_request_id()` 的字符串（实测 `"82"`，无 `X-Request-Id` 时为 `req-<uuid>`）；前端 `SynapseFriendRequest.request_id: number`，`sendFriendRequest` 返回类型也是 `number`。运行时类型与声明不符，任何 `+1` / 数值比较 / 严格相等都会出错。
- **涉及**：前端 `SynapseFriendExtensionService.ts:145-185`；后端 `friend_room.rs:397-402`
- **复现**：`POST /_matrix/vendor/v1/friends/request` → `{"request_id":"82","status":"pending"}`
- **严重程度**：**中**
- **原因推断**：后端早期 request_id 来自 DB 自增（i64），改为 `X-Request-Id` 透传后变成字符串，但响应体字段名未变、前端类型未改。
- **验证状态**：**已验证（实测 + 源码）**

### M-5 状态码与错误码语义错配（两处）

- **问题描述**：
  1. 废弃的 `offset` 分页参数返回 **400 `M_BAD_JSON`**，而 `M_BAD_JSON` 的语义是「请求体不是合法 JSON」。前端 `VALIDATION_ERRCODES` 命中 `M_BAD_JSON` → 向用户展示「请求格式错误」，与真实原因（分页方式已变更）无关。
  2. 缺少 token 返回 **401 `M_UNAUTHORIZED`** —— 该码**不在 Matrix 规范**（规范为 `M_UNKNOWN_TOKEN` / `M_MISSING_TOKEN`），前端 `AUTH_ERRCODES` 与 `locales/errors/*.ts` 均无此码，只能靠 `httpStatus===401` 兜底，文案退化为英文 `message`。
- **涉及**：后端 `friend_room.rs:266`（`ApiError::bad_request`）、`synapse-common/src/error.rs:283-288`（`MatrixErrorCode::Unauthorized`）；前端 `src/common/errors.ts:58`、`:75-96`
- **复现**：
  - `GET /friends?offset=10` → `400 {"errcode":"M_BAD_JSON","error":"Legacy offset pagination is no longer supported…"}`
  - `POST /upload/token`（无头）→ `401 {"errcode":"M_UNAUTHORIZED"}`
- **严重程度**：**中**
- **原因推断**：`ApiError::bad_request` 被当作「万能 400」，未区分 `M_INVALID_PARAM` 与 `M_BAD_JSON`；`M_UNAUTHORIZED` 是自造码，为「统一 401 语义」引入但破坏了 Matrix 客户端兼容。
- **验证状态**：**已验证（实测）**；状态码流水线判定 `biz=M_UNKNOWN` 同时映射 `http=400/409/500/501/503`（HIGH 同码多义）、`M_NOT_FOUND` 同时映射 `404/410`（HIGH）。

### M-6 幂等契约三方不一致，实际未生效（当前靠业务唯一性兜底）

- **问题描述**：前端在好友请求上带 `Idempotency-Key`；后端 `resolve_request_id()` 只读 `x-request-id`；CORS `Access-Control-Allow-Headers` 也不放行 `idempotency-key`（预检实测被过滤）。⇒ 该头在 Web 端会被剥离、在服务端被忽略，「SDK 通道失败→REST 重发」的去重能力是纸面的。
- **涉及**：前端 `SynapseFriendExtensionService.ts:156-168`、`friendUtils.ts:119-121`；后端 `synapse-web/src/utils/auth.rs:10-17`；CORS `synapse-web/src/middleware/cors.rs:216-244`
- **复现**：
  - 预检 `OPTIONS /_matrix/vendor/v1/friends/request`（`Access-Control-Request-Headers: authorization,content-type,idempotency-key`）→ 响应 `access-control-allow-headers: authorization, content-type`（**idempotency-key 被丢弃**）
  - 同 `Idempotency-Key` 连发两次 → 两次都 200，返回同一 `request_id:"82"`（**未产生重复**，是服务端 pending 唯一性在兜底，不是幂等键生效）
- **严重程度**：**中**（当前无数据重复，但契约是假的；一旦业务层唯一约束松动即重复提交）
- **原因推断**：前端按「HTTP 幂等键」通用实践实现，后端复用了「请求追踪 ID」头，两侧对同一个头没有共同约定。
- **验证状态**：**已验证（实测）**

### M-7 契约测试只校验路径，字段与状态码无任何契约

- **问题描述**：`friends.contract.test.ts` 仅断言「前端路径常量能在 SDK route-table 里匹配」，不校验请求体/响应体字段、类型与状态码；且 `FRIENDS.DM` 的断言是**空 `if` 体**（`if (!matched) {}`），永远通过。本轮 4 类字段错配、2 类状态码错配全部漏网。
- **涉及**：`src/services/matrix/paths/__tests__/friends.contract.test.ts:89-94`（空断言）、整体 45-109
- **复现**：改后端 `request_id` 类型或删 `friends` 字段 → 契约测试仍绿
- **严重程度**：**中**
- **原因推断**：契约层只做到「路由存在性」，缺少 schema（请求/响应）与错误码矩阵。
- **验证状态**：**已验证（源码）**

### L-3 `UploadService.baseUrl` 构造期快照

## 四、分维度核验结果

| 维度 | 结论 |
|---|---|
| **鉴权** | Bearer 注入方式正确（`SynapseExtensionHttpBase` 每次现取 token）；**唯一致命缺口**是 `UploadService` 完全不带鉴权（H-2）。401 的 errcode 用自造 `M_UNAUTHORIZED`（M-5）。刷新链路存在但主登录路径不排期（H-1） |
| **跨域** | 生产模式下仅回显白名单 origin 的 `Access-Control-Allow-Origin`，非白名单 origin 一律不带（浏览器直接拦截）；Tauri 走 `plugin-http` 原生通道不受 CORS 限制。**预检 allow-headers 缺 `idempotency-key`**（M-6）。`credentials:'omit'` + Bearer 语义自洽 |

| **文件上传** | 主链路断裂（H-2 + H-3）。Tauri `upload_file_put` 通道本身可用（`invokeWithErrorHandler` + progress Channel），问题全在「拿凭证」这一步 |
| **文件下载** | `mediaDownloadHelpers` 走 `client.getMediaManager().getDownloadUrl(mxc,{useAuthentication:true})`（MSC3916 兜底正确）；`/upload/token` 不提供 `downloadUrl`，前端若依赖该字段则拿不到（并入 H-3） |
| **超时/异常** | `HttpClient` 30s 超时 + 外部 signal 合并正确；扩展端点与 SDK 通道无应用级超时（M-2）。错误归一化 `createMatrixTransportError` 质量较高（errcode/retryAfterMs/status 齐全），但上层大量 catch 后返回空值（M-3） |
| **重复提交** | 好友请求实际不会重复（服务端 pending 唯一性），但幂等键契约是假的（M-6） |
