逐一读完方法清单后，必须修正初判——**这 4 个文件虽然都超千行，但问题性质完全不同，需要四种不同的药方**：

| 服务 | 行数 | 真实病因 | 严重度 |
| :--- | :--- | :--- | :--- |
| AdminFacadeService | 1062 | **虚胖**——已是 facade，千行全是薄委托 | 🟢 低（可缓） |
| MatrixSpaceService | 1138 | **双轨实现**——SDK 与 REST API 两套平行方法共存 | 🔴 高 |

## 一、AdminFacadeService（1062 行）—— 虚胖，非病灶

### 现状
`admin/` 目录已有 **18 个专职子服务**（ServerService / UserService / RoomService / FederationService / ReportService / SecurityService / QuotaService…），facade 方法全部是单行委托：

```ts
async getServerStats(): Promise<ServerStats> {
  return this.server.getServerStats()
}
```

facade 的真正价值只有两处：
1. `verifyServerSidePermission()` —— 服务端权限二次校验（L125），`sdkAdmin()` 入口统一拦截（L189）；
2. `adminRequest()` —— 统一的 Synapse Admin REST 通道（L206）。

### 诊断结论
这是**健康的 facade 模式**，行数来自委托数量而非职责过载。组件直连子服务会绕过权限闸门，所以 facade 必须保留。

### 建议（P2，不急）
- 保持 facade 作为唯一入口与权限闸门；
- 委托方法可按域拆为多个 mixin/子 facade（`AdminUserFacade` / `AdminRoomFacade`…）仅当行数继续增长时再做；
- 真正的改进点：给薄委托加 `@deprecated` 之外的防腐措施——CI 脚本检查"组件不得 import admin/ 子服务"（扩展现有 `check:sdk-boundary` 即可）。

**结论：从 P0 降级为 P2。**

## 二、MatrixSpaceService（1138 行）—— 双轨并行实现 🔴

### 现状
类内存在 **7 组以上 SDK / REST 平行方法**：

| SDK 轨 | REST 轨（ViaApi） |
| :--- | :--- |
| `getSpaceRooms` (L612) | `getSpaceRoomsViaApi` (L650) |
| `searchSpaces` (L519) | `searchSpacesViaApi` (L929) |
| `getUserSpaces` (L549) | `getUserSpacesViaApi` (L968) |
| `getRoomParentSpaces` (L493) | `getRoomParentSpacesViaApi` (L987) |
| `getSpaceMembers` (L273) | `getSpaceMembersViaApi` (L908) |

另有层级/摘要三胞胎：`getSpaceSummary` (L723) / `getSpaceHierarchy` (L750) / `getSpaceSummaryWithChildren` (L830) / `getSpaceHierarchyPublic` (L1057)。

### 病因
SDK 能力不足时用 REST 补位是合理的，但**两套入口混在一个类里**，调用方靠命名约定（`ViaApi` 后缀）猜测该用哪个，没有统一的能力探测与回退策略。

### 拆分方案

```
room/space/
├── SpaceCrudService.ts        # createSpace/getSpace/updateSpace/deleteSpace/join/leave/invite
├── SpaceHierarchyService.ts   # children 增删、getSpaceChildren、tree path、summary/hierarchy 四合一
├── SpaceQueryService.ts       # 搜索与用户空间列表（对外的唯一查询入口）
└── internal/
    ├── SpaceSdkGateway.ts     # SDK 轨实现（私有）
    └── SpaceApiGateway.ts     # REST 轨实现（私有）
```

**关键设计**：对外只暴露 `SpaceQueryService` 等 3 个服务；`ViaApi` 后缀从公共 API 消失，改为网关层内部能力探测（参考现有 `EndpointCapabilityService`）：

```ts
// SpaceQueryService 内部
async getSpaceRooms(spaceId: string) {
  return this.capability.supports('spaceHierarchy')
    ? this.sdkGateway.getSpaceRooms(spaceId)
    : this.apiGateway.getSpaceRooms(spaceId)
}
```

### 迁移步骤
1. 新建 `room/space/` 目录与两个 Gateway，纯搬运不改逻辑（facade 签名保持）；
2. 原 `MatrixSpaceService` 改为继承/组合三个子服务的兼容层，标 `@deprecated`；
3. 调用方分批切换到新服务（`grep -rl MatrixSpaceService src --include='*.vue'` 统计约 N 处）；
4. 全量切换后删除旧类。预计 3-4 天。

## 三、MatrixCryptoService（1096 行）—— 与既有拆分重叠 🔴

### 现状
`crypto/` 目录**已经拆得很好**：`MatrixKeyBackupService` / `MatrixVerificationService` / `MatrixE2EEBootstrapService` / `MatrixAttachmentEncryptionService` / `CryptoHealthMonitor` 都在。

但 `MatrixCryptoService` 仍然内含 5 坨职责：

| 职责块 | 方法区间 | 行数估算 | 与既有服务关系 |
| :--- | :--- | :--- | :--- |
| 设备验证 | L179-L259 | ~80 | ⚠️ 与 MatrixVerificationService 重叠 |
| 密钥备份 CRUD | L594-L900 | **~300** | ⚠️ 与 MatrixKeyBackupService 严重重叠 |
| SAS 验证流 | L902-L1000+ | ~100 | ⚠️ 与 MatrixVerificationService 重叠 |
| 密钥上传/查询/认领 | L455-L537 | ~80 | crypto 核心，保留 |
| 房间加解密控制 | L409-L428 | ~20 | 与 MatrixEncryptionService 边界模糊 |

### 病因
典型的"拆分烂尾"：新服务建了，旧类的方法没迁完，两条路都活着。

### 拆分方案（续完烂尾工程，而非新拆）
1. **密钥备份 CRUD 300 行 → 并入 `MatrixKeyBackupService`**（最大的一块，含 backup version/room keys/session key 三级 CRUD + recover/export/import）；
2. **设备验证 + SAS 流 → 并入 `MatrixVerificationService`**；
3. 剩余 `initializeCrypto` / `uploadKeys` / `queryKeys` / `claimKeys` / `sendToDevice` 保留为瘦身后的 CryptoCore（预计 300 行以内）；
4. 重叠方法先 diff 两侧实现差异，以测试更多的为准，另一侧 `@deprecated` 一个迭代后删除。

**注意**：加密代码迁移必须用既有测试护航——迁移前先把 `crypto/__tests__` 跑绿做基线，每迁一组方法跑一次。预计 3-5 天。

## 四、SynapseRustExtensionsService（1069 行）—— 杂物抽屉 🔴

### 现状
一个类装了 **8 个互不相关的域**：

| 域 | 方法 | 行数估算 |
| :--- | :--- | :--- |
| 好友关系 | getFriends / sendFriendRequest / accept / decline / note… | ~250 |
| 私聊 DM | createPrivateDm / getDmRoom / createPrivateChat | ~80 |
| 阅后即焚 + 防截图 | burn 系列 + antiScreenshot 系列 | ~90 |
| 邀请名单 | blocklist / allowlist | ~60 |
| 置顶事件 | sticky 系列 | ~50 |
| 房间摘要 | summary 系列 5 个方法 | ~90 |
| 验证码 | captcha 系列 3 个方法 | ~60 |
| 第三方协议 | thirdparty 系列 | ~50 |

### 病因
`synapse-rust` 私有扩展端点全部塞进一个"Extensions"类——命名即纵容，新端点来了顺手就加。

### 拆分方案
**按域就地解散，各归其位**（大部分目标目录已存在）：

| 域 | 去向 | 备注 |
| :--- | :--- | :--- |
| 好友关系 | `friends/MatrixFriendService`（已有 976 行，迁移时一并按 P1 拆分） | 合并两套好友实现，消除重复 |
| 私聊 DM | `room/MatrixDirectMessageService`（已存在） | |
| 阅后即焚 | `messaging/MatrixBurnAfterReadService`（已存在） | |
| 邀请名单/置顶/房间摘要 | `room/` 下新建 `RoomInviteListService` / 并入现有 pins/summary 服务 | |
| 验证码/第三方协议 | 新建 `auth/MatrixCaptchaService` + `MatrixThirdpartyService` | |
| 端点探测 | `ensureInitialized` + `checkEndpointAvailability` 下沉到 `EndpointCapabilityService` | 这是该类的隐藏公共基础设施 |

迁移后 `SynapseRustExtensionsService` 应**整个删除**，不留空壳。预计 3-4 天。

## 五、修正后的 P0 排序

| 优先级 | 项 | 理由 | 工时 |
| :--- | :--- | :--- | :--- |
| ~~P0~~ → **P2** | AdminFacadeService | 已是健康 facade，只需 CI 防腐 | 0.5 天 |

三个 P0 共计约 9-13 天，可串行也可按域并行（三个文件几乎无交叉依赖）。

**通用迁移纪律**（三个服务都适用）：
1. 迁移前跑 `pnpm vitest run <对应测试目录>` 做绿基线；
2. 纯搬运先行，逻辑改动分开提交（commitlint scope 分别用 `service`）；
3. 旧类改兼容层 + `@deprecated`，给调用方一个迭代的切换窗口；
4. 验收基线不变：`vue-tsc --noEmit` 0 错 + vitest 全绿（排除已知 15 个失败套件）+ biome clean。
