## 四、本轮发现的问题（按归属）

### 4.1 后端

#### BE-3 幂等键仍未生效（中）

- **问题描述**：`POST /_matrix/vendor/v1/friends/request` 不识别 `Idempotency-Key`，也不把 `X-Request-Id` 当幂等键。用**同一个** `Idempotency-Key` 打**两个不同目标**，得到两个不同的 `request_id`（实测 `92 → 93`）。
- **复现步骤**：
  1. 注册用户 A、C、D；
  2. 以 A 的 token 发 `POST /friends/request` → `{"user_id": C, "Idempotency-Key": "K"}`，记 `request_id=92`；
  3. 用**同一个** `K` 再发 `{"user_id": D}` → 返回 `request_id=93`（若键生效应回 92 或明确 `409`）。
- **影响程度**：中。当前「同目标重复请求」靠 `pending` 唯一性兜底（实测重复请求返回同一 id），所以**暂无重复数据**；但这是业务约束在兜底，不是幂等语义。一旦允许重复申请、或把同一模式套到「发消息/建群/转账类」写操作上，重发即产生重复副作用。
- **具体不足**：`resolve_request_id()` 只读 `x-request-id` 且仅用于日志/追踪，未参与去重；无 `(user_id, key)` 去重表。

#### BE-11 `versions` 未声明 `io.hula.friends`（低）

- **问题描述**：`GET /_matrix/client/versions` 的 `unstable_features` 里没有 `io.hula.friends`，只有 `GET /_matrix/client/v3/capabilities` 里有。
- **影响程度**：低。前端 `MatrixCapabilityService` 会合并两个来源，因此不影响功能；但若 `/capabilities` 请求失败，就会退化为 HEAD 探测（多一次请求、且在部分 WebView 下 HEAD 不可靠）。
- **具体不足**：同一能力标志在两个端点声明不一致，客户端需要读两处才能判定。

### 4.2 前端

#### FE-1 契约测试只校验路径，不校验字段与错误码（中，**已修**）

- **问题描述**：`src/services/matrix/paths/__tests__/friends.contract.test.ts` 仅断言「前端路径常量能在 SDK route-table 中匹配」。响应字段、请求体、状态码/errcode 全无契约守护 —— 上一轮 4 类字段错配与 2 类错误码错配正是由此漏网。
- **影响程度**：中（缺陷检出能力不足，而非线上故障）。
- **已做改动**（2026-11-05 第三轮）：
  1. 新增 `src/services/performance/__tests__/UploadService.contract.test.ts` —— 用**实测响应**（`6.3.0-7914e4630`）作夹具，锁住 `upload/token` 的 snake→camel 归一、`upload_method=POST` 判定、鉴权头、404/无 token 降级、`provider` 枚举归一；
  2. `src/common/__tests__/errors.test.ts` 增加「errcode → AppError.kind」参数化契约表（10 个实测评测码）+ 两条回归用例。
- **副产品**：该组用例当场发现并修复一处前端缺陷 —— `M_UNAUTHORIZED` 虽已归 `auth`，但 `recoverable` 白名单未含它，UI 会把它当成「不可恢复的权限错误」而非登录引导（详见 §9.2）。

#### FE-2 好友列表翻页为串行请求（低，**已修**）

- **问题描述**：`getFriends()` 按 `limit=200` 串行跟随 `next_batch`，最多 10 页（2000 人）。好友规模大时首屏要等 N 次 RTT。
- **影响程度**：低（本机数据量小，未实测放大效应）。
- **根因修正**：游标分页是**串行**的（第 N 页的 `next_batch` 依赖第 N 页响应），因此「并发预取后续页」不可行；真正的浪费在**重复读取**——启动阶段 `App.vue` 两处 + 通讯录 store 各自调用 `getFriends()`，乘上页数即为总请求数。
- **已做改动**：
  1. `MatrixFriendService.getFriends()` 加**单飞 + 15s TTL 缓存**（`friendsCache` / `friendsInFlight`）；
  2. 新增代际失效：`friendEvents.bumpFriendsGeneration()`，`MatrixFriendOperations` 在 8 个写操作成功点调用，`stop()` / `invalidateFriendsCache()` 亦清空；
  3. 4 条单测覆盖「缓存命中 / 并发合并 / 代际失效 / 显式失效」，并用变异自证（把 TTL 改 0 → 缓存用例立刻 FAIL，其余仍绿）。

#### FE-3 上传忽略后端 `download_url_prefix`（中，**本轮已修**）

- **问题描述**：后端 `upload/token` 已返回 `download_url_prefix`（`/_matrix/client/v1/media/download/<server>/`），前端此前只用 mxc→http 解析；SDK 未就绪时解析返回 `null`，会把 `mxc://` 原样写进消息体（webview 无法加载）。
- **已做改动**：`UploadService` 解析并透出 `downloadUrlPrefix`；`uploadTransports.uploadFileViaMatrix` 改为「prefix + mediaId 优先 → mxc 解析 → 原样 mxc」三级回退；`upload_method === 'POST'` 显式判定为原生通道。
- **验证**：`vue-tsc` 0 错、biome 干净、`check-file-size` OK；契约层断言 `upload/token 提供 download_url_prefix` 通过。

### 4.3 SDK

#### SDK-1 `mxcUrlToHttp` 挂在 ProfileManager 而非 MatrixClient（低，**已修**，见 §11）

- **问题描述**：SDK fork 把 `mxcUrlToHttp` 放在 `ProfileManager` 上，`MatrixClient` 本体没有；client 未初始化或 manager 扩展未装载时解析返回 `null`。
- **影响程度**：低。本仓已收敛到 `media/mxcUrl.ts::resolveMxcToHttp`（单一事实源），且本轮改为优先使用后端下发的 `download_url_prefix`，不再强依赖解析成功。
- **具体不足**：SDK API 位置与上游不一致，新调用点容易写成 `client.mxcUrlToHttp(...)` 幻影方法（历史已踩过）。

## 八、结论与后续建议

**结论**：在当前构建下，前后端在**认证、好友、私聊、消息、媒体、错误语义、CORS** 七个维度全部对齐，HIGH 级失败为 0；唯一残留的实质性缺陷是后端幂等键不生效（BE-3），且当前有业务唯一性兜底、不产生脏数据。上一轮报告中的 6 项后端缺陷已在新构建中修复，说明该文档的「后端清单」需要按构建版本维护。

**建议优先级**：

1. **P1 后端**：实现 `Idempotency-Key`（或明确废弃该头并在文档写明「仅保证同目标 pending 唯一」），并补一条「同 key 打不同目标应复用/409」的集成测试。
2. **P1 前端**：把 `contract-smoke.mjs` 纳入 CI 的可选任务（真实后端可用时执行），补上「字段/错误码」这一层契约守护（FE-1）。
3. **P2 后端**：把 `io.hula.friends` 同步声明到 `versions.unstable_features`，消除双来源不一致（BE-11）。
4. **P2 前端**：好友列表改「首页 + 加载更多」，避免大账号首屏串行 N 次 RTT（FE-2）。
5. **P3 文档**：删除或重写已被新构建修复的条目，并在后端清单顶部固定写明「适用镜像 tag / 容器启动时间」，防止再次出现「照旧文档修已修的问题」。

### 9.2 修复过程中新发现并修正的前端缺陷

**`M_UNAUTHORIZED` 的 `recoverable` 判定缺失（中）**

- **现象**：`toAppError` 已把 `M_UNAUTHORIZED` 归为 `kind: 'auth'`，但 `recoverable` 只在 `M_UNKNOWN_TOKEN` / `M_MISSING_TOKEN` 时为 `true` ⇒ 该码落到 `recoverable: false`。

- **定位**：`src/common/errors.ts`（`AUTH_ERRCODES` 分支）。
- **修正**：`recoverable` 白名单加入 `M_UNAUTHORIZED`；新增回归用例锁住。
- **验证**：修改前该用例 FAIL（`expected false to be true`），修改后 PASS —— 属真实缺陷，不是纸面问题。

### 10.2 改动

| 层 | 改动 |
|---|---|
| 扩展服务 | `SynapseFriendExtensionService.getFriends()` 的 catch 不再无条件 `return []`：仅「客户端未初始化/未就绪」这一临时态返回空，其余**抛出** |

| Store | `loadContacts()` 在拿到 `[]` 时检查信号：有信号 → `setFriendListError('contacts', …)` 并提前返回（UI 进 `error` 态，可点重试）；无信号 → 正常走空态 |
| UI | **零改动**（复用既有 `ErrorState` + 重试） |

**语义保证**：`error` 只在「读失败且无数据」时出现；已有列表数据时失败不打扰用户（静默降级，保留旧列表）。

### 10.3 顺带修掉的 N+1（通讯录首屏）

`loadContacts()` 在遍历 DM 房间时逐条 `await matrixPresenceService.getPresence(partnerId)`
只为判断「用户是否已删除」，而紧接着又用 `getBatchPresence(candidateUserIds)` 对**同一批用户**
做同样的事。即：DM 有 N 个就多 N 次串行往返，且结论完全重复。

改法：删除逐条调用，统一交给批量校验（批量失败时保留原列表，与原「逐条失败则保留」的 fail-open 语义一致）。

### 11.1 本轮最重要的一件事：上一轮的 M-3 是**纸面修复**

## 十三、第七轮：F-6 好友列表真分页（首页 + 逐页补齐）

> 目标：好友超过一页（后端单页上限 200）时，首屏不再等完所有页。
> 结论：**UI 零改动**，只把「数据怎么到 store」从「一次给全量」改成「逐页流式」。

### 13.1 分层

| 层 | 改动 |
|---|---|
| 扩展服务 `SynapseFriendExtensionService` | 拆出 `getFriendsPage(from?)`：**单页**读取，返回 `{ friends, nextBatch }`。失败语义与全量读一致（真实失败**抛出**、「客户端未就绪」返回空页）；游标原地打转（`next_batch === from`）归一为 `null`，否则外层会死循环 |
| `getFriends()` | 改为循环调用 `getFriendsPage`（行为不变：仍是一次给全量、仍带 `user_id` 去重、仍有 10 页上限） |
| `friendUtils.streamFriendPages(loadPage, maxPages=10)` | 纯函数式逐页产出器，`loadPage` 由调用方注入（避免 utils 直接依赖扩展服务形成循环导入） |
| 门面 | `export const streamFriendsPages = () => streamFriendPages(ext.getFriendsPage)`（一行绑定，不新增方法） |
| store `loadContacts()` | `for await` 消费分页：首页一到就把 `isLoading` 置 false，后续页**增量合并**进同一 `contactsList` |

### 13.2 两个必须知道的坑（都是本轮实际踩到的）

**① `mergeContactListPreservingPresence(prev, next)` 不是「追加」**
它的实现是 `next.map(...)` —— 用 `next` 重建列表、只从 `prev` 继承在线态。
第一版直接 `merge(list, pageContacts)`，结果**后一页把前一页顶掉**：分页测试断言
`['@a','@b']` 实际得到 `['@b']`。修法是自己拼 union 并按 `userId` 去重，再交给 merge 保留在线态。

**② `src/services/matrix` 有「文件数不得增长」守卫**
新增 `friends/friendPaging.ts` 后 `check:matrix-layering` 立刻红（`241 > 基线 240`）。
守卫的意图是「新服务按域落位，不要在本层堆文件」，而分页只是一个纯函数——
所以并入 `friendUtils.ts`（157→197 行），门面里只留一行绑定。

**③ DM-only 联系人要等分页结束再补**
「只有会话、不是好友」的联系人原来和好友一起建。分页后如果首屏就补，
第 2 页里那些**本来是好友**的人会先被建成「非好友」条目（`friendStatus: undefined`），
后续 merge 不会升级状态。因此改成末页之后再补，并按 `userId` 排除已存在的。

### 13.3 语义变化（写清楚，免得以后被当 bug）

`contactsList` 在「补齐窗口」内是**部分**列表，因此 `isFriend()` 类判断可能漏判。
但旧行为是「整段加载期间列表**全空**」—— 部分列表严格优于空列表，**不是回归**。
这条已写进 `loadContacts` 的注释，配套的 store 测试也锁了：
- 首屏失败且无数据 → 错误态（可重试）；
- 成功但 0 个好友 → 空态；
- 已有部分数据后失败 → **静默降级**，保留已渲染列表（不打成错误态）。

```bash
TAURI_ENV_PLATFORM=android npx vite optimize

#    让依赖图一次性被发现，之后再跑用例就不会中途重新优化
```

### 18.1 症状与定位方法

### 18.2 根因：setup store 里的对象字面量 getter 是「快照」

`src/stores/domains/chat/chat/message.ts` 用

```ts
return {
  get sessionList() { return sessionStore.sessionList },   // ← Pinia 在 store 创建时求值一次
  ...
}
```

转发另一个 store。setup store 的返回值会被 Pinia 逐键读取，`get` 因此**立即执行**，
拿到的是「当时的数组引用」；而 `sessionStore.getSessionList()` 用的是
`sessionList.value = uniqBy(...)` **整体替换**（`session.ts:263`），快照从此指向旧数组。
于是所有经 `chatStore` 读会话的路径都看不到新数据：

- 移动端列表 computed（`useMobileSessionList.ts:37`）没有响应式依赖 ⇒ 恒空；
- `global.ts:259` 全局未读角标恒 0；
- `MobileLayout.vue:183` 查不到会话 ⇒ 新消息不响提示音；
- `useChatSession.ts:60,71` 删除会话后 index 恒 -1 ⇒ 不自动选下一个。

桌面端没暴露是因为它走 `toRef(sessionStore, 'sessionList')`（`useSessionListState.ts:33`）。

### 18.3 修复（P0）

`message.ts` 三个转发改 `computed`（`syncLoading` 用可写 computed，避免 setter 落在非 state 键上）：

```ts
const sessionListRef = computed(() => sessionStore.sessionList)
const syncLoadingRef = computed({ get: () => sessionStore.syncLoading, set: (v) => { sessionStore.syncLoading = v } })
return { sessionList: sessionListRef, sessionOptions: sessionOptionsRef, syncLoading: syncLoadingRef, ... }
```

## 十九、P1/P3 收口：拉取时序、四态空态、滚动位置（2026-11-06 凌晨）

### 19.1 P1-a：`getSessionList` 改 single-flight

**缺陷**：`if (sessionOptions.isLoading) return` 把并发调用**静默短路** —— 后到者拿到一个已 resolve 的
Promise，`await` 完以为列表已就绪，实际请求还在路上。移动端首屏正好踩这个窗口
（bootstrap 在拉 → 页面 `onMounted` 的拉取被吞 → 列表空到用户手动下拉）。

**修法**：拆出 `fetchSessionList()`，`getSessionList` 用 `inFlight: Promise | null` 做 single-flight，
`isLoading` / `loadError` / `unreadReady` 在**发起时同步**置位，`finally` 里统一复位。

**守卫**（`sessionListSingleFlight.test.ts`，4 例，真实 store）：
并发只发一次请求 / **并发调用不得提前完成** / 结束后可再次请求 / 失败写 `loadError` 且复位。

> 变异自证：把实现改回 `if (isLoading) return` + `async` ⇒ 「不得提前完成」一例立刻红
> （`expected true to be false`）。
> 踩坑：最初用 `await Promise.resolve()` 断言，只让出一拍微任务，抓不到；改 `flushPromises()` 才稳定。

### 19.2 P1-b：同步事件驱动兜底刷新（移动端）

移动端此前只在「页面挂载 + 下拉刷新」拉列表；sync 事件只刷联系人。现在 `useMobileMessageActions`
在 `PREPARED` 时刷会话，`SYNCING` 且列表为空时也刷一次（3s 节流），覆盖「首屏拉取早于
sliding sync 落库」的窗口。

### 19.3 P3-a：四态空态（loading / error / empty / list）

判定抽成纯函数 `resolveSessionListState({count, isLoading, loadError})`（`useMobileSessionList.ts`），
组件按结果渲染四支：

- **有数据恒为 list** —— 下拉刷新期间不能把已有列表换成骨架，也不能被刷新失败遮挡；
- 空 + 失败 → `session-list-error`：显示「会话加载失败」+ **原始错误原因** + 重试按钮；
- 空 + 加载中 → `session-list-loading`（「加载中」），不再显示「暂无会话」；
- 空 + 未加载 + 无错误 → 真「暂无会话」。

### 19.4 错误语义：把「故障」与「0 条会话」分开（本轮唯一的产品语义变更）

排查失败态时发现：`MatrixSessionService.getSessionList()` 整体 `catch` 后返回 `[]`，
`MatrixFriendService.getSpecialFriends()` 同样吞错返回 `[]` ⇒ store 的 `loadError` 在生产里

| 情况 | 行为 |

| 未登录 / client 未初始化 | 返回 `[]`（真的没有会话，不是故障） |
| 执行期异常（`getRooms` / 状态解析抛错） | **抛出**，由 store 捕获写 `loadError`，UI 展示失败态 + 重试 |
| `getDMRooms` 失败 | 仍降级（沿用 `getDMRooms(false)` 的既有语义），不影响列表其余部分 |

守卫：`MatrixSessionService.test.ts` 新增 2 例（执行期异常必须 rejects；client 未初始化 resolves `[]`），
原 11 例（含「DM 查询失败仍出列表」）保持通过。
变异：把 `throw err` 改回 `return []` ⇒ 新用例立刻红。
