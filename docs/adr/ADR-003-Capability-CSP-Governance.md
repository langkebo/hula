# ADR-003: Capability 与 CSP 变更审计流程

## 状态

- [x] 提议
- [ ] 接受
- [ ] 弃用
- [ ] 已取代

## 背景

`hula` 是一个基于 Tauri 的跨端应用，其安全性高度依赖于：
1. **Tauri Capabilities**: 控制前端对 Rust 侧 API（文件系统、网络、Shell 等）的访问权限。
2. **Content Security Policy (CSP)**: 防止 XSS 攻击和非法数据外泄。

随着功能的迭代，开发者可能会为了方便而放开过大的权限（如 `fs:**` 或 `unsafe-inline`），这会显著增加攻击面。目前缺乏一个明确的评审流程来约束这些高危配置的变更。

## 决策

建立严格的 **Capability & CSP 变更审计台账** 制度，要求所有相关变更必须满足以下条件：

### 1. 变更触发条件
凡是修改以下文件的 PR，必须标记为 `Security Critical`：
- `src-tauri/capabilities/*.json`
- `src-tauri/tauri.conf.json` (涉及 `csp` 字段)

### 2. 审计流程
- **PR 描述要求**: 必须说明放开权限的**必要性**、**影响范围**及**缓解措施**。
- **强制 Review**: 必须由至少一名具有安全背景的架构师（或安全负责人）进行二审。
- **ADR 关联**: 若变更涉及重大权限放开（如允许执行任意 Shell 指令、放开 `unsafe-eval` 等），必须同步提交一份关联的 ADR 说明决策背景。

### 3. 自动化门禁
- **CI 检查**: 引入静态分析脚本（如 `check:v-html` 的扩展版本），检测是否引入了已知的弱安全配置。
- **审计记录**: 在 `docs/audit/capabilities-log.md` 维护一份权限变更台账，记录变更时间、PR 链接及批准人。

## 后果

### 正面影响
- 显著降低因权限配置不当导致的安全漏洞风险。
- 强化了团队的安全意识，使每一项权限放开都有据可查。
- 符合生产级 IM 应用的合规性要求。

### 负面影响
- 稍微增加了高危 PR 的合入耗时（需要额外 Review）。
- 增加了文档维护成本。
