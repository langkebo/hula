## 1. 执行原则与技能组合

### 1.1 三套技能体系的定位

| 技能体系 | 用途 | 在本项目中的角色 |
|---|---|---|
| **gstack** | 规划/评审/QA/发布/调试的完整"铁三角"工作流（plan → review → ship） | 每阶段结束时做 `/review` 代码评审、`/qa` 界面验证、`/ship` 合并 |
| **Superpowers** | 深度规划、系统设计、TDD 红线 | 用 `writing-plans` 写实施方案、`brainstorming` 收敛设计、`codebase-design` 定模块边界 |
| **MattPocock Skills** | 执行纪律、子代理、验证、代码评审 | 用 `subagent-driven-development` 分任务执行、`verification-before-completion` 做上证据、`requesting/receiving-code-review` 做质量门禁 |

### 1.2 组合工作流（每一阶段统一循环）

```
1. brainstorming/grilling   → 澄清需求与取舍（收敛范围，YAGNI）
2. writing-plans            → 把阶段拆成可执行任务（含验收标准）
3. using-git-worktrees      → 在隔离工作区执行，不污染主分支
4. subagent-driven-development → 每任务独立子代理 + 两阶段评审
5. verification-before-completion → 先跑命令取证，再宣布完成
6. requesting-code-review / gstack:/review → 合并前质量门禁
7. gstack:/qa → 浏览器/运行时验证界面
8. gstack:/ship → 合并收尾
```

### 1.3 全局纪律（贯穿所有任务）

- **YAGNI**：只做文档明确要求或审计确认有价值的事，不做"顺手优化"。
- **TDD 红线**：涉及逻辑/状态/交互的功能改动，先写失败测试，再实现，再验证。
- **证据优先**：任何"完成"声明前必须提交 `vue-tsc --noEmit`、`pnpm test:run`、`pnpm check` 的实际输出。
- **小步提交**：每任务一个 Conventional Commit，避免大而全的提交。
- **不破坏 SDK 边界**：所有 Matrix 操作走 `src/services/matrix/` 服务层，禁止组件直连 SDK。

## 2. 阶段 0：项目规则优化

**目标**：先让 `AGENTS.md`（即 `CLAUDE.md`）成为真正可执行的"工程宪法"，把重构需要的纪律、技能路由、验收命令固化进规则，再开始动代码。

### 2.1 现状问题（审计结论）

现有 `AGENTS.md` 内容全面但存在以下不足以支撑本次重构：

| # | 问题 | 影响 |
|---|---|---|
| 0.1 | 缺少 **技能路由规则**（gstack/SSW/MP 的触发条件） | 代理不知道何时调用哪个技能，执行依赖人工 |
| 0.2 | 缺少 **UI 设计系统的强制规范**（token 唯一来源、禁止硬编码、SVG-only 图标） | 新旧 token 混用、图标用 div 渲染的复发源 |
| 0.3 | 缺少 **重构特有的验收命令清单**（`pnpm check:ratchet`、`check:doc-coverage`、`quality:no-raw-fetch` 等） | 代理不知道有哪些自动化守护 |
| 0.4 | **组件体量红线**未定义（如 >800 行必须拆分） | 超大组件持续累积 |
| 0.5 | **isMobile() 双轨策略**未明确 | 桌面/移动端实现割裂，无法判断该走哪条路 |
| 0.6 | 缺少 **"接受评审"流程**（receiving-code-review 的纪律） | 反馈被盲目接受或拒绝 |

### 2.2 优化方案

> **执行技能**: `writing-plans`（先规划 AGENTS.md 怎么改）+ `editing`（直接编辑）
> **验收标准**: 修改后 `AGENTS.md` 增加以下章节，且 `pnpm check` 不受影响（规则文件不参与编译）。

**Task 0.1 — 新增 `## Skill routing` 章节**

在 `AGENTS.md` 末尾追加 MattPocock/gstack 技能路由规则，与现有 `## 工作流` 呼应：

```markdown
## Skill routing

当用户请求匹配某个技能时，先通过 Skill 工具调用，再谈实现。

关键路由规则：
- 任何重构/新功能动手前 → writing-plans（先写方案）
- 设计取舍/范围收敛 → brainstorming / grilling
- 写实现代码前 → test-driven-development（先写失败测试）
- 执行多任务计划 → subagent-driven-development 或 executing-plans
- 声称"完成/修复/通过"前 → verification-before-completion（先跑命令取证）
- 收到评审反馈 → receiving-code-review（先核实再采纳，不盲从）
- 请人评审 → requesting-code-review（见下方质量门禁）
- 需要隔离工作区 → using-git-worktrees
- 出现 bug → systematic-debugging（先诊断再修）
```

**Task 0.2 — 新增 `## UI 设计系统强制规范` 章节**

在 `## CSS Variables & UnoCSS` 之后追加：

```markdown
## UI 设计系统强制规范

- 设计 token 唯一来源：`src/styles/css/design-tokens.css`（权威），`variable.scss` 仅作旧别名层。
- 禁止硬编码颜色：新代码一律使用 `--tjg-*` token；不得出现 `#xxx`/`rgb()`/`rgba()` 新增值。
- 图标必须使用 SVG：禁止 div-based 图标；图标用 `<svg>` / `<use>` / Iconify，线宽 1.5px。
- 组件体量红线：任何 `.vue` 文件超过 800 行必须拆分（参照 workbench 层样板）。
- 桌面/移动端策略：优先补全 `src/mobile/` 独立实现；`isMobile()` 内联分支只允许在临界候补组件，禁止新增。
- 动效必须尊重 `prefers-reduced-motion`。
- 语义色/状态色用 token（`--tjg-status-*`），不依赖颜色传达状态。
```

**Task 0.3 — 新增 `## 重构验收命令` 章节**

在 `## 关键命令` 表格后追加守门命令清单：

```markdown
## 重构验收命令（每次改动后必须跑）

| 命令 | 用途 |
| :--- | :--- |
| `pnpm vue-tsc --noEmit` | 类型检查，必须 0 错误 |
| `pnpm test:run` | 单元测试全部通过 |
| `pnpm check:ratchet` | 硬编码颜色/样式守护（ratchet） |
| `pnpm check:doc-coverage` | 文档覆盖守护 |
| `pnpm check:sdk-boundary` | SDK 边界守护 |
| `pnpm quality:no-raw-fetch` | 禁止直接 fetch 守护 |
| `pnpm check` | Biome lint + i18n 检查 |
| `pnpm storybook` | 视觉回归（可选，涉及组件时） |
```

**Task 0.4 — 提交**

```bash
git add AGENTS.md
git commit -m "docs: 重构 AGENTS.md，固化技能路由与UI设计系统规范"
```

**验收标准**:
- [ ] `AGENTS.md` 含上述 4 个新章节
- [ ] `git log` 显示本次提交
- [ ] `pnpm check` 通过（若无调用规则文件报错）

## 5. 全局约束与验收基线

**Global Constraints**（所有任务继承）：

- 不得引入新依赖（除非文档明确要求）。
- 不得改变现有交互行为（拖拽、视图切换、响应式断点、消息收发）。
- Matrix 操作必须走 `src/services/matrix/` 服务层，禁止组件直连 SDK。
- 不得破坏 `matrixSdk.worker.ts` 的主线程 <50ms 约束。
- 图标必须 SVG；禁止 div-based 图标。
- 禁止硬编码颜色（用 `--tjg-*` token）。
- 遵循项目 Biome/Prettier 规范，Conventional Commits。

**全局验收命令（每任务完成后跑）**：

```bash
pnpm vue-tsc --noEmit
pnpm test:run
pnpm check
pnpm check:ratchet
pnpm check:sdk-boundary
pnpm quality:no-raw-fetch
```

**验收基线（最小）**：
- `vue-tsc --noEmit` 0 错误
- `pnpm test:run` 0 失败
- `pnpm check` 0 lint 错误
- `pnpm check:ratchet` 通过（无新增硬编码）

## 6. 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| 超大组件拆分引入行为回归 | 每任务先写渲染回归测试；使用 worktree 隔离 | 回退该提交；`git revert` |

| 私密聊天集成引入安全风险 | 截屏检测功能需充分测试；防截屏不影响正常使用 | 功能开关降级 |

## 7. TDD 执行指南

### 7.1 TDD 循环（每个任务统一执行）

```
RED    → 先写失败测试（描述期望行为）
GREEN  → 最小实现让测试通过
REFACTOR → 优化代码，测试仍通过
VERIFY → 跑全局验收命令取证
COMMIT → Conventional Commit 提交
```

### 7.2 技能调用顺序

```
1. Skill: writing-plans        → 将任务拆成可执行步骤
2. Skill: using-git-worktrees  → 创建隔离工作区
3. Skill: tdd                  → RED → GREEN → REFACTOR 循环
4. Skill: verification-before-completion → 跑命令取证
5. Skill: requesting-code-review → 请求代码评审
6. Skill: receiving-code-review  → 处理评审反馈
7. gstack:/qa                  → 界面验证
8. gstack:/ship                → 合并收尾
```

### 7.3 测试策略

| 改动类型 | 测试方式 | 示例 |
|---|---|---|
| Token 定义 | CSS 解析测试 | 验证 `--tjg-color-primary-50` 存在且值正确 |
| 组件拆分 | 渲染回归测试 | 拆分前后渲染输出一致 |
| 功能集成 | 行为测试 | 私密模式激活时 `PrivateModeBanner` 可见 |
| 逻辑修复 | 单元测试 | `usePrivacyProtection` 状态随私密模式变化 |
| UI 样式 | Storybook + 视觉快照 | 私密模式下消息气泡红色背景 |

### 7.4 执行优先级

```
第一批（P0，阻塞修复）:
```
