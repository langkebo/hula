## 三、能否按 §3-1 步骤执行：逐步对照

原步骤：「各自设本地解锁密码 → 登录 → 建加密房 → 互发并比对 SAS」。

| 步骤 | 能否执行 | 实测 |
|---|---|---|
| **0. 两台设备** | ⚠️ 降级 | 组合：**模拟器（A）+ 本机 Chromium（B）**。桌面端可启动但无法驱动 |
| **1. 设本地解锁密码** | ✅ **可 UI 操作** | 冷启动时**会弹**「输入本地解锁密码 / 这台设备无法访问系统密钥库，消息密钥由本地密码保护」，填密码点「解锁」，实测 **2000ms** 通过 |
| **2. 登录** | ✅ | 两端 DOM 事件填表登录成功（点「登录」前需等 ~500ms，Vue `v-model` 下一 tick 才更新） |
| **3. 建加密房** | ✅ | `createRoom` + `initial_state: m.room.encryption` → `algorithm=m.megolm.v1.aes-sha2`，对端 join |
| **4. 发加密消息** | 🟡 **SDK 层已验证，UI 层未覆盖** | `client.sendEvent()` → 服务端 `m.room.encrypted` ✅；UI 合成 Enter 只换行，从未真正发送 |
| **5. 对端解密** | ✅ 单向 | Chromium 解密并渲染出模拟器发出的密文 |
| **6. 比对 SAS** | ❌ 未做 | 服务端只验 to-device 信封（request/ready/key/mac/done 双向全通）；emoji 需两端人工比对 |

### 前置条件（缺一不可）

1. 后端 `8008` 在跑；2. `5210` 有 vite dev server 且 `TAURI_ENV_PLATFORM=android`；
3. `adb reverse 5210/8008`；4. `adb forward 9222`（pid 变则重做）；
5. **两端先过本地解锁**（安全存储在模拟器上不可用，`storageKey` 只能由此派生）；
6. **两端都必须登录过至少一次**（`device_keys` 上报是 E2EE 必要条件）。

## 五、现存问题（本轮判定）

> 分级：P0 阻断交付 / P1 影响主流程或结论可信度 / P2 体验或工程债。

### D5（P1，本轮实证）客户端从不发 `m.room_key_request`，新设备 UTD 无法自愈

- **现象**：新设备打开含历史加密消息的房间 → `isDecryptionFailure()=true`，UI 显示「无法解密这条消息 / 设备上缺少解密所需的密钥，重试可能从备份恢复密钥后成功」。
- **服务端证据**（`to_device_messages`，UTC）：
  ```
  全表 select count(*) where event_type like '%room_key%'  →  0
  近 30 分钟（含本轮 UTD 场景）: m.key.verification.done×1 · m.room.encrypted×1
  ```
  即：**一条 key request 都没有**。`m.room_key_request` 是 to-device 事件，不会出现在房间事件里，只能这样查。
- **影响**：换设备/重装后历史消息永久不可读；「重试」点下去也没有请求可发。
- **口径（按你的要求）**：**前端不自建补发逻辑**。后续真机联调一律用 synapse-rust 侧日志/表确认「客户端有没有发」，以服务端事实为准。
- **下一步**：先查 SDK 侧（`matrix-js-sdk` / `matrix-rust-crypto`）在 UTD 时是否调用 `requestRoomKey`、是否被开关或策略挡住；确认是「SDK 未发」还是「前端包装层吞掉」，再决定改哪一层。
- **验收**：UTD 后 30s 内 `to_device_messages` 出现 `m.room_key_request`（≥1 条）；在线发送方回 `m.forwarded_room_key`；页面自动解密，无需人工点「重试」。

### D4（P1，安全）`/keys/upload` 缺 `signatures` 的 device_keys 被接受并落库

- **现象**：带**错误**签名 → `400 M_BAD_JSON Invalid device key signature`（正确）；**完全不带** `signatures` → `200`，`/keys/query` 能查到该设备（`ed25519` 是伪造串）。
- **缓解**：one-time key 的签名**强制**校验（伪造 → `400 Invalid one-time key signature`），无法据此完成完整 Olm 握手。
- **下一步**：`device_keys.signatures` 缺失时直接 `400`；补 4 条单测（缺签名 / 空签名 / 错用户 / 错设备）。
- **验收**：`scripts/e2ee-device-smoke.mjs` 的「缺少 signatures 的 device_keys 应被拒绝」转 ✅。

### D2（P1）Android 安全存储全链失败 ⇒ 每台设备都必须过本地解锁

- **现象**（logcat 原文）：
  ```
  ERROR crypto: HOME 环境变量未设置，无法保存密钥文件
  WARN  secure_store: Keychain bug detected ... (macOS dev mode ACL issue). Falling back to file storage.
  WARN  secure_store: Cannot determine fallback path for key 'matrix_token_@...'
  ERROR secure_store: Both keychain and fallback failed to store secret
  ```
- **影响**：Android 上文案写成 macOS 语义；fallback 依赖 `HOME`（Android 无此变量）⇒ 两级都失败 ⇒ `storageKey=null` ⇒ crypto fail-closed。
- **本轮补充**：解锁门禁**确实兜住了**（D3 已修正），用户不会被完全卡死，但每台新设备都要多设一次密码。
- **下一步**：Android 走 Keystore/EncryptedSharedPreferences 分支；fallback 路径不依赖 `HOME`；修文案。
- **验收**：Android 上不设解锁也能 crypto 初始化；logcat 不再出现上述 4 条。

### ~~D3（原 P1）本地解锁门禁冷启动不弹窗~~ —— **本轮推翻**

- 第一版结论：`configured=true / unlocked=false` 时无对话框，直接进会话页。
- 本轮实测：从 splashscreen **冷启动会弹**「输入本地解锁密码」，填密码后 2000ms 通过。
- 差异原因（推测，待确认）：第一版是「已在会话页 + `location.reload()`」，走会话恢复路径；本轮是「进程冷启 → splashscreen → login」，走启动门禁路径。**即：门禁挂在登录/启动流程上，会话页刷新路径可能绕过**。
- **下一步**：单独验一条（TC-09：会话页整页刷新），确认该路径是否漏挂。

### D1（原 P0，**降级为「未验证」**）UI 发送入口未被脚本触发

- **现状**：Enter 在该输入框是**换行**；真实发送按钮未定位到；因此「UI 发送是否可用」**没有结论**。
- **下一步**：从 `MsgInput.vue` 的 `@handle-mobile-send` 反查 DOM（移动端发送控件），改用 `element.click()` 或 CDP 真实鼠标事件，再断言服务端出现 `m.room.encrypted`。
- **备注**：第一版观察到的「本房间有 N 台未验证设备」弹窗**真实存在**（文本与按钮都截到过），但它是否真的**阻断**发送仍未验证。

### D6（P2，工程）Tauri 移动端只能走 CDP

- `uiautomator dump` 对 Tauri WebView 返回 **0 个带文本节点**；`System Events` 不可用。
- **下一步**：把 `scripts/cdp-eval.mjs` 固化为移动端 e2e 执行层（封装 `click/fill/assert`），文档写明「Tauri 移动端 = CDP」。

### D7（P2，工程）本轮新增的脚手架保真度陷阱（已写进脚本注释）

1. **JS 合成的 `KeyboardEvent` 不等于真实按键**：`ng-input`/Vant 的发送逻辑不认，Enter 只换行；要真实按键必须走 CDP `Input.dispatchKeyEvent`；
2. **`document.body.innerText` 会把输入框内容当消息**：contenteditable 文本进入 `innerText`，用它判断「消息已渲染」会得到假阳性 —— 应查 `room.getLiveTimeline()` 的事件；
3. 模拟器冷启动先 ANR（Launcher）→ 必须 `force-stop` 重启 app，WebView devtools socket 才会出现。

|---|---|---|---|
| TC-01 加密房 | REST `createRoom` + `m.room.encryption` | `algorithm=m.megolm.v1.aes-sha2` | 协议脚本 L1 |
| TC-02 解锁门禁 | 冷启动到登录页 | 弹「输入本地解锁密码」→ 输入 → 2s 内进入 | 截图 + `isLocalUnlockUnlocked()` |
| TC-03 设备密钥上报 | 登录后 30s | `/keys/query` 有 `curve25519`+`ed25519` | 脚本 D3/S1 |
| TC-04 加密发送（SDK） | `client.sendEvent` | 服务端 `m.room.encrypted` | DB 校验 |
| TC-05 对端解密 | B 进房 | 渲染明文，`isDecryptionFailure()` 全 false | timeline 事件（**不用 innerText**） |
| **TC-06 UI 发送** | 真实点击发送按钮 | 服务端出现 `m.room.encrypted` | 三条同时成立：输入框清空 + timeline 有事件 + 服务端有事件 |
| **TC-07 UTD 恢复** | 新设备开老房 | 30s 内自发 `m.room_key_request`，收到 `m.forwarded_room_key`，自动解密 | `to_device_messages` 表 |
| TC-08 SAS 比对 | 两端同时开验证 | emoji 序列一致 | 人工截图 |
| TC-09 会话页 reload | 会话页整页刷新 | 仍弹解锁框（漏挂则记录） | 截图 |
| TC-10 安全存储 | Android 不设解锁登录 | crypto 能初始化 | logcat 无 4 条错误 |
| TC-11 签名 fail-open | 上传无 `signatures` 的 device_keys | 400 | 协议脚本 L4 |

### 6.5 后续验证方式

1. **协议层进 CI**：`E2EE_JSON=1 node scripts/e2ee-device-smoke.mjs`，断言「27 项绿」（D4 修完前允许 1 红并计入已知债）。
2. **真机 nightly**：`e2ee-two-device.mjs`（约 91s，依赖 AVD + dev server），不进 PR 门禁。
3. **服务端事实优先**：任何「消息是否发出 / 密钥是否请求」的结论，一律以 `/messages`、`events`、`to_device_messages` 为准，**不采信前端 innerText 或本地状态**（D5 就是这么定的）。
4. **变异自证**：
   - D4：恢复 fail-open → 协议脚本 L4 必红；

5. **文档回填**：每轮跑完回填主报告 §1 基线与 §3 状态表，避免「文档说没测、其实测过」。
