## 一、结论（先说结果）

| 问题 | 结论 |
|---|---|
| 能否按 §3-1 的步骤完整执行？ | **能跑通「加密 → 传输 → 对端解密」主链路，但不能按原步骤原样跑完**：原步骤是「双真机」，实际可用的是「Android 模拟器 + 本机第二端」；且必须先补一步**设置本地解锁密码**，否则 crypto 在两端都按设计 fail-closed，看起来像「E2EE 不支持」 |
| 移动端模拟器可用吗？ | **可用**。AVD `Medium_Phone`（arm64-v8a / android-37.0）启动后 `com.tjg.app` 3.0.10 能起、能登录、能收发；`adb reverse` 打通 5210/8008 |
| 能自动化吗？ | 模拟器**能**（WebView 开了 `webview_devtools_remote`，走 CDP 即可，`uiautomator dump` 取不到任何节点）；Mac 桌面端**不能可靠自动化**（WKWebView 无 CDP） |
| E2EE 本身通不通？ | **通**。模拟器侧加密发出（服务端 `m.room.encrypted` / `m.megolm.v1.aes-sha2`），Chromium 侧**解密并渲染出明文**。但 **UI 发送路径被「未验证设备」弹窗静默拦住**，不走 UI、直接调 SDK 才能发出去 |
| 最大风险 | 用户侧表现为「点了发送、气泡出现、对方收不到、没有任何报错」—— 这是最坏的一类故障（假成功） |

**一句话**：环境够用，加密链路也通，卡在「UI 门禁 + 安全存储 + 本地解锁」三处工程问题上，且这三处都会伪装成「E2EE 坏了」。

## 三、能否按 §3-1 步骤执行：逐步对照

原步骤（主报告 §3 第 1 项）：「各自设本地解锁密码 → 登录 → 建加密房 → 互发并比对 SAS」。

| 步骤 | 能否执行 | 实测/原因 |
|---|---|---|
| **0. 两台设备** | ⚠️ **降级** | 只有 1 台机器可自动化。实际组合：**Android 模拟器（A）+ 本机 Chromium（B）** 可跑通全链路；「Mac 真机桌面端」可启动但无法可靠驱动（§4.4） |
| **1. 设本地解锁密码** | ✅ 能，但**必须靠代码调用** | 模拟器/浏览器里都没有可直接点的入口路径可自动化；本次通过 `import('/src/services/secure/localUnlockKey.ts')` 调 `configureLocalUnlock()` 完成。**不做这一步 crypto 100% fail-closed** |
| **2. 登录** | ✅ 能 | 两端均用 DOM 事件填表登录成功。注意：点「登录」前必须等一拍（Vue `v-model` 要下一个 tick），否则提交空值且无提示 |
| **3. 建加密房** | ✅ 能（REST 侧） | `createRoom` + `initial_state: m.room.encryption` → 回读 `algorithm=m.megolm.v1.aes-sha2`；对端 `join` 成功 |
| **4. 互发加密消息** | ⚠️ **UI 路径被拦** | UI 发送触发「本房间有 N 台未验证设备」弹窗，**不选就不发、且无错误提示**；`client.sendEvent()` 直发则成功落 `m.room.encrypted` |
| **5. 对端解密** | ✅ 能（部分） | Chromium 端成功解密并渲染模拟器发出的密文；**反向（Android 端渲染 Chromium 的密文）未通过**，见 §4.3-S5 |
| **6. 比对 SAS** | ❌ 未完成 | 服务端侧只能验 to-device 信封（request/ready/key/mac/done 双向全通，§4.1-L5）；SAS emoji 由客户端 ECDH 派生，需两端同时在设备验证弹窗里人工比对，本次未做 |

### 前置条件清单（缺一不可）

1. 后端 `8008` 在跑（`docker` 栈），且房间版本支持 `m.room.encryption`；
2. `5210` 有 vite dev server，且 `TAURI_ENV_PLATFORM=android`（否则 Vant 组件解析失败）；
3. `adb reverse tcp:5210 tcp:5210` + `tcp:8008 tcp:8008`（APK 是 dev 构建，走 `127.0.0.1`）；
4. `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`（拿 pid 后 forward，pid 变则重做）；
5. **两端都要先配置本地解锁密码**（安全存储在模拟器上不可用，`storageKey` 只能由此派生）；
6. 两端都必须**登录过至少一次**（`device_keys` 上报是 E2EE 的必要条件，没有它发送必失败）。

### 环境限制（不是配置错误，是硬限制）

| 限制 | 影响 | 规避 |
|---|---|---|
| `uiautomator dump` 对 Tauri WebView **0 个带文本节点** | Appium/uiautomator 方案完全不可用 | 用 CDP（`scripts/cdp-eval.mjs`） |
| macOS WKWebView 无 CDP | 桌面端无法脚本化点击/断言 | 桌面端只做「启动 + 肉眼/截图」冒烟；功能验证放模拟器 + Chromium |
| `screencapture` 抓不到 tjg 窗口（只拍到壁纸） | 桌面端无法自动截屏取证 | 需人工切到该 Space 或授予录屏权限 |
| APK 是 2026-08-29 的 dev 构建 | Rust 侧命令可能落后于当前前端 | 前端走 devUrl 是最新的；涉及新增 Rust 命令的功能需重打 APK |
| 安全存储在 Android 上双失败（§5-D2） | 每台新设备都必须设解锁密码 | 修 Rust 侧后端选择逻辑 |

## 五、由实测定位的现存问题

> 分级口径沿用主报告：P0 阻断交付 / P1 影响主流程或结论可信度 / P2 体验或工程债。

### D1（P0）UI 发送被「未验证设备」弹窗静默拦截，且本地已显示成功

- **现象**：加密房里点发送 → 弹出「本房间有 N 台未验证设备…仅向已验证设备发送 / 关闭」；不选择时消息**不会发出**，但气泡已渲染在本地，**没有 toast、没有红色重发按钮**。
- **证据**：双端轮 S3（UI 点击成功 → 服务端 `encrypted=0/plaintext=0`），同一房间用 `client.sendEvent()` 直发立刻 `encrypted=1`。
- **影响**：用户完全无法察觉消息没发出去；对端永远收不到，且双方都看不到任何错误。这是「假成功」，比直接报错更糟。
- **下一步**：① 门禁未决时**不要**乐观插入气泡（或在气泡上打「待确认」态）；② 关闭/取消弹窗要显式提示「消息未发送」；③ 用户选择后记住偏好（`setBlockUnverifiedDevices`），避免每条都问。
- **验收**：门禁未决时服务端 0 条 **且** UI 不出现「已发送」气泡；选择后服务端出现 `m.room.encrypted`。

### D2（P1）Android 上安全存储全链失败 ⇒ 每台设备都必须设本地解锁

- **现象**（logcat 原文）：
  ```
  ERROR tjg_app_lib::utils::crypto: HOME 环境变量未设置，无法保存密钥文件
  WARN  secure_store: Keychain bug detected ... set_password returned Ok but get_password (new Entry)
        returned NoEntry (macOS dev mode ACL issue). Falling back to file storage.
  WARN  secure_store: Cannot determine fallback path for key 'matrix_token_@...'
  ERROR secure_store: Both keychain and fallback failed to store secret
  WARN  user_service: Failed to store token in secure storage: Access to secure storage was denied by the system
  ```
- **影响**：Android 上分支文案写成 `macOS dev mode ACL issue`（明显不是该平台语义），且 fallback 依赖 `HOME`（Android 上不存在）⇒ 两级都失败 ⇒ `storageKey=null` ⇒ crypto fail-closed。用户不设解锁密码就永远没有 E2EE，且没有任何 UI 引导。
- **下一步**：① Android 侧改用 Keystore/EncryptedSharedPreferences 后端，或在 `secure_store` 里对 `target_os="android"` 走独立分支；② fallback 路径不要依赖 `HOME`（用 app 私有目录）；③ 修文案（不得在 Android 上提 macOS）；④ 修不了时，登录后**主动引导**设置本地解锁（而不是静默降级）。
- **验收**：Android 上 `getSecureStorageBackendInfo()` 报出可用的原生后端；未设解锁也能 crypto 初始化；`adb logcat` 不再出现上述 5 条。

### D3（P1）本地解锁门禁冷启动不弹窗，静默进入「crypto 不可用」状态

- **现象**：`configureLocalUnlock()` 成功后整页 reload → `isLocalUnlockConfigured()=true`、`isLocalUnlockUnlocked()=false`、**没有任何解锁对话框**，页面直接进 `/mobile/message`（"暂无会话"），crypto 保持不可用。
- **影响**：与 D2 叠加后，用户会看到「能登录、能进会话、消息发不出/解不开」，且没有任何可执行的恢复入口。
- **下一步**：启动流程里 `isLocalUnlockConfigured() && !isLocalUnlockUnlocked()` 必须拦在会话页之前（参考 `router/secretChatGuard.ts` 的 `pendingPath` + 弹窗模式）。
- **验收**：配置过解锁但未解锁时，冷启动必弹解锁框；取消则回登录页。

### D4（P1，安全）`/keys/upload` 缺 `signatures` 的 device_keys 被接受并落库

- **现象**：带**错误**签名 → `400 M_BAD_JSON Invalid device key signature`（正确）；**完全不带** `signatures` → `200`，且 `/keys/query` 能查到该设备（`ed25519` 值是伪造串）。
- **影响**：验签只在「signatures 字段存在」时执行，属 fail-open。攻击者用自己的 token 就能往设备列表写一条无签名设备记录，污染对端 `/keys/query` 结果（跨签名/TOFU 判断的基础被削弱）。
- **已确认的缓解**：one-time key 的签名是**强制**校验的（伪造签名 → `400 Invalid one-time key signature`），所以无法据此完成完整 Olm 握手。
- **下一步**：`device_keys` 缺失 `signatures` 时直接 `400`；补一条单测（缺签名/空签名/错用户/错设备 四种）。
- **验收**：`scripts/e2ee-device-smoke.mjs` 的「缺少 signatures 的 device_keys 应被拒绝」转 ✅。

### D5（P2）新设备解密失败（UTD）无自动密钥请求恢复

- **现象**：新登录设备打开加密房，历史/在途消息显示「无法解密这条消息 / 设备上缺少解密所需的密钥，重试可能从备份恢复密钥后成功」，事件 `isDecryptionFailure()=true`，`DecryptionError`。
- **影响**：换设备/重装后用户体验断崖；是否能恢复完全取决于用户是否点了「重试」且发送方在线。
- **下一步**：确认 `m.room_key_request` 是否在 UTD 时自动发出、发送方是否响应；若没有，接入 `requestRoomKey` 并在 UI 上给「正在向其他设备请求密钥」的状态。
- **验收**：新设备打开房间后 30s 内自动从在线设备取回会话密钥并解密，无需人工点「重试」。

### D6（P2，工程）移动端 Tauri 只能走 CDP，没有常规 UI 自动化通道

- **现象**：`uiautomator dump` 对 Tauri WebView 返回 **0 个带文本节点**（整棵树没有可读文本）。
- **影响**：Appium/原生 UI 测试方案无效；团队若按常规思路写移动端 e2e 会一直「找不到元素」。
- **下一步**：把 `scripts/cdp-eval.mjs` 固化为移动端 e2e 的执行层（封装成 helper），并在文档里写明「Tauri 移动端 = CDP，不是 uiautomator」。

### 对上一轮结论的修正（如实记录）

| 上一轮说法 | 实测结论 |
|---|---|
| 「浏览器态不可测 E2EE（crypto fail-closed）」 | **不准确**。fail-closed 只在「拿不到 storageKey」时发生；配置本地解锁后浏览器态 crypto 可用，Chromium 端成功解密 |
| 「E2EE 必须双真机」 | **可降级**为「1 台真机（模拟器）+ 1 个第二端（Chromium/桌面）」，加解密链路依然可验；不可替代的是 SAS 人工比对 |

### 6.5 后续验证方式（怎么保证不回归）

1. **协议层进 CI**：`scripts/e2ee-device-smoke.mjs` 不依赖 UI，只需后端；以 `E2EE_JSON=1` 输出断言结果，断言「27 项全绿」（D4 修完前允许 1 红，并把它当已知债计数）。
