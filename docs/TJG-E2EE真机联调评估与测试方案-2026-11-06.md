### 4.5 TC-06 是怎么打通的（这条比结论更重要）

前两轮把「服务端没消息」误判成「UI 静默失败」。真实原因是三件事叠在一起：

| # | 事实                                                                                                      | 后果                                                     |
| - | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 1 | `#message-input` 的 Enter 是**换行**（`@keydown.exact.enter` 走 `handleEnterKey`，但移动端口令下不发送）                  | 合成 `KeyboardEvent` 与 CDP 真实按键都只换行                      |
| 2 | 发送按钮是 `<n-button v-if="hasInput">{{ t('editor.send') }}</n-button>`（`MsgInputMobileControls.vue:23-29`） | **输入框没内容时按钮根本不存在**；用 JS 直接改 `innerText` 不触发 `hasInput` |
| 3 | 按钮文案来自 i18n `editor.send`（zh-CN = `发送`）                                                                 | 按 `aria-label="发送"` 找不到它（它没有 aria-label）               |

正确姿势（已固化进脚本）：

```js
await cdp.eval(`document.querySelector('#message-input').focus()`)
await cdp.send('Input.insertText', { text })          // 真实输入 → hasInput 更新 → 按钮渲染
const btn = /* [...document.querySelectorAll('button')].find(b => /^(发送|Send)$/.test(b.innerText.trim())) */
await cdp.send('Input.dispatchMouseEvent', { type: 'mousePressed',  x, y, button: 'left', clickCount: 1 })
await cdp.send('Input.dispatchMouseEvent', { type: 'mouseReleased', x, y, button: 'left', clickCount: 1 })
```

判据三条同时成立才算过：**输入框清空 + timeline 新增事件 + 服务端出现 `m.room.encrypted`**。

> 反例留档：`document.body.innerText` 会把 contenteditable 的内容也算进去，  
> 用它判断「消息已渲染」会假阳性 —— 第一版就是这么误判的（D7）。

## 五、现存问题

### D5（P1，**结论已更正**）key request 能发、能存，但**没有「响应并转发密钥」的通道**

> 上一版写的是「客户端从不发 `m.room_key_request`」，**判据选错了表**。
> 本项目有两套通道：标准 to-device（`to_device_messages`）与**自定义 HTTP 端点**
> （`e2ee_key_requests`）。只查前者必然恒为 0，据此得出的「从不发」是错的。
> 2026-11-07 早间用 `scripts/d5-key-request-probe.mjs` 重新取证，结论改写如下。

#### ① 前端确实会自动发起（实测证据）

制造可控 UTD（向房间发一条伪造 `m.room.encrypted`，随机 `session_id`）后：

```
✅ 客户端标记为 UTD — timeline=13 条，UTD=1 条
✅ performCheck 的计数 — undecryptableMessageCount=1
✅ 服务端 e2ee_key_requests 新增 — 总数 29 → 31（本次 +2）
ℹ️  明细：req_1794008012055 | DEVICENVaDCVZe5a | d5probe_1794008093870 | request
        req_1794008011941 | DEVICENVaDCVZe5a | d5probe_1794008093870 | request
ℹ️  to_device %room_key% 新增 — 0 → 0（走 HTTP 通道时这里不会变）
```

代码链路：`useEncryption.startCryptoHealthMonitor()` → `CryptoHealthMonitor.start()`（5 分钟一次）
→ `performCheck()` → `undecryptableMessageCount > 0` → `triggerKeyRequests()`
→ 遍历 timeline 找 `getContent().msgtype === 'm.bad.encrypted'`（SDK `models/event.js:820` 确实赋这个值）
→ `matrixCryptoService.createRoomKeyRequest()` → `POST /room_keys/request`。

**所以「前端包装层吞掉」不成立**，判据字段也是对的。

#### ② 真正的缺口：请求无人兑现

| 端点 / API | 存在 | 说明 |
|---|---|---|
| `POST /room_keys/request` | ✅ | `synapse-web/src/routes/e2ee/keys.rs:34` |
| `GET /room_keys/request` | ✅ | 同上 |
| `DELETE /room_keys/request/{id}` | ✅ | `keys.rs:35` |
| **响应请求 / 转发密钥** | ❌ | 服务端**没有**这条路由；SDK 也只有 `create/list/deleteRoomKeyRequest`，**无 fulfill/shareRoomKey** |

全表状态（`e2ee_key_requests`，31 条）：

```
action=cancellation, is_fulfilled=t  → 18 条
action=request,      is_fulfilled=f  →  9 条
action=m.request,    is_fulfilled=f  →  4 条
fulfilled_by_device 全部为空
```

即：**历史上没有任何一次请求是被「另一台设备转发密钥」兑现的**。请求写进去就悬空，所以 UTD 永远自愈不了。

#### ③ 附带发现（字段语义，P2）

`action=cancellation` 的 18 条 `is_fulfilled=true` —— 把「撤销请求」记成「已兑现」。
按语义 `is_fulfilled` 应只表示「密钥已被转发」，撤销不应置真。

#### 下一步（按你的口径：前端不自建补发）

1. **后端**：补 `PUT /room_keys/request/{request_id}`（或等价端点），语义是「某设备把 session 的密钥转给请求方」，
   成功时写 `is_fulfilled=true` + `fulfilled_by_device`；
2. **SDK fork**：补 `fulfillRoomKeyRequest()`，收到 pending 请求时由**持有该 session 的设备**调用；
3. **前端**：只做「发现有 pending 请求 → 调 SDK 的方法」，**不自己拼协议**；
4. `cancellation` 不应置 `is_fulfilled=true`（单独一条修正）。

#### 验收

- 新设备打开老房 → 30s 内 `e2ee_key_requests` 出现 `is_fulfilled=true` 且 `fulfilled_by_device` 非空；
- 页面自动解密，无需点「重试」；
- `cancellation` 记录 `is_fulfilled=false`。

#### 复现

```bash
node scripts/d5-key-request-probe.mjs           # 用当前房间
node scripts/d5-key-request-probe.mjs '!room:x' # 指定房间
```

### D4（P1，安全）`/keys/upload` 缺 `signatures` 的 device_keys 被接受并落库

- 错签名 → `400 M_BAD_JSON`（正确）；**无签名 → `200` 且落库**（fail-open）。
- 缓解：one-time key 签名强制校验（伪造 → `400`），无法完成完整 Olm 握手。
- 下一步：缺 `signatures` 直接 `400` + 4 条单测；验收看协议脚本 L4 那条转 ✅。

### D2（P1）Android 安全存储全链失败 ⇒ 每台设备都要过本地解锁

```
ERROR crypto: HOME 环境变量未设置，无法保存密钥文件
WARN  secure_store: Keychain bug detected ... (macOS dev mode ACL issue). Falling back to file storage.
WARN  secure_store: Cannot determine fallback path for key 'matrix_token_@...'
ERROR secure_store: Both keychain and fallback failed to store secret
```

Android 上文案写成 macOS 语义；fallback 依赖 `HOME`（Android 无）→ 两级全失败 → `storageKey=null` → crypto fail-closed。  
下一步：Android 走 Keystore 分支、fallback 不依赖 `HOME`、修文案；验收看 logcat 不再出现上述 4 条。

### D8（P2，工程）Chromium 浏览器态下移动聊天页渲染极慢

- 现象：`router.push` 到 `/mobile/chatRoom/chatMain/<rid>` 后 URL 已正确、`getRoom()` 能拿到 12 条 timeline，但 `document.body.innerText` 只有 208 字符持续 30s+；同一房间在模拟器上渲染正常。
- 影响：只影响**浏览器态第二端**的断言（S4 因此判为「判据无效」），不影响真机结论。
- 下一步：查移动聊天页在桌面 Chromium 下的条件渲染（是否为 `isMobileRef` + 视口/UA 组合导致 v-if 分支未激活）。

### D6 / D7（P2，工程）

- **D6**：`uiautomator dump` 对 Tauri WebView 返回 0 个带文本节点；移动端 e2e 只能走 CDP（`scripts/cdp-eval.mjs` 已可用）。

### 8.3 结论与建议

| 方案 | 可行性 | 代价 |
|---|---|---|
| iOS 模拟器 ×1 + Android ×1（全自动） | ❌ | iOS 无 UI 注入通道 |
| iOS 模拟器 ×1（人工操作）+ Android ×1（自动） | 🟡 | iOS 端需人工登录/点发送；且中文方框影响可读性 |
| **Android ×2（全自动）** | ✅ **推荐** | 需 2 个 AVD + 串行化 crypto 初始化；宿主内存要够 |

**下一步**（按优先级）：
1. 双 Android 串行化：先让 A 完成登录 + crypto + 发送，再启动/登录 B（避免同抢资源）；
2. 修 iOS 中文方框（字体回退），否则 iOS 端即使人工操作也难以判读；
3. iOS 若要自动化，唯一可行路径是 Appium + WebDriverAgent（需能跑 `xcodebuild test`），成本远高于 Android。

## 九、双 Android 串行互测打通（2026-11-08 下午）

§8.2 的双端互测当时只跑出「A 发得出、B 收不到」。这一轮把编排改成**阶段化串行**，双向解密全部成立。

### 9.1 为什么必须串行（先纠正上一轮的归因）

上一轮把 B 端 crypto 起不来归因为「两台模拟器抢资源」。实测后更准确的描述是：

| 观测 | 真相 |
|---|---|
| `attempted=true / initialized=false / error=null` | **不是失败**：`initRustCrypto()` 还没 resolve（挂起）。失败会带 `error` |
| A 端本地 `initialized=true`，服务端 180s 无 `device_keys` | 本地初始化 ≠ 已上报；但根因不是慢，见 9.3 的 D9 |
| 两台同时跑时更容易卡 | 宿主 16GB 只剩 ~70MB 空闲、两台各 4 vCPU，确实加剧，但**不是唯一原因** |

脚本现在把三种状态分开判：`initialized=true`（就绪）/ `error!==null`（真失败）/ `attempted && error===null && !initialized`（挂起，超 90s 才 reload 重试一次）。

### 9.2 串行编排（`scripts/e2ee-two-androids.mjs`）

同一时刻只有一台设备在做 crypto 初始化，另一台 `am force-stop`：

| 阶段 | 动作 | 关键约束 |
|---|---|---|
| **S0** | REST 建号 + 建加密房（`m.room.encryption`）+ B join + 两台 `adb reverse` | — |
| **S1** | 停 B → A 启动/解锁/登录/crypto → 进房 → 发 `msgA1` | A 发送时 B 还没有 `device_keys`，所以 `msgA1` 对 B 必然是 UTD |
| **S2** | 停 A → B 启动/解锁/登录/crypto → 进房（记录 UTD）→ 发 `msgB1` | B 的消息是「A 离线时发出」，A 回来时必须能解 |
| **S3** | A 冷启动回来（会话恢复）→ 解 `msgB1` → 发 `msgA2` → B 解 `msgA2` | 双向都要成立才算过 |

`force-stop` 后 pid 变化，`adb forward <cdp> localabstract:webview_devtools_remote_<pid>` 必须重建（脚本自动处理）。

### 9.4 串行过程中撞出的两个新缺陷

#### D9（P1，E2EE 静默失效）「登出 → 登录（同页）」后 client 与 crypto 脱钩

- **现象**：在同一页面执行 `store.logout()` 再登录新账号，之后
  `getClient().getUserId()` 仍是**上一个账号**、`getClient().getCrypto()` 为 `null`，
  但 `getRustCryptoDebugState()` 回报 `initialized=true`（`attempted=true, error=null`）。
  ⇒ 服务端 180s 内**没有任何 `/keys/*` 请求**，device_keys 永不上传，E2EE 静默不可用。
- **证据**：本轮前三轮串行全部卡在此处（S1 就断）；
  `pg` 侧 `device_keys` 对新账号 0 行；CDP 抓网络显示整段启动无 `/keys/*`。
- **为什么危险**：debug state 没有账号维度，UI 与测试都容易被它骗成「crypto 已就绪」。
- **规避**：登出后**必须 reload** 再登录（脚本 `logoutAndReload`）；加上 reload 后立刻 36/0。
- **建议修**：
  1. `getRustCryptoDebugState()` 返回值补 `userId`/`deviceId`，并让 `ensureCrypto` 在账号/设备变化时重置状态；
  2. 登出流程显式 `stopClient → 释放 cryptoBackend → 清 debug state`，登录后重新 init；
  3. 把「client.getCrypto() === null 但 debug initialized=true」做成一条守卫（单测 + 运行期告警）。

#### D10（P1，功能不可用）设备验证（SAS）缺「启动 SAS 方法 + verify」两步

- **现象**：`startSasVerification` + 对端 `acceptVerification` 之后，两端 `getSasView()` 永远抛
  `Cannot read SAS: … has not started a SAS method yet`；再往后抛 `… has no SAS available`。
- **根因**：`MatrixVerificationService.getSasView()` 只读 `verifier.getShowSasCallbacks()`，
  而 SDK 需要先 `request.startVerification('m.sas.v1')` 再 `verifier.verify()` 才会产出 SAS。
  全仓 `grep -r "startVerification(|\.verify()" src` **只命中单测**，生产代码没有这两步。
- **影响**：`DeviceVerifyDialog` 会一直等 `waitForSasView` 到 120s 超时；用户永远比不到 emoji。
- **实测（脚本直接调 SDK 补上这两步）**：服务端 to-device 立刻出现完整流转
  `m.key.verification.request → ready → start → accept → key`，说明**协议层是通的**；
  但两端 `verify()` 在 80s 内仍未 resolve，其中一次 B 端以 `m.timeout` 取消。
  ⇒ 即便补齐调用，SAS 产出这一步还另有阻塞，需要继续定位（下一步）。
- **建议修**：① 服务层补 `startSasVerificationMethod(txId)` 与 `verifySas(txId)`（内部即上述两步）；
  ② `DeviceVerifyDialog` 在「对方已接受」后调用；③ 补一条双端集成用例（本脚本可作为骨架）。

#### D11（P2，测试/体验）验证事务不跨会话且不清理

- **现象**：上一次跑残留的 transaction 会一直挂在 `getPendingVerifications()` 里；
  按「取第一条」的写法会**接受旧事务**（本轮踩过两次），新事务永远停在 Requested。
- **建议**：进设置页/打开验证弹窗时先 `cancelVerification` 过期事务；`initialize()` 里按 `timestamp` 过滤陈旧项。

### 9.5 对 D2 的精确化（原来是「Android 安全存储全链失败」）

根因收敛到**两处 fallback 都只认 `$HOME`**，而 Android 进程没有 `HOME`：

| 位置 | 逻辑 | 后果 |
|---|---|---|
| `src-tauri/src/utils/secure_store.rs:37-40` | `get_fallback_dir()` = `$HOME/.tjg/secure-storage` | `Cannot determine fallback path` → `Both keychain and fallback failed`（logcat 直证） |
| `src-tauri/src/utils/crypto.rs:36-40` | `get_key_file_path()` = `$HOME/.tjg/master-key` | 主密钥取不到 → token **加解密**失败 |

可复跑判据（`scripts/session-persist-probe.mjs`，串行测试后单跑一次）：

```
登录 ok，client userId=@persistmw7m0444
冷启动后：userId=null，路由=/mobile/login
⇒ 会话未恢复（D2）
```

修法建议：fallback 根目录改用 Tauri 的 app data dir（代码里已有 `TJG_PROFILE_DIR`，
`secure_store::get_service_name()` 已经在读它，但 fallback 路径没读）；改完后本探针应转为 pass。
