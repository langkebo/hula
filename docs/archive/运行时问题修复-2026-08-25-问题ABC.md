## 问题 C：Rust Crypto 因 deviceId 时序竞态被跳过（E2EE 失效）✅ 已修复

**现象**：日志 `缺少 userId 或 deviceId，跳过 Rust Crypto 初始化`，应用退化为非加密模式。

**根因链**：

1. SDK 的 `getDeviceId()` 只读 `this.deviceId`，它**仅在 `createClient(opts.deviceId)` 时赋值一次**（`matrix-js-sdk/lib/client.js:507`），登录不会回填它。
2. session restore 路径 `restoreWithAccessToken` 先调 `initialize`（**不传 deviceId**）→ 再调 `loginWithToken`。
3. `loginWithToken` 的 `shouldReuse` 复用分支直接返回 `config.deviceId`（此时为 `undefined`），**跳过了 whoami 预解析**——这正是 memory 里「deviceId 必须在 initialize 前定好」铁律的漏网场景。
4. 即使走 whoami，synapse-rust 的 whoami 端点也可能不返回 `device_id`。

最终 `createClient` 时 deviceId 为 `null` → `ensureCrypto` 里 `!deviceId` → 直接 return → E2EE 未初始化。

**修复**（`MatrixClientAuth.ts` + `deviceIdPersistence.ts`）：

- 复用分支加 `reusableDeviceId` 非空守卫，空则落到 whoami 预解析分支。
- `stableDeviceId = resolveStableDeviceId(config, whoamiDeviceId) ?? generateDeviceId()` 兜底。
- 密码/SSO 登录：`deviceId: loginResponse.device_id ?? reusedDeviceId / generateDeviceId()`。
- 新增 `generateDeviceId()`（16 位大写 hex，与 `qrLoginHelpers.generateDeviceId` 同源，独立实现保零依赖）。

## 问题 B：启动仍超 15s ✅ 已修复

**现象**：`登录后 Matrix 启动收尾超过 15000ms，转为后台继续`。

**根因**：日志 28.059 初始化 → 42.920 超时之间**完全静默**，恰好是 `waitForCrossWindowCryptoInit` 无条件等待 15s 的「crypto-init-done」广播。第一个初始化窗口没有任何其他窗口给它广播 done，于是白等 15s。此前 P1 修的 sliding-sync 探测（5s）并非本次 15s 的来源。

**修复**：`CROSS_WINDOW_DONE_WAIT_MS` 从 15_000 缩短到 1_000。跨窗口互斥已由 `ensureCrypto` 层的 Web Locks（`navigator.locks.request` exclusive）保证，此处的 done 广播仅是「其他窗口恰好已完成」的短探测，无需长等。

## 问题 A：MatrixClientService 被构造两次 — 非 bug，定性为多窗口预期行为

**现象**：日志 `Matrix 客户端服务初始化` 出现两次（间隔约 0.6s）。

**结论**：`MatrixClientService` 已有 `globalThis.__TJG_MATRIX_CLIENT_SERVICE__` 单例守卫（只防同一窗口内重复实例化）。两次日志是 **login 窗口 + home 窗口各自独立 `globalThis`** 各 new 一次所致——Tauri 多窗口每个 WebView 有独立 globalThis，这是固有特性，代码注释已明确。

跨窗口的 crypto 竞争已由 Web Locks（互斥锁）+ BroadcastChannel（done 广播）协调覆盖，本次问题 B 修复还进一步优化了该协调的等待时长。**无需改码**。
