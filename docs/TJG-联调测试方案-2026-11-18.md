## 0. 结论先行

**推荐方案 A「分层收口」：不新建测试框架，把已经存在的 e2e／探针／契约冒烟收进三个统一入口 + 一个时效四元组 + 一条分层门禁链。**

三条核心理由：

1. **资产已足够，缺的是入口**。项目现有 38 个 e2e spec（含 `e2e/visual/` 下的 Storybook 视觉回归；其中 11 个 live）、10 个服务端探针、1 套 71 条断言的契约冒烟、23 个 lint 门禁测试——覆盖面并不薄；但 `test:e2e:live` 只收录 4 个 live spec、10 个探针只有 1 个有 npm script，**其余只能靠人记得 `node scripts/xxx.mjs` 加一堆环境变量**。
2. **联调结论没有时效绑定，所以会持续腐坏**。`check:release` 33 段全是静态门禁，不含任何 `test:*`；`integration-smoke.yml` 只在每天 02:30 UTC 与手动触发，不挂 PR。于是「联调过了」这句话没有可核验的含义——文档族里后端镜像 commit 出现 5 个不同值、SDK commit 3 个值、端口两套（6130 vs 5211），都是同一个根因。
3. **假绿防线是散落的个人经验，不是机制**。`PROBE_REQUIRE_FRESH_APK`、`pm clear`、`getLiveTimeline()` 取代 `innerText`、负对照、变异自证——每条都对，但都写在文档里靠人执行。一旦换人复跑，结论不可比。

一句话：**这份方案不解决「测得够不够多」，解决「测过的结论还算不算数」。**

## 3. 现状链路与七个结构性痛点

### 3.1 当前「跑一次联调」的真实链路

```
手工起后端容器 ──→ 手工确认 healthy ──→ 手工起 5210/5211 dev server
        │                                        │
        │                                        ├─→ 手工 adb reverse / forward（真机时）
        │                                        └─→ 手工开一次页面预热（依赖图发现）
        │
        ├─→ 想起要跑哪个探针 ──→ 翻文档 §五 复跑速查 ──→ 手工导出 3~8 个环境变量
        │
        ├─→ 想起 live spec ──→ 只有 4 个在 test:e2e:live ──→ 其余 7 个靠 §19.57/§19.61 命令
        │
        └─→ 跑完 ──→ 把结果手写进三份文档之一 ──→ 三份文档口径互不一致
                              │
                              └─→ 下次换人复跑，无法判断「上次结论是否还成立」
```

### 3.2 痛点（每条带实测证据）

| 编号 | 痛点 | 证据 | 后果 |
|---|---|---|---|

## 6. 推荐方案 A：分层收口

### 6.1 分层模型

```
L0 静态门禁     check:release 33 段 + tests/lint 23 个        PR 必跑，≤5 min
   ↓
L1 离线契约     vitest contract / 单测地板（90 文件 849 例）    PR 必跑
   ↓
L2 服务端探针   contract-smoke(71) + 10 探针（REST/DB 直查）   nightly，需 live
   ↓
L3 浏览器 e2e   38 spec（11 live，按路由集自动分派）            nightly，需 live
   ↓
L4 真机/双端    Android 探针、E2EE 双端、通话 TURN             release 前人工清单
```

每层只依赖下一层的产物，不跨层断言：L3 不直接查 DB，L2 不驱动 UI，L4 才碰真机。

### 6.2 统一入口：三个 script 取代 N 份速查表

`package.json` 新增（示意，实施时按此落地）：

```json
{
  "scripts": {
    "test:live": "node scripts/live/run-live.mjs",
    "test:live:list": "node scripts/live/run-live.mjs --list",
    "test:probe": "node scripts/live/run-probe.mjs",
    "test:probe:list": "node scripts/live/run-probe.mjs --list",
    "check:live-manifest": "node scripts/check-live-manifest.mjs"
  }
}
```

`scripts/live/run-live.mjs` 的核心职责（约 120 行）：

```js
// scripts/live/run-live.mjs —— 只做编排，不复刻 playwright 的能力
import { readFileSync } from 'node:fs'
import { spawnSync } from 'node:child_process'
import { captureBaseline, assertBaseline } from '../lib/live-env.mjs'

const manifest = JSON.parse(readFileSync('scripts/live/live-manifest.json', 'utf8'))
const targets = manifest.specs.filter((s) => s.live)

if (process.argv.includes('--list')) {
  for (const s of targets) console.log(`${s.name}\t${s.routeSet}\t${s.oracle}\t${s.owner}`)
  process.exit(0)
}

// 路由集在 manifest 里已固化，且由 tests/lint/e2e-route-sets.test.ts 与 e2e/specRouteSets.ts 三处对齐
const PROJECT = { desktop: 'desktop-chromium', mobile: 'mobile-chromium' }
const allowDrift = process.argv.includes('--allow-drift')

const baseline = captureBaseline()
assertBaseline(baseline, {
  expected: manifest.expectedBaseline ?? {},
  requireApk: manifest.requireApk,
  allowDrift
})

for (const routeSet of ['desktop', 'mobile']) {
  const files = targets.filter((s) => s.routeSet === routeSet).map((s) => s.file)
  if (!files.length) continue
  const res = spawnSync(
    'npx',
    ['playwright', 'test', ...files, `--project=${PROJECT[routeSet]}`, '--reporter=json', '--workers=1'],
    { stdio: 'inherit', env: { ...process.env } }
  )
  if (res.status !== 0) process.exitCode = 1
}
```

要点：**按 `specRouteSets.ts` 自动分派 project**，而不是靠人手记「这条要跑 desktop」。路由集本身已有 `tests/lint/e2e-route-sets.test.ts` 三处一致性校验，直接复用。

### 6.3 时效四元组：让「联调过」变成可核验命题

`scripts/lib/live-env.mjs`：

```js
// 采集：把「结论属于哪个环境」固化成四个不可推导的值
import { execFileSync } from 'node:child_process'
import { readFileSync, statSync } from 'node:fs'

const exec = (cmd) => execFileSync('sh', ['-c', cmd], { encoding: 'utf8' }).trim()
const statOrNull = (p) => { try { return statSync(p) } catch { return null } }

export function captureBaseline() {
  const image = exec(`docker inspect synapse-app --format '{{.Config.Image}}'`)
  const startedAt = exec(`docker inspect synapse-app --format '{{.State.StartedAt}}'`)
  const pin = JSON.parse(readFileSync('meta/sdk-pin.json', 'utf8'))
  const apk = statOrNull('src-tauri/gen/android/app/build/outputs/apk/arm64/debug/app-arm64-debug.apk')
  return {
    backend_image: image,                     // 例：synapse-rust:6.3.0-8e6e4a5f2
    backend_started_at: startedAt,            // 容器启动时刻，换镜像必变
    sdk_pin: { commit: pin.sdk_commit, tarball: pin.tarball_sha256, version: pin.sdk_version },
    apk_mtime: apk?.mtimeMs ?? null
  }
}

export function assertBaseline(actual, { expected, requireApk, allowDrift = false }) {
  const drift = []
  if (expected.backend_image && actual.backend_image !== expected.backend_image) drift.push('backend_image')
  if (expected.sdk_pin?.commit && actual.sdk_pin.commit !== expected.sdk_pin.commit) drift.push('sdk_pin')
  if (requireApk && !actual.apk_mtime) drift.push('apk_mtime(missing)')
  if (!drift.length) return
  if (allowDrift) {
    console.warn(`[live-env] 显式豁免环境漂移：${drift.join(', ')}（报告须记 drift_reason）`)
    return
  }
  console.error(`[live-env] 环境漂移：${drift.join(', ')}`)
  console.error('  重跑前请先对齐基线；确需放行请传 --allow-drift 并在报告里记 drift_reason')
  process.exit(2)                            // 2 = 环境不匹配，不是测试失败
}
```

**为什么必须四个值**：`backend_image` 只有 tag（可能被重建覆盖），`started_at` 才区分「同一 tag 重启过」；`sdk_pin` 防止前端跑在旧 tarball 上；`apk_mtime` 防止在旧 Rust 上取证（这正是 `check:apk-freshness` 已经解决的那类假绿，只是现在只覆盖 APK 一侧）。

### 6.4 单一真源与文档生成

`scripts/live/live-manifest.json` 每条至少六个字段：

```json
{
  "specs": [
    {
      "name": "room-settings-live",
      "file": "e2e/room-settings-live.spec.ts",
      "routeSet": "both",
      "live": true,
      "oracle": "server+messages",
      "covers": ["B-ROOM-SETTINGS", "CAP-02"],
      "owner": "chat"
    }
  ],
  "probes": [
    {
      "name": "push-delivery",
      "file": "scripts/push-delivery-probe.mjs",
      "category": "server",
      "requires": ["SYNAPSE_DB_CONTAINER"],
      "oracle": "backend-log+db",
      "covers": ["B11"]
    }
  ],
  "requireApk": false
}
```

`scripts/check-live-manifest.mjs`（进 `check:release`）做三件事，都是 fail-closed：

1. `e2e/*.spec.ts` 与 manifest 双向比对——**新增 spec 未登记即红**，登记了但文件不存在也红；
2. `scripts/*probe*.mjs` 与 manifest 双向比对；
3. `status: passed` 的条目必须带 `last_run` 四元组，且 `backend_image` 与当前 pin 的 commit 前缀一致；否则降级为 `stale`。

这样 P-05「文档超前」从**写作纪律**问题变成**编译错误**：状态由 JSON 生成，手写表格不可能再抢跑。

### 6.5 门禁分层

| 层 | 触发 | 内容 | 时长预算 | 失败语义 |
|---|---|---|---|---|
| PR | `quality-gate.yml` | L0（33 段）+ L1（单测地板 + contract）+ `check:live-manifest` | ≤5 min | 阻断合并 |
| Nightly | `integration-smoke.yml` 扩展 | L2（71 case + 10 探针）+ L3（38 spec 分路由集） | ≤40 min | 开 issue，不阻断 |
| Release | `release-validation.yml` | L0–L3 全量 + L4 人工清单勾选 | ≤90 min | 阻断发布 |
| 手动 | `workflow_dispatch` | 单 spec／单探针，带 `--allow-drift` | — | 只记报告 |

关键设计：**nightly 失败不阻断合并，但必须落到 `live-status.json` 的 `stale`**。理由是 live 环境本身有抖动（§19.57 记录「同一进程串跑会偶发 page-closed」），阻断式门禁会让人习惯性绕过；而「stale 标记」会持续可见，比红灯更能驱动修复。

### 8.4 结构性问题：`check:release` 是 `&&` 链，**每次只能看见第一个红**

2026-11-19 实测：`check:release` 34 段串行 `&&`，第 N 段失败后**后面全部不执行**。于是：

| 轮次 | 首个可见失败 | 处置 |
|---|---|---|
| 1 | `check:bare-matrix-paths`（8 条 prefix 拼接） | 改代码 + `--accept-new` 登记 → 通过 |
| 2 | `check:tauri-capability-window-coverage`（`settings` 窗口未登记） | 补注册表 → 通过 |
| 3 | `check-matrix-service-layering`（`MatrixAccountDataMethods.ts` 新增 token 读取、依赖链 14>12、服务文件 272>244） | **不是本批改动**，未修 |

**这制造了一种系统性的错觉**：每次修好一个，都以为「只差一点」，实际可能还差 N 个。
更糟的是它让「全量门禁」长期不可用——只要前面某个段红着，后面 20 多段等于从没跑过。

### 8.5 已落地：`pnpm check:release:all` 一次跑完全部 34 段

`scripts/check-release-all.mjs`：解析 `check:release` 的段列表，**逐段执行且失败继续**，最后汇总
「通过 N/总数」并给出每段的首行错误。`check:release` 本身保持 `&&` 快速失败（CI 用），两者分工。

**首次全量结果：32/34 通过，2 失败**

| 段 | 结果 | 性质 |
|---|---|---|
| `check:matrix-layering` | ❌ | **既有债**：`MatrixAccountDataMethods.ts` 新增 token 读取、依赖链 14>12、服务文件 272>244。涉及文件最后改于 11-18 / 11-06，非本批改动 |
| `check:coverage` | ❌→**修了假绿，本地仍受环境限制** | 原来它写的是 `cmd1 ; cmd2`（**分号**）：cmd1 跑测试挂了，cmd2 照样读磁盘上**上一次的** `coverage-summary.json` 并「通过」——这是真·假绿，CI 上同样成立（OOM/超时/崩溃都会被它掩盖）。已改 `&&` 短路 + 给 `check-coverage-floor` 加报告新鲜度校验（默认 30 分钟）。修后本地跑仍 EXIT=1，但原因是 vitest **收尾**删 `coverage/.tmp` 被 SAFE_DELETE hook 拦，与代码无关；实测测试 **1113 文件 / 12311 用例全过**、覆盖率 lines 60.77% / statements 59.56% / functions 53.30% / branches 50.73% **全部高于地板** |

**写脚本时自己踩的坑**：`spawnSync` 默认 `maxBuffer` 只有 1MB，而 `check:coverage` 这类跑全量单测的段
输出可达数十 MB ⇒ `ENOBUFS` ⇒ 返回 `status=null`，看起来像「被信号杀死」，**首次实测就把 `check:coverage`
误报成红**。修法：`maxBuffer: 64MB`，并区分「命令自己非零退出」与「被超时/信号终止」（后者打印 signal）。

> 判读纪律（现在可以精确执行了）：**看到 `check:release` 红，先看它执行到第几段**；
> 要做全量体检就用 `check:release:all`，它的汇总会告诉你「34 段里到底几段红」。

**端口口径（已核清，非冲突）**：`build/config/vite.config.desktop.ts:9` 与 `tauri.macos/windows/linux.conf.json` 的 devUrl 都是 **6130**（日常桌面开发）；`tauri.android/ios.conf.json` 是 **5210**（移动与 mobile e2e）；`playwright.config.ts:26,67` 自起 **5211** 供 `desktop-chromium` 使用（与开发者手起的 6130 隔离）。因此 `TJG-前端启动与联调环境指南.md` 写 6130、联调报告写 5211 **都不算错**，缺的是「场景」这一维。P1-4 只做表述规范化，不统一取值。

**处置建议**：指南的定位收敛为「如何起环境 + 三个端口各管什么」，基线值与判定归 `live-status.json`，避免两处各写一份。

**⚠️ 手起 dev server 的两个坑（2026-11-19 实测，都会表现成「登录 502」）**：

1. **必须显式传 `VITE_HOMESERVER_URL`**。`.env.local` 里 `VITE_HOMESERVER_URL="https://matrix.test"`（TLS 由 NGINX 终止），但该入口当前**不可达**——`synapse-nginx` 只绑在局域网地址 `10.168.1.231:443`，`127.0.0.1:443` 无监听（`https://matrix.test:8443` 走 `synapse-nginx-proxy` 才是通的）。于是 vite proxy target 指向不可达的 https ⇒ `ECONNRESET` ⇒ `/_matrix/client/v3/login` 返回 **502**，而直连 `127.0.0.1:8008` 一切正常。
2. **`reuseExistingServer: !CI` 会静默复用配置不全的 server**。Playwright 自起时会注入 `VITE_HOMESERVER_URL: liveHomeserverUrl`（来自 `MATRIX_LIVE_HOMESERVER_URL`），但你自己 `pnpm dev` 起的那个不会。端口已被占用 ⇒ Playwright 直接复用 ⇒ 你拿到一个 proxy 错的 server，且**没有任何提示**。

正确的本地跑法（预热 + 复用，避免每次都付冷启动编译代价）：

```bash
VITE_HOMESERVER_URL=http://127.0.0.1:8008 TAURI_ENV_PLATFORM=windows \
  NODE_OPTIONS='' CODEBUDDY_BROKERED_FS_HOOK_ENABLED=0 pnpm dev --host 127.0.0.1 --port 5211 &
# 先 curl 预热关键模块，再 CI= 复用跑测试
CI= npx playwright test e2e/<spec> --project=desktop-chromium --workers=1
```

## 11. 风险与回滚

| 风险 | 触发条件 | 影响 | 应对 |
|---|---|---|---|
| 存量 spec 本身不稳定 | nightly 首周 | 常红 → 被无视 | 首周只记录不告警；把抖动条目在 manifest 标 `flaky: true` 并单独跟踪 |
| 并行写者 sweep | 本仓并行写者活跃 | 新脚本被误提交或覆盖 | 显式 pathspec 提交 + 提交后 `git show --name-only HEAD` 核对 |
| `matrixLive.ts` 接口变更 | 有人改 23 个环境变量 | 入口脚本失效 | P0 只读不改；如需改走单独评审 |

| 真机资源不足 | 双 AVD 各 3 GB，宿主 16 GB | L4 跑不起来 | L4 默认不进 nightly，只在 release 前跑 |
| 时效四元组误伤 | 本地重建容器但未更新基线 | 误报 drift | `--allow-drift` + `drift_reason` 显式豁免 |

**回滚**：P0 改动集中在 3 个新增文件 + `package.json` 3 行（2 个 script + 1 处 release 链）+ `quality-gate.yml` 1 行；回滚 = 删 3 个文件并 revert 那两处，不涉及数据迁移，无锁表风险。

### §12.8 根因闭环：三条「真缺陷」其实是同一个编译 500（2026-11-19 00:00–00:20）

**现象**：`room-settings-live` Phase 3 稳定失败于 `page.evaluate: Execution context was destroyed`（两次复现，非 flaky），失败快照显示页面已回到启动骨架 + 「输入本地解锁密码」弹窗；`account-keyboard-live` 报 `#message-input` 30s 不出现；`my-hub-live` 存储管理 3.0m 超时。

**诊断链（四步，每步都可复现）**：

| 步 | 手段 | 得到的事实 |
|---|---|---|
| 1 | trace 的 `screencast` 帧 | 失败时不是白屏，是**启动骨架** ⇒ app 重置了 |
| 2 | trace 的 `pageError` 事件 | `Failed to fetch dynamically imported module: .../src/layout/right/index.vue` |
| 3 | trace 的 network 快照 | 该模块本身 **200**；其依赖 `src/components/workbench/TjgSpaceTree.vue` 返回 **500** |
| 4 | curl 该模块取错误正文 | `[@vue/compiler-sfc] No fs option provided to compileScript ... resolving imported types`，指向 `defineProps<TjgSpaceTreeProps>()` |

**根因**：`cc0fe2bda`（11-18 19:37）把 `TjgSpaceTree.vue` 的内联 `defineProps<{...}>()` 改成 `defineProps<TjgSpaceTreeProps>()`（类型从 `./useTjgSpaceTree` 导入）。而 `vite-plugin-vue-setup-extend@0.4.0` 在 `enforce:'pre'` 里对**每个** `.vue` 调 `compileScript(descriptor, { id })` —— **没传 `fs`** —— 只为读 `attrs.name`。解析跨文件类型必须读文件 ⇒ 抛错 ⇒ vite 500 ⇒ `layout/right/index.vue` 动态导入失败 ⇒ 右侧面板整片不渲染、页面重置。

这也解释了为什么 `vue-tsc` 与 `pnpm build` 全绿：build 走 `@vitejs/plugin-vue`（传了 fs），只有 dev 的第三方 pre 插件没传。**门禁全绿但 dev 白屏**。

**修法**：移除 `vite-plugin-vue-setup-extend`，5 个用 `<script setup name="X">` 的文件改用 Vue 原生 `defineOptions({ name: 'X' })`（仓库里已有此模式）。同时把 `HMR_LAZY_LOAD_FILTER` 清空 —— 它原本把 `'layout/right/index.vue'` 当作「dev 时序噪声」过滤，真缺陷出现后成了眼罩。

**验证（真后端 + 真账号，同一 dev server 内连续跑）**：

| spec | 修前 | 修后 |
|---|---|---|
| `room-settings-live` | ❌ 2/3，Phase 3 `context destroyed` | ✅ **7/7**（1.7m） |
| `account-keyboard-live` | ❌ 0/1 | ✅ **1/1**（17.0s） |
| `my-hub-live` | ❌ 5/6，存储管理 3.0m 超时 | ❌ **5/6**，存储管理 **27.2s 通过**；仅推送设置失败（见下） |
| `room-key-request-live`（基线） | — | ✅ 1/1（28.8s） |

**本轮自己踩的坑（记下来避免重犯）**：第一版修法是写了个本地插件替代，但 `transform` 返回 `map: null` 丢了 sourcemap ⇒ 任何 HMR 都降级成 **full reload** ⇒ 登录 `page.evaluate` 被销毁，连原本通过的 `room-key-request-live` 也红了。**改插件不能只看编译结果，要看它对 HMR 的影响。**

**FE-F5 已落地（2026-11-19）**：`pushMobileRoute` 新增 `expectPath` —— 不传时，字符串 target 自动用它做前缀校验，`{ name }` 对象不校验；只多读一次 `currentRoute`，**不引入额外等待**（`settleMs: 0` 的计时用例零成本）。这样「根本没跳过去」不再伪装成「页面缺元素」。

### §12.9 `my-hub-live` 定性为 flaky（`FE-F6`）：失败点会漂移

落地落点校验后连跑多次，结果并不稳定——**失败点在不同跑次之间来回换**：

| # | 预热内容 | 结果 | 失败项 |
|---|---|---|---|
| 1 | 通知历史 + 存储管理 | 4/6 | 4 条报「router 实例不可达」 |
| 2 | 同上（修 `$router` 等待后） | 5/6 | 存储管理 3.0m 超时 |
| 3 | 同上（根因修复后） | 5/6 | 推送设置「未跳转」 |

| 5 | 不预热 pushSettings | 5/6 | **首条**九宫格登录 180s 超时 |

三次失败同因（#5 是登录阶段、#6 是三条用例的登录阶段）⇒ 根因是**浏览器态没有系统密钥库**：每次登录都会触发「设置/输入本地解锁密码」门禁，弹层与登录表单渲染竞争，`input` 数量迟迟不到 3。真机有密钥库，不会触发这条路径 ⇒ **不是产品缺陷**。

治理方向（按性价比）：
1. `loginOnMobileUi` 里把 `dismissLocalUnlockDialog` **提到等 input 之前**，而不是现在 poll 内「顺手点」；
2. 登录页模块纳入预热清单（`Login.vue`／`AutoLoginForm.vue`）；
3. 首条用例吃的是**冷启动编译成本**，应单列预算，不要和功能超时混用——否则「谁排第一谁超时」。

⇒ 这条的教训是：**单次绿/红都不可信，先看失败点是否漂移**。漂移即 flaky，继续追「哪个功能坏了」是白费力气。
### §12.10 门禁处置改进与一次「测试被 in-flight 半成品污染」的实例（2026-11-19 10:1x）

**改进**（`e2e/support/androidDevice.ts` 的 `loginOnMobileUi`）：原 poll 每轮只给门禁 300ms，而弹窗有进场动画，常常「点了但没点到」；现在给 1s，并且**门禁仍在就返回 0**——逼 poll 继续等到它真的消失，而不是把「被遮住时的中间态 input 计数」当结果。

**效果**：门禁类失败从「一次跑 3 条」降到「1 条」，**有效但未根除**。

**连跑两次的新证据（都 5/6，但失败项不同）**：

| 跑次 | 失败项 | 错误 |
|---|---|---|
| run1 | 九宫格 | `page.evaluate SyntaxError: timelineOutcomes.ts does not provide an export named 'normalizeRoomFilesPage'` |
| run2 | 存储管理 | 登录表单未渲染出 3 个输入框（门禁） |

⚠️ **run1 的失败不是产品缺陷，也不是本方案的债务**：工作区的 `src/services/matrix/room/timelineOutcomes.ts` 被并行写者删了 122 行（含 `export function normalizeRoomFilesPage`），而 `TimelineService.ts:21` 仍在 import 它。HEAD 里该导出是存在的（`timelineOutcomes.ts:462`），所以这是**在飞半成品**——若被误提交，消息页会整片报错。

⇒ 由此得出一条更前面的判断：**测之前先看工作区有没有 in-flight 不一致**。有的话，任何 live 结论都不成立，因为失败项可能来自半成品而不是被测对象。这也是本轮停在这里、不再继续刷 `my-hub-live` 的原因。

**结局（同日 10:4x）：等拆分自洽后连跑两次，`my-hub-live` 均 6/6（2.8m / 2.7m，各用例 22–37s 无卡顿）。**

⇒ 所以「停一下、等工作区自洽再测」是对的：如果当时硬刷，只会把半成品的失败当成产品缺陷，浪费更多轮次。这条与 §3 的判读口径合起来看——
**一个失败要同时排除「探测器问题」「环境 in-flight」「真缺陷」三种可能，才谈得上定性**。
