## /keys/query 429 风暴排查与修复
- **风暴机制链**：synapse-rust/nginx 持续 429 → 客户端 MatrixRateLimitInterceptor 对 POST 一律不重试直接放行 → SDK OutgoingRequestProcessor.requestWithRetry 重试 4 次（calculateRetryBackoff，>4 放弃）→ rust-crypto 出站请求重新入队 → 下个 sync 周期（3-6s）再打一次 → 无限循环。
- **服务端两个 429 来源**（synapse-rust 仓库）：① Rust 中间件 `rate_limit.rs` 按 IP+endpoint 令牌桶，`fail_open_on_error: false` 时限流器故障会 fail-closed 全量 429（带 x-ratelimit-remaining 头）；② nginx `matrix_api` zone 10r/s per IP burst=50 nodelay + `limit_req_status 429`（无 x-ratelimit 头）。
- **修复（Tjg 端）**：`MatrixRateLimitInterceptor.ts` ①新增幂等 POST 白名单（/keys/query、/keys/changes），429 时按 retry_after_ms 退避重试（429=服务端未处理，重试无副作用）；②新增端点级熔断器——连续 3 次 429 开路，指数冷却 5s→120s，熔断期返回合成 429（带 retry_after_ms 头，SDK safeGetRetryAfterMs 会按其退避），成功响应自动复位，`__resetRateLimitCircuitForTests` 供测试。`runtimeFetch.ts` 429 日志增加 retry-after 与 x-ratelimit-remaining 头以区分 nginx/Rust 来源。
- 验收：32/32 测试通过（新增 4 例），vue-tsc 0 错，biome clean。
- **遗留（服务端）**：需检查 matrix.test 部署的实际 rate_limit.yaml 与 Rust 日志是否有 "Rate limiter error"；建议 /keys/* 端点改按 user 限流而非 IP。

### 429 现网日志判读（07:54 matrix.test，二诊）
- 现象：friends/requests in+out、keys/query 多 endpoint 同时 429，均无 retry-after 与 x-ratelimit-remaining 头 → 判定为 **nginx per-IP 限流**（Rust 中间件会带 x-ratelimit 头）。
- 根因定性：**启动突发（thundering herd） vs nginx 10r/s per-IP burst=50 nodelay**——启动瞬间 initial sync + crypto keys/query + friends initialize 并发，burst 桶秒空后 nodelay 全量 429；好友轮询 30s 一次非风暴源。前端熔断/退避按设计工作（attempt 1/3、~1s 退避、无无限循环）。
- 结论：**非前端 bug**，服务端限流配置与正常同步流量不匹配（dev 单 IP 放大）。改进：服务端 /keys/*、/friends/* 按 user 限流或 dev 放宽 burst；前端可选启动错峰 + 多窗口共享轮询。

## MatrixClient 重复初始化收敛：initialize 幂等守卫 + loginWithToken 预解析 deviceId
- **根因链**：`loginWithToken` 在 `config.deviceId` 缺失时先 `initialize(deviceId: undefined)` 建 client → 刚 createClient 的 `getDeviceId()` 常为空 → 走 whoami 回填 → **第二次 initialize**。而 `MatrixConnectionManager.initialize()` 无幂等保护，直接覆盖 `this.client`，旧 client 泄漏。表现为日志中 MatrixConnection 初始化成对出现、synapse `keys/query` 多次 429（E2EE 设备密钥查询翻倍）、阅读回执重复（两套事件监听器）。

## runtimeFetch 回退浏览器 fetch 的回归修复（18:03，对应日志 WARN）
- **症状**：`[RuntimeFetch] Tauri native fetch failed, falling back to browser fetch The resource id 3191644895 is invalid.`（sliding sync 长轮询 `/_matrix/client/unstable/org.matrix.simplified_msc3575/sync?...timeout=30000`）。
- **本质**：这是 Tauri plugin-http 在「请求被主动取消 / 插件自身资源表竞态 / /sync 自激循环里 rid 被挤掉」时抛的取消语义错误，**不是网络故障**。但 `runtimeFetch.ts` 旧逻辑把"是否当 abort"**门控在 `init.signal.aborted`**，当 JS 信号未置位时走到 `shouldUseBrowserFallback(input)`（按 URL 命中）→ **回退浏览器 fetch 并重放 SDK 已放弃的 /sync 长轮询**，产生幽灵重复请求——正好违反 08-09 既定铁律「Tauri resource id invalid / Request cancelled ≠ 网络错误：命中则归一化 AbortError，不回退浏览器 fetch、不重试」。
- **更隐蔽**：真实报错是 "The resource id **3191644895** is invalid."，而旧 `isRetryableNetworkError` 用 `includes('resource id invalid')`（中间无数字）子串匹配不上，说明对真实格式早已失效。
- **更糟**：`runtimeFetch.test.ts:178` 旧用例**断言了被禁止的行为**（`resource id invalid` 无 abort 信号时应"回退浏览器 fetch 并重试"），把 bug 当成了规格。已删除该用例。
- **修复**（`src/services/matrix/network/runtimeFetch.ts`）：
  1. 新增 `isTauriCancelError(error)`：按错误内容识别（`message.includes('resource id') && includes('invalid')` 覆盖 "The resource id X is invalid."；`includes('request cancelled')`），**不依赖 JS signal**。
  2. catch 守卫由 `if (isSignalAborted(init))` 改为 `if (isSignalAborted(init) || isTauriCancelError(error))` → 命中直接 `throw createAbortError(url)`，**不回退、不重试**。
  3. `isRetryableNetworkError` 移除 `resource id invalid`（取消错误已在更早 catch 归一化，不该再被当可重试网络错误；且子串本就匹配不上真实格式）。
- **回归测试**：`runtimeFetch.test.ts` 新增「The resource id 3191644895 is invalid. 无 abort 信号 → rejects AbortError、browserFetch 不被调用」；原"无信号回退重试"用例改为用真正网络错误 `error sending request` 触发（保留回退+重试行为，仅限真网络故障）。
- **验收**：runtimeFetch 11/11 + MatrixClientService.slidingsync 16/16 全绿、biome 2 文件 clean、vue-tsc 0 errors。
- **意义**：这是 08-09 之前已写下的约定被代码+测试违反的典型案例——改之前应 grep 关键约束（"不回退浏览器 fetch"）确认实现与约定一致。
