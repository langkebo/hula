## 铁律（新增）：工作区存在**并发会话**时禁止批量提交
- 现象：同一 working tree 下另一会话在跑 `git add` / `git commit` / **`git reset`**；共享 `index` 与 `.git/COMMIT_EDITMSG`。
- 已致损害：①我 `git add` 的 16 个文件被对方 `git commit`（无路径限定）**吞进对方提交**；②对方 `-m` 写入 `COMMIT_EDITMSG`，
  我的 `git commit` 读回**对方的提交信息**（内容对、信息错）；③对方连续 `git reset` 把我的提交**回退掉**（reflog 可见 `reset: moving to ...`）。
- 防护：一律 **`git commit -m "msg" -- <显式路径>`**（pathspec 模式给钩子临时索引，只含我指定路径，不吞对方暂存）；提交前查
  `git diff --cached --name-only` 是否已被他人暂存；提交后用 `git merge-base --is-ancestor <sha> HEAD` 确认提交**仍在祖先链上**；
  大批量改动前先 `cp` 一份工作区副本到仓外（本次已备份至 `/tmp/tjg_style_backup_*`）。
- 结论：并发会话活跃时应**先让对方停下**再提交，否则历史归属不可控。

## 第九批：pnpm allowBuilds 阻塞修复 + 三个上游级发现

**交付**（提交 `330f7b89`，仅 1 文件）：`pnpm-workspace.yaml` 的 `allowBuilds` 由占位符填为真布尔值，并删除已死的 `onlyBuiltDependencies`。

**定因**：`set this to true or false` 不是手抖——**是 pnpm 12 自动写入的占位符**。官方文档原文：install 时未列入 `allowBuilds` 的待审依赖会被自动追加到 `pnpm-workspace.yaml` 并写入占位符值，待人工裁决。`allowBuilds` 自 **v10.26.0** 引入，**v11 起取代** `onlyBuiltDependencies`/`onlyBuiltDependenciesFile`/`neverBuiltDependencies`/`ignoredBuiltDependencies`/`ignoreDepScripts`（旧设置在 v12 下是**静默死配置**，这是 @vue-office 明明写在 onlyBuiltDependencies 里却仍被 ignored 的原因）。

**裁决判据 = 与 CI（pnpm 10）既有审批结果对齐**，而非主观判断哪个包「必要」：
- `@parcel/watcher` / `esbuild` → **false**（均已有预编译平台包 `@parcel/watcher-darwin-arm64` / `@esbuild-darwin-arm64`，本地编译只是回退路径；`esbuild: false` 本身就是 pnpm 官方示例）
- `@vue-office/*` ×4 / `msw` / `vue-demi` → **true**（承接 workspace `onlyBuiltDependencies` 与 `package.json` `pnpm.onlyBuiltDependencies` 的原有意图；postinstall 均为幂等的 switchVersion / 无害）
- `unrs-resolver` / `sharp` **不在 lockfile 依赖树内 → 不列**，避免臆造条目

**验证**：变异自证（只把 esbuild 改回占位符 → `ERR_PNPM_IGNORED_BUILDS` **精确只点名 `esbuild@0.28.1`**；还原 → exit 0）· `pnpm-lock.yaml` sha256 未变（`1116d689…`）· `vue-demi/lib/index.mjs` mtime 变成本次 install 时刻（证明 true 真执行了脚本）· vue-tsc 0 错 · ratchet/i18n 门禁全绿。

**三个新发现（上游级，已固化进新 skill）**：
1. **pnpm 依赖新鲜时整段跳过 install（连审批检查一起跳过）**：改完 pnpm 配置直接跑 `pnpm install` 可能输出 `Done in 55ms` 什么都不做 →「看起来修好了」实为**根本没检查**。**复现与验证必须加 `--force`**（`--dry-run` 同样不做审批检查）。
2. **绝不能用旧版 pnpm 对高版本生成的 lockfile 跑 `--force`**：install 是**先删旧依赖再链接**，低版本在 frozen 校验阶段失败退出会留下 `node_modules` 残骸（`node_modules/typescript`、`.bin/vue-tsc` 消失；`npx` 于是去 npx 缓存抓不匹配版本 → `ERR_PACKAGE_PATH_NOT_EXPORTED: './lib/tsc'`）。本次实测踩到，用**同版本** `pnpm install --frozen-lockfile --force` 修回。
3. **CI 长期全红 + `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` 的真根因 = pnpm 双版本交替写 lockfile**：本机 corepack→**12.4.1**、homebrew→**10.30.1**、CI `version: 10` 三处并存。铁证：`pnpm-lock.yaml` 顶层 `overrides:` 块在 commit 之间 **0/1 反复横跳**（09-13/14 有 → **09-18 丢** → 09-19 回 → 09-20 又丢）。pnpm 12 不读 `package.json` 的 `pnpm.overrides` → 重写 lockfile 时**抹掉该块**；CI 的 pnpm 10 仍读那 5 条 overrides → 与 lockfile 记录不符 → **`--frozen-lockfile` 必失败**（已用 CI 同款 10.30.1 本地确定性复现；且换 HEAD 版配置同样复现 → **与本批改动无关**）。
   补充：Quality Gate 历史 **15/15 全 failure**（08-23 起，含 push master），且失败 job 被中途终止（harden-runner lockdown / orphan cleanup / `UNKNOWN STEP`）→ CI 红另有**平台层成分**，不能只归因 mismatch。

**建议下一批（待授权）**：① `package.json` 加 `"packageManager": "pnpm@10.30.1"`（与 CI `version: 10` 对齐，且 ≥10.26 仍支持 allowBuilds）并重生成 lockfile；② 若决定留在 pnpm 12，则把 `overrides` 迁进 `pnpm-workspace.yaml` 再重写 lockfile。二者任选其一才能真正消除漂移。

**新 skill**：`pnpm-allowbuilds-version-drift`（症状 / 根因模型 / 裁决判据 / 四个陷阱 / 验证三步 / 根治方案 / 收尾清单）。
