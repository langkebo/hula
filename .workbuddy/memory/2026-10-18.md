## P0-8：SecretChatPage 页面级收尾

### 锁定态视图（最容易泄漏的一屏）
- `locked = !useSecretChatSession().isUnlocked`：直接读单例的**响应式 computed**，不用事件
  （事件会漏掉「自动锁 / 另一窗口上锁」等路径；computed 天然跟着状态走）
- 锁定态：列表 `v-if` 掉 + `hiddenSessions` **直接返回空数组**（双保险，模板改坏也不泄漏）
- **不用 blur/灰度过遮罩**：遮罩能被读屏与截图绕过；而且会话名本身就暴露「你和谁有私密往来」
- **不再跳走**：原实现 `router.replace('/message')`，现改「留在本页 + 锁定态 + 输入密码继续原地解锁」

### 关闭即锁的坑
`handleClose` 里 `lockSecretChatSession()` 再 `router.back()`。
⚠️ **只在显式关闭时上锁，不要放 `onUnmounted`**：点会话进房间会触发卸载，
若那时上锁，路由守卫会立刻把目标房间拦掉（表现是「点了没反应」）。

### 其它
- 副标题如实化：`home.secret_chat.subtitle` =「本机加密显示；服务端仍按保留策略保存消息」
- 原地解锁后要补一次 `loadPrivateRoomRegistry`（`onMounted` 在锁定态提前 return 了）→ `watch(isUnlocked)`
- 模板里 `'条未读'` / `'的头像'` 两处硬编码中文改为 `t(key, { count / name })`
- 文件 400 行整（新文件硬限 400），压注释时注意别涨

## P0-0 遗留收尾：移动端私密房门禁（P0 批次真正闭环）

### 洞在哪
桌面守卫 `secretChatGuard.extractRoomId` 只认 `message` / `windowChat` 的 `:roomId`；
移动端房间路由是 `/mobile/chatRoom/chatMain/:uid?`（参数是**对端 uid**）⇒
**移动端整条路径绕过门禁**：通知点击可直达私密房，连解锁框都不弹。

### 改法
- `composables/secretChat/useMobilePrivateRoomGate.ts`（84 行）：`assertAccess(uid?)`
- 挂在**聊天布局层** `ChatRoomLayout.vue`：`watch([route.name, route.params.uid], {immediate:true})`
  —— keep-alive 下再次进入只触发 watch，所以不能只靠 onMounted

### 四条判据（都有单测）
普通房放行 / 私密房未解锁→请求解锁+replace / 私密房已解锁→放行 /
登记表加载失败→**不放过**（宁可拦错也不漏，且必须给提示，否则像 bug）；
另：私密房存在但当前账号无密码配置 → 拦下并提示，**不许退化成普通房**。

### ⚠️ 写用例时发现的真实缺陷
候选房间必须**两个都看**（`globalStore.currentSessionRoomId` + uid 反查）。
只看前者时，通知点击可能还停在上一个**普通房** ⇒ 私密房被放行。

### ⚠️ 变异自证暴露的「假通过」
「私密房已解锁→放行」用例最初没设 `currentSessionRoomId=''`，
于是走的是「第一个候选是普通房 → 提前放行」，**根本没测到解锁分支**
（去掉解锁判定后该用例仍绿）。修正后变异才被抓到。
教训：**放行类断言必须确认它命中的是目标分支**，否则就是自洽测试。
