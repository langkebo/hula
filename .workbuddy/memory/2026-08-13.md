## storage 优化方案分析（产出 docs/storage-optimization-plan.md）

### 后端 synapse-rust 缓存机制（synapse-cache crate，4530 行）
- **双层缓存**：L1 moka 内存（max_capacity 100_000）+ L2 Redis（deadpool-redis）
- **分级 TTL**（strategy.rs CacheTtl）：presence 60s → token 300s → room 900~1800s → profile 3600s；负缓存 not_found 300s；批量缓存
- **统计指标**：DegradationMetrics（local/redis hit/miss、熔断、降级、hit_rate、degradation_rate）+ CacheStats（hits/misses/evictions/total_entries/memory_usage_bytes/hit_rate）
- **暴露**：Prometheus `/metrics` + `/_synapse/admin/v1/telemetry/metrics`

### 前端 storage 现状
- localStorage 60+ 键、47 文件，无统一管理；IndexedDB 9 文件（搜索索引/crypto/SDK 状态）
- **REFRESH_TOKEN 明文存 localStorage**（安全风险）
- 缩略图缓存（thumbnailCache.ts）是唯一有 TTL+LRU（7天+500MB）的
- settingsSchema 无 storage tab

### 方案四阶段
1. 安全：REFRESH_TOKEN 迁移 + 命名规范（统一 tjg. 命名空间）
2. 统计：FrontendCacheStats 对齐后端 CacheStats（hits/misses/evictions/memory/hitRate）
3. UI：storage 设置项（占用统计 + 清理 + 容量配置）
4. 治理：通用 ExpirableCache 推广（抽离 thumbnailCache 的 TTL+LRU 逻辑）

### 关键结论
前端核心问题不是"缺缓存"，而是"缓存无治理"；后端双层缓存+分级 TTL+完整统计是前端对齐基准

- rust-crypto store 用 RUST_SDK_STORE_PREFIX 的 IndexedDB（加密密钥/设备数据**持久化**）
- **退出登录（SessionLogoutService）只清 localStorage token，未调用 clearClientStores** → rust-crypto IndexedDB 残留（切换账号安全/容量风险）

### 集成结论
- **能靠 SDK**：清理（clearClientStores，P0 集成到退出登录 + storage 设置项"清理 SDK 数据"按钮）；store 持久化模式切换（IndexedDBStore vs StubStore）
- **不能靠 SDK**：容量统计（navigator.storage.estimate）、命中率统计（前端埋点）、自有缓存治理（ExpirableCache）——需前端自研

## 两步走方案（SDK 封装后端缓存体系 → 前端集成）

### SDK store 现状缺口（核验）
- **无 TTL**（后端 CacheTtl 分级 60s~3600s）
- **无统计**（后端 CacheStats：hits/misses/evictions/memory/hit_rate）
- **局部容量限制**（MemoryStore OOB 50、pending 100，无统一预算）
- 已有：clearClientStores 清理 + MemoryStore 局部 LRU

### SDK 数据分类与后端对应
- SDK IndexedDB 表：users/rooms/sync/oob_membership_events/to_device_queue
- 对应后端：user_profile / room_info / room_members / sync token

### 两步走方案（已写入 storage-optimization-plan.md 第四章）
1. **第一步（SDK 增强）**：新增 `src/store/ttl.ts`（分级 TTL 对齐 CacheTtl）+ `src/store/stats.ts`（StoreStats 对齐 CacheStats，Atomic 无锁计数）+ 统一容量管理；改完 `pack-sdk-tarball.mjs --apply` + pnpm install
2. **第二步（前端集成）**：用 SDK StoreStats 查询占用/命中率 + storage 设置项统一仪表 + clearClientStores 清理
- 收益：SDK store 获得与后端对等治理能力（TTL+统计+容量）
- 风险：第三方库改动需重新打包 tgz + 回归 SDK 单测；TTL 勿误删 sync token（导致重复全量同步）
